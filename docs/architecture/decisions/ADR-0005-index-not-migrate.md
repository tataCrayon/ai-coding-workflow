# ADR-0005：索引而非搬迁（不搬家方案）

> 状态：已采纳 ｜ 日期：2026-11-19 ｜ 取代 [ADR-0002](ADR-0002-asset-layering.md) 中「先分类再迁移」的默认路径

## 背景

ADR-0002 定的路径是「先出完整分类表 → 逐层迁移」。评审时提出的替代方案：

> 能不能不搬，只做引用/索引？效果应该一样吧。

## 决策：默认索引，按需搬迁

**运行时资产留在原地**（各工具的 skills / rules / agents / hooks 目录），
本仓只维护**索引与说明**（`skills/CATALOG.md` 之类的目录文件）。

只有在下面两个条件之一成立时，才把单个资产搬进本仓：

| 触发条件 | 为什么索引不够 |
|---|---|
| 需要**版本化**（要能看 diff、回溯、code review） | 家目录不是 git 仓 |
| 需要**跨机器 / 跨人共享** | 家目录是本机目录，别人拿不到 |

## 索引 vs 搬迁：效果是否等价

| 维度 | 索引 | 搬迁 |
|---|---|---|
| 能否被 AI 找到 | ✅ 通过 CATALOG 检索 | ✅ 直接在仓里 |
| 会不会出现两份内容 | ✅ 不会 | ❌ 必然（除非本仓是唯一副本） |
| 运行时是否生效 | ✅ 原地生效 | ⚠️ 需要镜像/链接，否则运行时看不到 |
| 能否 diff / 回溯 | ❌ | ✅ |
| 能否共享给他人 | ❌ | ✅ |
| 维护成本 | 低（只在增删时改索引） | 高（内容改动 + 镜像同步） |

**结论**：对「找得到、跑得起来」这个目标，索引和搬迁完全等价；差异只在版本化与共享。

## 为什么搬迁反而更危险

搬迁的真实形态是：**内容复制到本仓 + 运行时侧保留一份**。
两份内容立刻开始漂移，而 AI 会更信「在 git 仓里的那份」——
这正是 [ADR-0003](ADR-0003-doc-freshness.md) 说的「过期文档污染面变大」。

要避免漂移，搬迁必须配套**单一物理副本**：

| 方案 | Windows 可行性 |
|---|---|
| 目录符号链接 `mklink /D` | ❌ 需要管理员/开发者模式，普通权限失败 |
| 目录联接 `mklink /J` | ✅ 可用、可读、无管理员要求 |
| 单向同步脚本（本仓为源） | ✅ 可用，但多一步、多一处失败点 |

即：搬迁可行，但要额外解决镜像问题；索引方案没有这个问题。

## 后果

**收益**
- 零迁移风险，今天就能用
- 单一事实源，不会出现「哪份是真的」
- 索引本身很轻，维护成本低

**代价**
- **skill 仍然无版本化**：改坏了没法回滚到某个版本
- **仍然无法共享**：换机器 / 给同事，索引指过去是空的
- 索引会滞后：新增 skill 忘了更新 CATALOG 就检索不到

**缓解**
- 索引滞后 → 把「更新 CATALOG」写进新增 skill 的 checklist
- 版本化/共享需求出现时 → 按上表触发条件，**逐个**搬，且必须同时把运行时侧改成 junction

## 与 ADR-0002 的关系

ADR-0002 的 **L1/L2/L3 分层判定依然有效**，但它不再是「迁移计划」，而是「搬迁时的归属判定」。
默认路径由「先分类再迁移」改为「先索引，按需迁移」。

> 补充（V3.2.0）：本仓的 `skills/` 是**向外分发**的种子包，属于上表「需要跨机器共享」的例外——
> 因此核心 skill 直接入住本仓，而**工作区专属 skill**（依赖内部系统的那批）仍只做索引、不入包。
