# ADR-0001：以 home repo 承载跨仓 AI 资产

> 状态：已采纳 ｜ 日期：2026-11-19 ｜ 来源：ai-studio 实践提炼

## 背景

一个工作区可能有十几个独立 git 仓（Java / Go / Gradle / Node 混布），分属多条产品线。
跨仓需求常见（一次改动要动 BFF + 下游服务 + 权限库），但 agent 从某个业务仓起会话时只看得见那个仓。

现状的两个具体问题：

1. **skills / rules 全在家目录**（`~/.claude`、`~/.agents`），没有版本化、无法团队共享、也无从判断哪些其实只服务单个仓。
2. **最有价值的跨仓事实不在任何 git 仓里**：业务链路、DB 连接、接口契约散在各工具的会话记忆里，不进版本控制，不跟任何仓一起走。

## 决策

采用 **home repo** 模式：

- 本仓放：跨仓复用的 skills / rules / agents、共享文档、可执行的仓指针
- 业务代码留在各自仓，本仓不进任何构建链路
- 会话起点：**跨仓任务从本仓起，单仓深挖直接进那个仓**（见 [ADR-0004](ADR-0004-session-start-and-pointers.md)）

## 被否掉的替代方案

| 方案 | 否决原因 |
|---|---|
| **monorepo**：把所有仓合成一个 | 各产品线有独立 CI / 分支策略 / 发布节奏，合仓等于重做发布体系；且有多人协作边界 |
| **保持现状**：全部依赖家目录 | 无版本化、无法共享；skill 无分层，全局上下文被单仓资产污染 |
| **每个业务仓各放一份 skills** | 必然漂移；同一个 skill 改一处要同步 N 处 |
| **git submodule 挂载各业务仓** | 指针需要的是「路径 + 来源」，不是版本锁；submodule 会把本仓 commit 与业务仓绑定，反而增加维护成本 |

## 后果

**收益**
- 跨仓需求不用换会话、不用重复喂上下文
- skills 一份、可版本化、可 review
- 跨仓事实第一次进入版本控制

**代价（必须接受，否则会翻车）**
1. **单仓深度变浅**：从本仓起会话，文件树 / `git log` / 编译报错不在上下文里，要额外去捞。
   → 缓解：`repos/<repo>.md` 只写「进这个仓之前必须知道的事」，剩下进仓再看。
2. **过期文档污染面变大**：单仓的过期文档只坑那个仓；本仓的过期文档坑所有会话。
   → 缓解：每份文档带 `verified:` 日期，见 [ADR-0003](ADR-0003-doc-freshness.md)。
3. **「全局事实源」的信任溢价**：agent 更信本仓文档，错得更彻底。
   → 缓解：文档只写**可验证的事实**（表结构、路径、命令），不写「大概是这样」。
