# 专家包模式（Expert Package Pattern）— V3.0 开发工作流核心

> V3.0 最重要的架构转变：**开发流程从「20+ 个流程 Skill 的描述路由」收敛为「1 个专家包 + 唯一入口 + 轻重双路」**。
> 本文档给出模式定义、迁移方法与实战案例。演进动因见 [EVOLUTION-V3.md](./EVOLUTION-V3.md)。

---

## 一、为什么旧模式失效了

V2.0 的开发流程由一组平行的流程 Skill 构成（sop-pipeline-orchestrator / req-standardizer / spec-verifier / us-coding-engine / cr-review-pipeline…），靠 skill-routing.md 的描述匹配触发。实测暴露三个结构性问题：

| 问题 | 实测证据 |
|------|----------|
| **路由稀释**：25+ 个 Skill 的 description 平摊注意力，"完整需求开发"类触发词经常不命中 | 用户自述"Skill 太多了，AI 并没有真正用到" |
| **双份漂移**：同一 Skill 在两个工具目录各一份，静默分叉 | 盘点出 33 对漂移实体，req-standardizer 两版差 1.8KB |
| **死路由**：路由表描述不存在的能力，越写越长越不可信 | 209 行 alwaysApply 路由表含多个从未存在的 Skill |
| **嵌套过重**：流程层层包裹，小任务也被大仪式拖累 | 3-8 改动点任务 = 30+ subagent、三层 SOP 留痕（OPT-033 诊断） |

**结论**：路由的可靠性不取决于 description 写得多好，而取决于**入口数量足够少**。

## 二、模式定义

```
用户需求
   │
   ▼
┌─────────────────────────────────────────────────┐
│ 专家包入口（唯一）——bootstrap                       │
│ 职责：读真相源 → 分级 S/M/L → 指派阶段技能            │
└─────────────────────────────────────────────────┘
   │            │             │
   S 级         M 级          L 级
   直接做       轻量走        全流程
  （不进包）   （跳可选阶段）  （全门禁）
```

### 1. 唯一入口 + 分级（轻重双路）

| 级 | 判定 | 路径 |
|----|------|------|
| **S** | ≤2 改动点（加字段/改日志/小 bug） | 直接做 + 跑相关验证 + 提交。**不进包**，无 spec 门禁无 SOP 留痕 |
| **M** | 一个可提交的小功能，3-5 改动点 | 轻量 spec（需求 3 句 + 改动点表）→ plan 简版 → impl → verify |
| **L** | 新功能/新表/新接口/动接口语义/跨仓库 | 全流程：spec（含签收门禁）→ datadesign → plan → 分批 impl → verify → **understand（必走）** → handoff |

**两条裁定规则**：分级争议时宁低勿高；但**涉资金/资产/权限的变更一律 L 级**。

### 2. 阶段技能只做一件事

包内每个阶段技能职责单一、互不重复加载（对照实例：backendflow 包 9 件——bootstrap/spec/datadesign/plan/impl/verify/understand/trace/handoff）。深度方法论下沉 `references/`，SKILL.md 本体 ≤500 行（渐进披露）。

### 3. 钩子寄生（不侵入宿主）

横切能力以「只插一行」的方式寄生在阶段节点上，宿主业务逻辑零改动：

| 钩子 | 宿主节点 | 能力 |
|------|----------|------|
| H1 边界问答 | spec 签收门禁前 | 把非平凡决策转成「如果…会怎样」题，**按重要性选材不凑数**；答不上的点回填主文档 |
| H2 理解交接 | verify 后 | 三件套：一页纸 + 实码时序图（带 file:line）+ 自测题，写入理解账本 |
| H3 间隔复习 | spec 开工首步 | Leitner 盒复习队列（≤2 题/需求），连错 2 轮触发补课 |
| H4 能力盘点 | Skill 增删时 | 提醒刷新能力一页纸 + 跑 check-links.py |

详见 [skills/comprehension-ledger/SKILL.md](../skills/comprehension-ledger/SKILL.md)。

### 4. 路由透明化

包内各阶段加载非显而易见的 Skill 时，必须输出一行：「用了 X，因为 Y」——用户始终知道哪个能力被用了、为什么。这是对「路由黑箱」的零成本解法。

### 5. 分层交付（治"方案信息太多"）

L 级方案只给**1 页主文档**（业务目标 3 句 + 改动点表 + 风险 3 条，5 分钟读完）；字段级契约/DDL/备选对比全部下沉附录并标注「仅实施时 AI 读取，人按需查」。信息量由理解缺口驱动，不由"完整"驱动。

### 6. 签收纪律

- 未经用户签收的 L 级方案，一行生产代码都不许写。
- 问答题（Q）与默认决策（D）**分开编号、分节呈现**；默认决策签收时必须显式复述完整清单，**沉默不当作同意**。
- 方案给 ≥2 选项带推荐；用户动手改过至少一处（或口述修改 AI 落稿后确认）才算签收。

## 三、迁移方法（从 V2 流程 Skill 迁到专家包）

1. **盘点**：列出全部流程类 Skill，标注哪些阶段被真实用过（看 eval 日志，不凭印象）。
2. **归档不删除**：旧流程 Skill 移入归档目录，内容有价值的下沉为包内 `references/`。回滚 = 移回来。
3. **建入口**：写 bootstrap SKILL.md（分级表 + 阶段地图 + 真相源约定），路由表只指向它一个入口。
4. **域化**：从通用骨架出发，把领域铁律（如金融的 BigDecimal 精度/多租户/幂等）写进 impl/datadesign，而不是另立 Skill。
5. **接账本**：四钩子按第二节第 3 条插行；创建 `.agent/understanding/ledger.md`。
6. **巡检**：跑 `scripts/check-links.py`，路由表与包内引用零死链才算迁移完成。

## 四、实战案例：backendflow（Java 金融后端域）

- 触发：用户反馈"Skill 太多没被真正用到"+"做完需求我对业务没印象"（OPT-035/036 立项）。
- 动作：33 对漂移实体归档归一 → 第一代 9 个流程 Skill 退役 → backendflow 9 件包（唯一入口）→ comprehension-ledger 四钩子寄生 → 规则层 core/methodology 分层（常驻注入 -60%）。
- 实测（首个 L 级需求）：现状摸底发现**约七成已在历史分支实现**（255+87 commits），需求性质修正为"合分支+增量"，merge-tree 提前探出 10 文件双改冲突；签收门禁忠实生效（未签收零代码）。教训：H1 出 9 题连发导致用户只答前 3 → 已修正为按重要性选材 + Q/D 分离。
