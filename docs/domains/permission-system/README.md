# 权限系统（示例业务域）

> verified: 2026-11-23 ｜ 验证方式: 示例内容，演示多仓机制写法；部署前请替换

> 本文件是**写法示例**，不是任何真实系统的文档。演示「一个跨多仓的机制该怎么写」。

## 这个域是什么

统一权限体系：权限点定义、角色绑定、租户隔离。**不负责**：认证（登录态）本身、业务侧鉴权逻辑的实现。

## 涉及哪些仓

| 角色 | 仓 | 职责 |
|---|---|---|
| 源头 | `permission-web` | 权限点与角色定义的唯一写入方 |
| 管理中台 | `permission-admin` | 运营侧配置界面，写源头库 |
| 消费方 | 各业务 BFF | 启动时拉取本租户权限快照，本地缓存 |

仓指针集中维护在 `repos/INDEX.md`，此处不重复路径与 clone 地址。

## 核心机制：源头 + 同步

```
permission-web (源头库) ──定时差异同步──> 各租户库 ──> 业务 BFF 读取
```

三条硬事实（这几条最容易踩）：

1. **直插租户库会被同步任务清掉**——差异同步以源头为准，租户库是派生数据
2. **权限点 ID 全局唯一**，跨环境一致；改名不改 ID
3. **同步任务失败不会自动回滚**，表现为「改了源头但业务侧看不到」

## 从哪进代码

| 要做什么 | 从哪看 |
|---|---|
| 新增权限点 | 源头库的定义表 + 同步任务的映射规则 |
| 排查「权限改了不起作用」 | 先看同步任务最近一次执行记录，再查租户库快照时间 |
| 改鉴权逻辑 | 业务 BFF 的拦截器，**不要**改源头 |
