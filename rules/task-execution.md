# 统一任务执行框架

> 本文件职责：定义代码任务的**执行规范**，包括任务命名、简单任务快速闭环、复杂任务防御式执行。
> 熔断协议由 `circuit-breaker.md` 统一定义，本文件不重复熔断流程。
> Spec 模板详见 `task-execution-spec-template.md`；验证与审视详见 `task-execution-validation.md`；长任务上下文管理详见 `task-execution-context-management.md`。

## 🔒 SOP 三条铁律（Pipeline 编排时强制）

> 触发条件（V3.0）：专家包 L 级全流程、或任何批量连续执行多任务的场景（含旧 sop-pipeline-orchestrator/R/A/X 编排，保留作兼容提法）。以下铁律不可协商。

### 铁律 1：不许中途停下
SOP 启动后必须执行到最终提交完成；每步完成后立即进入下一步，不停顿、不等待、不询问。
**仅以下情况允许停下**：① 需求分析后等用户确认理解 ② 测试 N 轮仍失败 ③ 评审 N 轮自修复仍失败 ④ commit 后等用户确认再 push ⑤ push 失败 ⑥ 需用户提供信息。

### 铁律 2：验证才能声称通过
没有运行验证命令的输出 → 不能声称通过。"应该没问题""看起来正确" = 不合格。

### 铁律 3：测试轻量优先
测试优先用轻量隔离方案（纯 Mock、不启动重量级容器/上下文）。重量级上下文失败 → 立即降回轻量方案，不花时间修上下文。先编译通过再跑测试。

## 📝 任务命名规范（全局约束）

所有 AI 生成的"任务描述"类产物，**名称必须具体到可执行**，遵循公式：

**`[动作] + [目标对象] + [具体内容]`**

| ❌ 模糊命名 | ✅ 具体命名 |
|------------|-----------|
| 修改相关代码 | 在 `UserService.validateEmail()` 中添加格式校验 |
| 处理逻辑 | 为 `CreateOrderRequest` 的 `amount` 字段增加非空校验 |
| 写测试 | 为 `PriceCalculator.calculate()` 编写边界值单元测试 |
| 做 Review | 对 `OrderBatchService` 的本次变更执行 Code Review |
| 20260401_修改代码.md（存档文件名） | 20260401_OrderBatchService增加金额精度校验.md |

**底线**：读名称就能知道"改哪个文件/类的什么东西"，不需要展开详情。

## 🎯 简单任务 vs 复杂任务

模型根据任务复杂度自主判断执行方式，无需显式分类。

### 简单任务（单文件修改、纯逻辑修复、判空防护、文案修改等）

1. **意图声明**：用 1-2 句话说明要改什么以及为什么
2. **直接实施**：直接执行代码修改，或在需要并行/上下文隔离时委派 子代理（Coder）执行
3. **闭环**：向用户报告完成结果

**⚠️ 升级信号**：执行过程中若发现实际影响面扩大（≥2 个文件联动、接口签名变更、扩展点变更、数据库 Schema 变更），必须切换到复杂任务流程。

## 🎯 复杂任务执行流程（10 步概览）

以下为复杂任务的 10 个执行步骤，每步仅列一行概要，详细规则见对应子文件。

| 步骤 | 概要 | 详细规则 |
|------|------|---------|
| 1 | 任务持久化：在 `.agent/context/` 下创建任务文件夹或单文件 | `task-persistence.md` |
| 2 | 分析评估：业务分析(2a) + 实现模式提取(2b) | 本文件步骤 2 详解 |
| 3 | Spec 生成：产出结构化 Spec 给用户确认（No Spec, No Code） | `task-execution-spec-template.md` |
| 4 | Spec 实体验证 | `task-execution-validation.md` |
| 5 | 设计交叉验证与多视角审视 | `task-execution-validation.md` |
| 6 | Checkpoint：等用户确认 Spec 后再继续 | `task-execution-validation.md` |
| 7 | 实施代码编辑：按 Spec 技术方案逐个子任务执行 | — |
| 8 | 质量防线 | `task-execution-validation.md` |
| 9a | 编码期测试守护：只运行已有测试，不为新代码写测试类 | — |
| 9b | 测试类落地（代码定稿后）：依据 Spec 测试用例清单兑现为可执行测试类 | `unit-test-master` Skill |
| 10 | 验收与存档：对照 Spec 验收标准逐项确认，Reverse Sync | `task-persistence.md` |

### 步骤 2 详解：分析评估

**2a. 业务分析**：查阅知识资产，调用 `java-change-impact-analyzer` 或 `code-business-analyzer` Skill 做业务分析或变更影响评估。需要并行分析多模块时，可委派 子代理（Analyzer）。

**2b. 实现模式提取**（编码类任务必做）：读取目标模块中**已有的同类代码**，提取以下信息供 Spec 使用：
- **分层与目录结构**：各层的实际包路径/目录
- **代码风格范本**：实体类用什么注解、字段用基本类型还是包装类型、数据访问层的写法约定
- **基础设施约定**：ORM 映射文件的目录和命名规范、枚举风格
- **集成点接口签名**：需要调用的现有 Service/数据访问层的实际方法签名和参数类型

> **为什么在设计阶段就做？** 这些信息决定了技术方案的可行性和具体性。如果等到编码阶段才看，Spec 会缺少文件清单、路径、事务边界等关键细节，导致编码时大量返工。
>
> **精简原则**：如果是修改现有代码（而非新增），只需读目标方法及其直接调用方/被调用方，不需要全面提取模式。

## ⚠️ 熔断协议

Bug 修复或测试排查**连续 ≥3 次**未解决时，强制执行 `circuit-breaker.md`。熔断的触发条件、执行动作和报告格式以 `circuit-breaker.md` 为唯一权威，此处不重复。
