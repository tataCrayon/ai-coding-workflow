# 统一任务执行框架

> 本文件职责：定义代码任务的**执行规范**，包括任务命名、简单任务快速闭环、复杂任务防御式执行。
> 熔断协议由 `circuit-breaker.md` 统一定义，本文件不重复熔断流程。

## 📝 任务命名规范（全局约束）

所有 AI 生成的"任务描述"类产物，**名称必须具体到可执行**，遵循公式：

**`[动作] + [目标对象] + [具体内容]`**

| ❌ 模糊命名 | ✅ 具体命名 |
|------------|-----------|
| 修改相关代码 | 在 `UserService.validateEmail()` 中添加格式校验 |
| 处理逻辑 | 为 `CreateOrderRequest` 的 `amount` 字段增加非空校验 |
| 写测试 | 为 `PriceCalculator.calculate()` 编写边界值单元测试 |
| 做 Review | 对 `OrderBatchService` 的本次变更执行 Code Review |
| 20260401_修改代码.md（存档文件名） | 20260401_OrderBatchService增加金额精度校验.md |

**底线**：读名称就能知道"改哪个文件/类的什么东西"，不需要展开详情。

---

## 🎯 任务执行规范

模型根据任务复杂度自主判断执行方式，无需显式分类。

---

### 简单任务（单文件修改、纯逻辑修复、判空防护、文案修改等）

1. **意图声明**：用 1-2 句话说明要改什么以及为什么
2. **直接实施**：直接执行代码修改，或在需要并行/上下文隔离时委派 Named Agent（Coder）执行
3. **闭环**：向用户报告完成结果

**⚠️ 升级信号**：执行过程中若发现实际影响面扩大（≥2 个文件联动、接口签名变更、扩展点变更、数据库 Schema 变更），必须切换到复杂任务流程。

---

### 复杂任务（跨文件联动、核心业务流程、架构设计、大规模重构等）

1. **任务持久化**：在 `.agent/context/` 下创建任务文件夹（中大型）或单文件（简单任务），格式参见 `task-persistence.md`

2. **分析评估**：分两阶段收集信息，确保设计有充分的事实基础。

   **2a. 业务分析**：查阅知识资产，调用 `java-change-impact-analyzer` 或 `code-business-analyzer` Skill 做业务分析或变更影响评估。需要并行分析多模块时，可委派 Named Agent（Analyzer）。

   **2b. 实现模式提取**（编码类任务必做）：读取目标模块中**已有的同类代码**，提取以下信息供 Spec 使用：
   - **分层与目录结构**：各层的实际包路径/目录
   - **代码风格范本**：实体类用什么注解、字段用基本类型还是包装类型、数据访问层的写法约定
   - **基础设施约定**：ORM 映射文件的目录和命名规范、枚举风格
   - **集成点接口签名**：需要调用的现有 Service/数据访问层的实际方法签名和参数类型

   > **为什么在设计阶段就做？** 这些信息决定了技术方案的可行性和具体性。如果等到编码阶段才看，Spec 会缺少文件清单、路径、事务边界等关键细节，导致编码时大量返工。
   >
   > **精简原则**：如果是修改现有代码（而非新增），只需读目标方法及其直接调用方/被调用方，不需要全面提取模式。

3. **Spec（需求规格）**：基于分析结论和实现模式，产出结构化 Spec 给用户确认。**No Spec, No Code** — 未经确认的 Spec 不得开始实施。Spec 模板：

   ```
   ## 任务目标
   [1-2 句话描述要实现什么、为什么]

   ## 验收标准
   - [ ] [可测量的完成条件 1]
   - [ ] [可测量的完成条件 2]

   ## 显式约束（What NOT to build）
   - 不要 [防止 AI 发散的边界 1]

   ## 集成点（与现有代码的交互）
   - 使用现有的 `XxxService`（位于 xxx 包）
   - [其他需要交互的现有类/接口/配置]

   ## 技术方案
   | # | 子任务 | 变更说明 | 验收条件 |
   |---|--------|---------|---------|
   | 1 | ... | ... | ... |

   ## 实现蓝图（编码类任务必填）

   > 本章节是设计的核心产出物，目标是让编码阶段（含跨会话新 AI 接手）拿到就能直接写代码。

   ### 需新增/修改的文件清单
   | # | 文件（完整路径） | 新增/修改 | 说明 | 范本文件 |
   |---|----------------|---------|------|---------|
   | 1 | `com.xxx.XxxClass` | 新增 | ... | 参照 `YyyClass` 的风格 |

   > - 路径必须写到包/目录级别，新增文件必须标注放置的模块
   > - 每个新增文件必须标注「范本文件」——在步骤 2b 中识别的同类现有代码

   ### 代码链路（入口 → 出口的 Class.method 调用图）
   用缩进表示调用层级，标注外部依赖和 DB 操作。

   ### 核心流程伪代码（如涉及新增业务流程）
   用伪代码描述核心逻辑，标注：分支条件、异常处理、集成点（注明类名）、幂等/防重/并发控制。

   ### 事务与并发设计（如涉及数据写入）
   | 操作 | 事务策略 | 理由 |
   |------|---------|------|

   ### 数据模型变更（如涉及新增/修改表结构）
   DDL 或字段变更说明，附约束和索引设计理由。

   > **精简原则**：小型修改（≤3 文件）只写文件清单；中型功能加代码链路；大型功能/新增流程全部填写。

   ## 测试用例清单（Test Cases，编码类任务必填）

   > **设计哲学：测试用例先行（早），测试类后置（晚）。**
   > 在设计阶段先产出**稳定的测试用例清单**（行为契约），把易变的测试类推迟到代码定稿后再落地。
   > 原因：实现代码到上线前都可能调整，测试类与实现强耦合会反复返工；而测试用例描述的是「输入什么→期望什么」的行为契约，代码怎么改它都稳定。

   | ID | Given（前置/输入） | When（触发动作） | Then（期望结果） | 覆盖点 |
   |----|------------------|----------------|----------------|--------|
   | TC-01 | [初始状态/入参] | [调用的行为，用业务语言] | [期望的输出/状态变化] | 正常主流程 |
   | TC-02 | ... | ... | ... | 边界值 |
   | TC-03 | ... | ... | ... | 异常/失败 |

   > **铁律**：
   > - 用例只描述**行为契约**（业务语言的输入→期望），**禁止出现具体类名/方法名/字段名**——否则代码一改用例就失效
   > - 必须覆盖：正常主流程 + 边界值 + 异常/失败路径，且与「边缘场景与失败模式」表逐条对应
   > - 每条「验收标准」至少被一条用例覆盖

   ## 假设清单（Assumptions Audit）
   | # | 假设 | 验证方式 | 状态 |
   |---|------|---------|------|
   | 1 | [对现有代码/接口/数据模型行为的假设] | read_file / grep / 运行测试 | ✅已验证 / ❓待验证 |

   > 每个集成点至少对应一条假设。状态必须在交叉验证步骤中更新。

   ## 边缘场景与失败模式（Edge Cases & Failure Modes）
   | # | 场景 | 触发条件 | 预期行为 | 缓解措施 |
   |---|------|---------|---------|---------|
   | 1 | [并发竞争/空值/超时/数据越界/依赖不可用/幂等重入...] | ... | ... | ... |

   > 至少覆盖：空值/异常输入、并发/重入、依赖超时或不可用、数据边界值。

   ## 非功能需求（如适用）
   - [幂等性/日志/安全/兼容性/回滚等]

   ## 风险
   - [潜在风险及缓解措施]
   ```

   **Spec 精简原则**：Spec 的范围应与任务范围匹配：
   - **小型跨文件修改**：只需「任务目标 + 技术方案 + 显式约束」
   - **中型功能实现**：追加「假设清单 + 边缘场景」
   - **大型功能/核心链路/涉及新集成点**：完整 Spec + 全部验证步骤
   - 写 Spec 的时间不应超过实施时间

4. **Spec 实体验证**：Spec 生成后，调用 `spec-verifier` Skill 自动验证 Spec 中引用的类/方法/配置是否真实存在、签名是否一致、模式是否合规。
   - **P0 阻断项**（存在性/签名不匹配）：AI 先自动修正 Spec 并重新验证，修正后再呈现给用户
   - **仅有告警**：连同验证报告一起呈现给用户判断
   - **跳过条件**：小型跨文件修改（≤3 个子任务且不涉及新集成点）可跳过 P1 维度验证

5. **设计交叉验证**（Design Cross-Validation）：在 Spec 实体验证通过后、呈现给用户前，执行逻辑层面的可行性验证。目标是**在写代码之前发现设计缺陷**。

   **5a. 代码链路验证**：对技术方案中每个涉及现有代码交互的子任务，追踪至少一层调用链（入口方法 → 直接依赖），验证声明的调用路径真实连通、类型兼容、隐式链路（拦截器/AOP/消息监听）不影响预期、事务边界覆盖原子操作。将验证结果回填到假设清单。

   **5b. Spec 内部一致性检查**：检查各章节是否矛盾——每条验收标准都有子任务和测试用例覆盖；每个边缘场景都有测试用例覆盖；测试用例未出现具体类名/方法名；显式约束不与技术方案冲突；待验证假设超过总数 50% 时标记"验证不充分"告警。

   **5c. 反向推演（Pre-mortem）**：假设方案已上线且出了问题，逆向推演最可能的 Top 3 故障点；每个故障点检查 Spec 中是否有防护措施，没有则补充到边缘场景表。

   **交叉验证输出**：在 Spec 末尾追加「交叉验证报告」：
   ```
   ## 交叉验证报告
   - **链路验证**：✅ N 条链路已验证 / ⚠️ M 条存在风险（列出）
   - **一致性检查**：✅ 无矛盾 / ⚠️ 发现 K 处不一致（列出）
   - **反向推演 Top 3 风险**：1. [风险]→[已有防护/需补充] 2. ... 3. ...
   - **综合结论**：🟢 可实施 / 🟡 需补充后实施 / 🔴 需重新设计
   ```

   **跳过条件**：小型跨文件修改可跳过；中型任务可只做 5a。

6. **多视角设计审视**（Multi-Perspective Design Review）：从三个角色视角审视 Spec，发现盲区。

   | 视角 | 关注点 | 审视问题 |
   |------|--------|---------|
   | **开发者** | 可实现性、复杂度、可维护性 | 方案能否合理时间内实现？是否引入不必要复杂度？ |
   | **测试者** | 可测试性、可观测性、边界覆盖 | 如何验证每个子任务正确？日志/指标是否足够排查？ |
   | **使用者/运维** | 易用性、错误提示、运维负担 | 配置是否直观？出错能否快速定位？ |

   发现的问题直接修正到 Spec 对应章节。审视输出追加到交叉验证报告。

   **跳过条件**：小型和中型修改可跳过；仅大型功能/核心链路/面向用户的功能强制执行。

7. **Checkpoint**：等用户确认 Spec（含验证报告和交叉验证报告）后再继续。
   - **可逆修改**（加逻辑、重构、新增文件等）：用户确认后直接实施，不打断心流
   - **不可逆修改**（删文件、改数据库 Schema、改对外接口签名）：Spec 中必须标注风险，用户**显式确认**后再实施

8. **实施代码编辑**：按 Spec 中的技术方案逐个子任务执行。需要并行或上下文隔离时，可委派 Named Agent（Coder）

9. **质量防线**：≥3 文件变更或接口变更时，调用 `code-review-checklist` Skill 审查。需要干净上下文审查时，可委派 Named Agent（Reviewer）。修改文件 ≥5 个时，改为生成子任务简报避免上下文爆炸

10. **编码期测试守护（不写新测试类）**：编码过程中**只运行已有测试**确保不回归，**不为本次新代码编写测试类**。
    - **原因**：实现代码到验收前都可能调整，过早写测试类会随实现反复返工。测试意图已在 Spec 的「测试用例清单」中以稳定的行为契约形式固化。
    - 编码中如发现「测试用例清单」有遗漏或需调整，**更新清单本身**（行为契约层），而非去写测试类。

11. **测试类落地（代码定稿后）**：在代码经 CR 确认、接近定稿时，调用 `unit-test-master` Skill，**依据 Spec 的「测试用例清单」逐条（`TC-NN`）将稳定用例兑现为可执行测试类**。
    - 测试方法用注释或命名标注其对应的用例 ID，实现用例与测试的双向追溯
    - 逐条核对：每条 `TC-NN` 都有对应测试方法，无遗漏；测试全绿后方可进入验收
    - **跳过条件**：纯文案/注释/配置类无逻辑变更可跳过；其余编码类任务不得跳过

12. **验收与存档**：对照 Spec 验收标准逐项确认完成，确认「测试用例清单」已全部兑现为通过的测试，输出变更报告，更新进度存档状态为"已完成"。如实施中 Spec 有变化，**Reverse Sync** — 将实际变更回写到 Spec 中保持一致

## ⚠️ 熔断协议

Bug 修复或测试排查**连续 ≥3 次**未解决时，强制执行 `circuit-breaker.md`。熔断的触发条件、执行动作和报告格式以 `circuit-breaker.md` 为唯一权威，此处不重复。

## 📦 长任务与大上下文管理

### 长任务先建任务再执行

以下场景**必须先创建任务文件夹再执行**：

| 场景 | 判定标准 | 原因 |
|------|---------|------|
| **跨多模块分析/修改** | 涉及 ≥3 个模块或 ≥5 个文件 | 上下文容易超出单次对话容量 |
| **全链路梳理** | 需要追踪入口 → 出口全链路 | 中间结果多，需持久化防丢失 |
| **Skill/规则优化** | 涉及多个 Skill 或 Rule 文件的联动修改 | 需分阶段执行，避免一次改太多出错 |
| **大规模重构** | 涉及接口签名变更、数据结构变更等 | 影响面大，需持久化 Spec 和影响清单 |

**执行方式**：调用 `task-spawner`，将目标、已知上下文、任务项持久化为 `.agent/context/` 下的任务文件夹，然后在新对话中执行。

### 上下文自主压缩

当 AI 在执行任务过程中**感知到上下文负荷过大**时，应**自主执行上下文压缩**，无需等待用户指令。

**触发条件**（满足任一）：对话轮次 ≥6 轮且仍有未完成任务项 / 单轮工具调用产生 ≥3 个大文件（>200 行）的完整内容 / 累计读取了 ≥10 个文件。

**压缩动作**：① 提炼关键结论（文件路径 + 一句话结论，丢弃原始代码细节）② 更新任务文件 ③ 标记已完成项 ④ 声明压缩。

**压缩原则**：
- **保留**：关键事实、文件路径、类名方法名、决策结论、排除理由
- **丢弃**：已读取文件的完整代码内容（需要时可再次读取）、中间搜索结果的完整列表
- **绝不丢弃**：用户明确提供的约束和边界、尚未完成的任务项

### 对话轮次存档提醒

当单次对话轮次 **≥8 轮**时，AI 应主动建议存档进度后开启新对话继续。用户确认后按 `task-persistence.md` 格式在 `.agent/context/` 下创建任务文件夹（或单文件）。
