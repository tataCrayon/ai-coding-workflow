# Skill 协作与编排规则

> 本规则定义 Skill 间的协作协议、复合场景编排和 Agent 间数据流转格式。
> 协作是**扩展能力**，不改变任何 Skill 的独立运行行为。

## 1. 协作声明规范

每个 Skill 的协作章节（追加在 SKILL.md 末尾）应包含以下三部分：

- **上游输入**：声明"我可以接收哪些 Skill 的输出作为输入"，格式：`**Skill 名**: 输出内容描述 → 本 Skill 如何使用`
- **下游输出**：声明"我的输出可以流向哪些 Skill"，格式：`**Skill 名**: 本 Skill 输出什么 → 对方如何使用`
- **触发条件**：声明"什么场景下建议串联"（可选，复杂场景才需要）

**原则**：
- 声明是建议性的，路由层决定是否实际串联
- 协作章节不影响 Skill 独立运行时的行为

## 2. 复合场景编排协议

以下 5 个编排协议覆盖最常见的多 Skill 串联场景。AI 在识别到复合意图时，按协议编排执行。

### 协议 1：实现需求并写测试

**触发意图**："实现 XX 功能并写测试"、"改完代码帮我补测试"

**编排流程**：
1. `code-business-analyzer` — 分析需求涉及的业务规则和代码结构
2. 主对话基于步骤 1 的分析结论生成 Spec（技术方案）→ `spec-verifier` 验证事实性
   - 验证通过：继续步骤 3
   - 验证不通过：修正 Spec 中的错误引用后重新验证（最多 2 轮，仍不通过则暂停请用户确认）
3. Coder Agent 按 Spec 执行实现
4. `unit-test-master` — 为新增/修改的方法编写单元测试

**数据流转**：步骤 1 的业务规则分析 → 步骤 2 的 Spec 内容；步骤 3 的变更方法签名 + 分支逻辑 → 步骤 4 的测试目标和边界条件

### 协议 2：CR 并修复问题

**触发意图**："帮我处理 CR 意见"、"CR 完修复一下"

**编排流程**：
1. 获取 Review 意见：
   - 有 CR 链接 → `cr-review-pipeline`（自动拉取 CR 评审意见并解析）
   - 无 CR 链接，用户要求自主 CR → `code-review-checklist`（多维 + 生产就绪检查）
2. 输出问题清单（按严重度排序：🔴 必修 → 🟡 建议 → 🟢 优化）
3. Coder Agent 逐项修复（仅修复 🔴 必修项，🟡 建议项由 Coder 判断是否采纳）
4. （可选）Reviewer Agent 二次验证修复质量——仅当步骤 3 修复了 ≥3 个 🔴 项时建议触发

**回路约束**：步骤 3→4 最多循环 2 轮，超过则输出剩余问题清单让用户决策

### 协议 3：分析影响范围并生成任务

**触发意图**："分析一下这个改动的影响范围，生成修改任务"

**编排流程**：
1. `java-change-impact-analyzer` — 输出多层影响清单
2. `task-spawner`（TASK 模式）— 将影响清单转化为可执行的任务文件

**数据流转**：步骤 1 的影响文件清单 + 修改建议 → 步骤 2 的任务项内容

### 协议 4：定位代码并分析业务规则

**触发意图**："找到 XX 相关的代码，分析一下业务逻辑"

**编排流程**：
1. `code-concept-tracer` — 输出命中矩阵（文件 + 行号 + 相关度）
2. `code-business-analyzer` — 对命中文件进行深度业务分析

**数据流转**：步骤 1 的命中矩阵（Top 文件列表）→ 步骤 2 的分析入口

### 协议 5：实现需求并 CR

**触发意图**："改完代码帮我 Review 一下"、"实现后自动 CR"

**编排流程**：
1. Coder Agent 执行实现
2. `code-review-checklist`（Reviewer Agent）— 多维审查
3. 修复回路：Reviewer 发现问题 → Coder 修复 →（可选）Reviewer 二次验证

**回路约束**：步骤 2→3 最多循环 2 轮

### 协议 6：高风险改动对抗式验证

**触发意图**："高风险变更需要对抗验证"、"改核心逻辑要多重审视"、"这个改动影响大，要严格检查"

**适用场景**：修改核心接口签名、修改公共组件底层逻辑、修改数据处理链路、跨模块联动变更等高风险操作。

**编排流程**：
1. Coder Agent 执行实现
2. 3 个独立的 Reviewer Agent 分别从不同角度对抗验证（每个 Agent 专注于一个维度：正确性/安全性/可维护性），prompt 中明确要求"你的目标是**反驳**这个变更，找出所有可能的问题。如果找不到反驳理由，才确认通过"
3. 收集 3 个验证结论：
   - ≥2 个 Agent refute（反驳）→ **驳回变更**，输出所有反驳理由，Coder 须重新实现或提请用户决策
   - ≤1 个 Agent refute → **变更通过**，但反驳理由必须作为风险提示输出
4. 如被驳回，Coder 修正后最多再执行 1 轮对抗验证

**回路约束**：步骤 1→4 最多循环 2 轮，超过则输出剩余风险清单让用户决策

**数据流转**：Coder 的变更文件清单 + 变更意图 → 3 个 Reviewer Agent 的反驳结论（含严重度、具体代码位置、反驳理由）→ 风险综合评估

## 3. Agent 间数据流转格式

子代理之间的任务交接使用以下结构化格式，确保信息无损传递。各 Skill 在自己的 SKILL.md 中定义了具体的委派角色和职责，此处的数据流转格式是通用模板。

### 3.1 Analyzer → Coder

```
## 变更交接

### 影响文件清单
- `path/to/File` — 修改原因简述

### 变更方案
- 文件: 具体修改内容描述

### 约束条件
- 不可变更的接口/行为
- 必须保持的兼容性
```

### 3.2 Coder → Reviewer

```
## 审查交接

### 变更文件清单
| 文件 | 改动类型 | 改动意图 |
|------|---------|---------|
| `path/to/File` | 新增/修改/删除 | 一句话描述为什么改 |

### 业务背景
- 需求简述（1-2 句）
- 关键业务规则

### 重点关注
- 需要特别审查的逻辑点
```

### 3.3 Coder → Tester

```
## 测试交接

### 新增/修改的方法
- `ClassName#methodName(ParamType)` — 方法职责简述

### 分支逻辑
- 条件 A → 行为 X
- 条件 B → 行为 Y

### 边界条件
- null 输入、空集合、数值边界等需覆盖的边界
```

### 3.4 Reviewer → Coder（修复回路）

```
## 修复任务

### 发现清单
| # | 严重度 | 文件:行号 | 问题描述 | 修复建议 |
|---|--------|-----------|---------|---------|
| 1 | 🔴 必修 | `File:42` | 描述 | 建议 |
| 2 | 🟡 建议 | `File:78` | 描述 | 建议 |

### 修复约束
- 🔴 必修项必须全部修复
- 🟡 建议项由 Coder 判断是否采纳
- 最多 2 轮修复回路
```

## 4. 并行 vs 串行决策矩阵

| 条件 | 决策 | 原因 |
|------|------|------|
| 两个任务都是只读（分析/审查） | ✅ 可并行 | 无写冲突 |
| 任一任务涉及写操作 | ❌ 必须串行 | 避免文件冲突 |
| 后一任务依赖前一任务的输出 | ❌ 必须串行 | 数据依赖 |
| 两个任务操作不同文件集合 | ✅ 可并行 | 无交叉 |

### 子代理并行模式

> 各 Skill 在 SKILL.md 中定义具体的委派角色（如 Analyzer/Coder/Tester/Reviewer），此处仅列出常见组合模式。

| 组合 | 模式 | 说明 |
|------|------|------|
| 只读分析 ‖ 只读审查 | 并行 | 两者均只读，可同时执行 |
| 只读分析 ‖ 只读分析 | 并行 | 分析不同模块时可并行 |
| 可写编码 → 测试 | 串行 | 先改代码，后写测试 |
| 可写编码 → 只读审查 | 串行 | 先写代码，后审查 |
| 只读审查 → 可写修复 | 串行 | 先审查，后修复 |

### 并行安全约束

- **并行上限**：单次最多 3 个并行 Agent
- **冲突裁决**：并行结果出现冲突时，以安全性优先裁决（参照 AGENTS.md 冲突裁决规则）
- **结果合并**：并行 Agent 完成后，主对话负责合并结论并决定下一步
