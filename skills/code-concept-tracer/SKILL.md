# Code Concept Tracer (业务概念追踪器)

> **核心定位**：从业务语言出发 → 定位代码全景 → 防止修改遗漏。
> 是复杂任务流程的"前置侦察兵"，快速给出一张"地图"，不做深度分析。

## 🎯 两大核心能力

### 能力一：术语追踪
**用户意图**："权限怎么做的"、"缓存逻辑在哪"、"消息推送涉及哪些地方"

### 能力二：需求影响评估
**用户意图**："这个需求会影响哪些代码"、"改这个功能要动哪些地方"

---

## 执行流程

### Step 1：输入理解与关键词提取

从用户输入中提取关键信息：

| 维度 | 提取内容 | 示例 |
|------|---------|------|
| **业务概念** | 用户提到的核心术语 | "权限"、"缓存"、"消息推送" |
| **业务域** | 所属业务领域 | "用户管理"、"订单"、"支付" |
| **模块范围** | 涉及的系统模块 | "核心模块/插件模块/配置层/ALL" |
| **环境范围** | 涉及的环境或变体 | "生产/测试/ALL" |
| **变更类型** | 新增/修改/删除（仅需求影响评估时） | "新增" |

**关键词扩展**：将业务术语扩展为代码中可能出现的多种形式：
- 中文 → 英文（权限 → permission/auth）
- 全称 → 缩写（configuration → config）
- 查阅项目术语表（如 `.notes/foundation/glossary.md`）匹配标准名称和别名

### Step 2：全量扫描

使用 `file_grep` 对扩展后的关键词进行全量扫描，按以下维度分组：

```
file_grep(query="Permission|Auth|权限", include_pattern="*.java")
file_grep(query="Permission|Auth|权限", include_pattern="*.ts")
file_grep(query="Permission|Auth|权限", include_pattern="*.json")
file_grep(query="Permission|Auth|权限", include_pattern="*.xml")
file_grep(query="Permission|Auth|权限", include_pattern="*.yaml")
```

**分组规则**：将命中结果按 `模块 × 业务环节` 分组：
- 模块：从文件路径提取（如 `modules/user-service` → 用户服务模块）
- 业务环节：从包名/目录名推断（如 `controller/auth` → 认证入口）

### Step 3：调用链追踪

对每个命中点，追踪其调用关系：
- 使用语言特定的调用链分析工具追踪"谁调用了它"（上游）
- 使用 `file_grep` 搜索该类/方法的引用位置（下游）
- 标注该命中点在业务流程中的位置（入口层 → 服务层 → 数据层）

### Step 4：输出追踪报告

## 输出格式

### 术语追踪报告

```markdown
## 概念追踪报告：{业务概念}

### 命中矩阵

| 模块 | 业务环节 | 文件 | 类/函数名 | 一句话业务含义 |
|------|---------|------|----------|--------------|
| 用户服务 | 认证-权限控制 | PermissionConfig.java | getPermissions() | 权限配置加载 |
| 用户服务 | 认证-准入 | AuthExtPoints.java | admitRules() | 准入规则链中引用权限判断 |
| 核心层 | 认证-通用 | PermissionService.java | hasPermission() | 权限判断通用服务 |

### 调用关系

{概念} 的代码调用关系：
- `PermissionService.hasPermission()` ← 被以下位置调用：
  - `UserController.updateProfile()` 📍 用户信息修改入口
  - `AdminController.manageUsers()` 📍 管理后台入口
- `PermissionConfig.getPermissions()` ← 被以下位置调用：
  - `PermissionService.hasPermission()` 📍 权限判断入口

### 修改建议
如果要修改"{概念}"相关逻辑，需要联动检查以下位置：
1. ⚠️ `PermissionService` — 核心层通用服务，修改会影响所有模块
2. ⚠️ `PermissionConfig` — 特定模块专属配置
3. 💡 建议检查其他模块是否有类似的权限配置类

### 分析盲区
- ⚠️ 未扫描到其他模块的权限配置，可能不存在或使用了不同的命名
```

### 需求影响分析报告

```markdown
## 需求影响分析报告

### 需求概述
{一句话描述需求}

### 关键信息
| 维度 | 值 |
|------|-----|
| 业务域 | {所属业务领域} |
| 模块范围 | {涉及的模块} |
| 环境范围 | {涉及的环境} |
| 变更类型 | {新增/修改/删除} |

### 直接影响（必须修改）

| 序号 | 文件路径 | 修改内容 | 修改原因 |
|------|---------|---------|---------|

### 关联影响（需要检查）

| 序号 | 文件路径 | 影响原因 | 风险等级 |
|------|---------|---------|---------|

### 影响的业务流程

| 流程名 | 影响环节 | 影响方式 |
|--------|---------|---------|

### 风险评估

| 风险 | 等级 | 说明 | 缓解措施 |
|------|------|------|---------|

### 实现建议
1. **修改步骤**（按顺序）
2. **测试建议**
3. **发布注意事项**
```

## ⚠️ 常量与枚举值解读规范（强制）

分析过程中遇到常量值、枚举值、魔法字符串，**严禁根据英文名称自行翻译推测业务含义**，必须先获取代码中的注释后再输出。

**强制执行步骤**：
1. **先定位定义**：通过 `read_file` 或 `file_grep` 找到常量/枚举的定义位置
2. **读取注释**：读取该定义上方的文档注释、行内注释或类级注释
3. **有注释 → 引用注释**：业务含义直接引用注释原文，标注 📍 代码位置
4. **无注释 → 标注推测**：用 ⚠️ 标注"无注释，以下为推测"

## 依赖库类读取技巧

当分析过程中遇到定义在依赖库（非本项目源码）中的类时，如果需要查看依赖库的类定义，使用 `read_file` 工具通过全路径类名读取。不同语言/框架的读取方式可能不同，请根据项目实际情况灵活选择。

## 与其他 Skill 的协作

```
用户问："权限怎么做的，要怎么改？"
  ↓
code-concept-tracer（本 Skill）
  → 快速扫描，输出命中矩阵："权限相关代码在这 N 个地方"
  ↓
用户："帮我深入分析第3个的业务规则"
  ↓
code-business-analyzer
  → 深入分析具体规则（全链路/规则卡片/场景对比）
  ↓
用户确认要改代码
  ↓
change-impact-analyzer
  → 代码级变更影响分析（DTO/VO/数据库映射/调用链联动）
```

> **与 `change-impact-analyzer` 的边界**：
> - 本 Skill：从**业务语言**出发，定位"哪些地方和这个概念有关"
> - `change-impact-analyzer`：从**具体代码变更点**出发，分析"改这个方法会影响哪些调用方"

## Sub Agent 委派策略

> **核心原则**：Step 1（输入理解）和 Step 4（输出报告）在主对话执行，Step 2（全量扫描）和 Step 3（调用链追踪）优先委派给 Sub Agent。

### 委派触发条件

当以下任一条件满足时，**应主动委派**而非在主对话中执行：
- 扫描范围跨越 ≥2 个模块（如核心层 + 插件层）
- 关键词扩展后有 ≥3 组搜索模式
- 用户要求"找出所有 XX 相关的代码"

### 委派编排模式

```
主对话：Step 1 输入理解 + 关键词扩展
    ↓
并发委派（最多 3 个 Sub Agent）：
├── Sub Agent 1: 扫描核心模块代码
├── Sub Agent 2: 扫描插件/扩展模块代码
├── Sub Agent 3: 扫描配置层（*.json / *.xml / *.yaml）
    ↓
主对话：Step 4 整合命中矩阵 + 输出报告
```

### 委派 Prompt 模板

每个 Sub Agent 的 prompt 必须包含：
1. **任务类型**：只读调研任务
2. **关键词列表**：从 Step 1 扩展出的完整关键词（中英文、全称缩写）
3. **扫描范围**：明确的模块/目录路径
4. **分组规则**：按 `模块 × 业务环节` 分组
5. **返回格式**：命中文件路径、类/函数名、所在行号、一句话业务含义
6. **禁止行为**：不要修改任何文件，不要做深度业务分析（那是 `code-business-analyzer` 的职责）
