# Database Design Guard（数据库设计守卫）

> **核心定位**：四能力数据库治理——评审、盘点、规范、遗产屏蔽。
> 不仅检查"表结构是否合理"，更要评估**"数据模型是否契合业务语义"**。
> 金融领域有严格的金额精度、审计追溯和命名规范要求，任何偏差都可能造成资金风险。

---

## 一、四大能力概览

| 能力 | 代号 | 目标 | 触发词 |
|------|------|------|--------|
| DB 评审 | R | 对已有/新建表结构做合规审查 | "数据库评审"、"DB评审"、"表结构评审" |
| 数字资产盘点 | I | 扫描全库表、梳理业务归属和数据流向 | "数字资产盘点"、"盘点表"、"DB盘点" |
| 数据库规范 | S | 输出/校验项目级 DB 规范文档 | "数据库规范"、"DB规范"、"命名规范" |
| 遗产屏蔽 | L | 对遗留脏表/冗余字段标记冻结策略 | "遗产屏蔽"、"脏表处理"、"遗留字段治理" |

## 三、各能力详解

### 3.1 DB 评审（R）

对已有或新建的表结构进行合规审查，输出评审报告：

1. **收集待评审表结构**：读取 Entity 类、DDL 脚本或建表语句
2. **逐表检查以下维度**：

| 检查维度 | 检查项 | 金融领域特别关注 |
|---------|--------|----------------|
| 字段类型 | 金额字段是否 DECIMAL/BigDecimal | 严禁 float/double 存金额 |
| 命名规范 | 是否 snake_case、是否业务语义明确 | 见下方金融领域规则 |
| 主键策略 | 是否有主键、是否合理（自增/UUID/业务键） | 分布式场景优先 UUID |
| 审计字段 | 是否有 created_at/updated_at/created_by/updated_by | 金融审计追溯强制要求 |
| 索引设计 | 是否有合理索引、是否有冗余索引 | 高频查询场景需覆盖索引 |
| 字段冗余 | 是否有无用字段、是否有过宽字段 | 遗产字段应标记冻结 |
| 范式与反范式 | 是否符合业务需要的范式层级 | 读多写少场景允许适度反范式 |

3. **输出评审结论**：每表给出 ✅ 合规 / ❌ 违规 / ⚠️ 建议调整，附整改方案

### 3.2 数字资产盘点（I）

扫描项目中的所有数据库表，梳理业务归属：

1. **全量扫描**：搜索项目代码中的 Entity 类、DDL 文件、MyBatis mapper 等
2. **业务归属标注**：将每张表映射到业务域（如：订单域、支付域、用户域）
3. **数据流向梳理**：标记表之间的外键关系、关联查询、数据流转链路
4. **输出资产清单**：表名 | 业务域 | 核心字段 | 上游来源 | 下游消费 | 健康度评估

### 3.3 数据库规范（S）

输出或校验项目级数据库规范：

1. **检查项目已有规范**：搜索 `.notes/`、`docs/` 中是否有 DB 规范文档
2. **若无规范，生成模板**：基于金融领域最佳实践生成规范文档模板
3. **若有规范，校验一致性**：将现有表结构对照规范逐项校验
4. **输出规范文档**或**校验报告**

### 3.4 遗产屏蔽（L）

对遗留脏表、冗余字段制定冻结策略，防止继续扩散：

1. **识别遗产项**：无业务归属的表、无代码引用的字段、命名不合规的历史字段
2. **分级策略**：

| 遗产级别 | 策略 | 说明 |
|---------|------|------|
| 🟢 低风险 | 标注废弃 + 限制新代码引用 | 字段仍在使用但命名不合规 |
| 🟡 中风险 | 冻结写入 + 数据迁移计划 | 表/字段有部分引用但可替代 |
| 🔴 高风险 | 禁止访问 + 限期清理 | 完全无引用的脏表/脏字段 |

3. **输出冻结清单**：遗产项 | 级别 | 策略 | 替代方案 | 执行时间线

## 四、金融领域核心规则

> 以下规则在金融/资金场景中为**铁律硬约束**，违反即评审不通过。

| 规则 | 说明 |
|------|------|
| **金额 DECIMAL** | 所有涉及金额、利率、费率、数量的字段，类型必须是 `DECIMAL(p,s)`（Java 中 `BigDecimal`）。严禁 `float`/`double`/`INTEGER` 存金额 |
| **审计字段强制** | 每张业务表必须有 `created_at`、`updated_at`、`created_by`、`updated_by` 四个审计字段，用于合规追溯 |
| **snake_case 命名** | 表名、字段名统一 snake_case（如 `order_amount`，禁止 `orderAmount` 或 `OrderAmt`） |
| **业务语义命名** | 表名必须体现业务域（如 `rwa_order`，禁止 `t_order` 或 `order_info`）；字段名必须体现业务含义（如 `settlement_status`，禁止 `status` 或 `flag`） |
| **状态字段枚举化** | 状态类字段在代码中必须对应枚举类型，禁止用魔法数字（如 `status=1/2/3`） |
| **软删除优先** | 金融数据禁止物理删除，必须使用 `is_deleted` 软删除标记 + 删除时间戳 |
| **金额精度统一** | 金额精度全局统一（如 `DECIMAL(18,2)`），不同表不得使用不同精度 |

> 详细金融 DB 规则参见 References 中的规范文档。

## 六、人工门禁

**执行完设计后必须暂停**，向用户输出以下确认提示：

```
🔒 数据库设计门禁：
- 已完成 [R/I/S/L] 能力执行
- 输出文档：04-database-design.md
- 金融合规检查结论：[通过/有待修正项]

请确认设计方案后，再进入代码编写阶段。(确认/调整/回退)
```

用户确认后才可继续；用户要求调整则回到 Step 2 重新执行。**主会话负责等待用户反馈**——Skill 工具单次调用无法暂停。

## 八、Collaboration（协作说明）

**上游输入**：
- **code-business-analyzer**: 业务规则分析结果 → 作为字段语义设计的依据
- **architecture-guard**: 模块归属判定 → 确定数据模型应归属哪个业务域

**下游输出**：
- **unit-test-master**: 表结构设计中的关键约束 → 作为测试断言的验证点
- **api-doc-generator**: 数据模型定义 → 作为 API 请求/响应体的字段来源
- **change-documenter**: 表结构变更 → 作为变更留痕中的数据库变更部分

**触发条件**：
- 需求涉及新增/修改数据库表时，建议先执行本 Skill 的 R 能力，再进入代码编写
- 定期执行 I+S 能力做资产盘点和规范校验
- 发现遗留脏表时触发 L 能力
