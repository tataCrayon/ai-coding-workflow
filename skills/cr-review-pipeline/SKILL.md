# CR Review Pipeline（CR 评审结果自动化评估与修复流水线）

> **核心问题**：CR 结果内容量大，逐条评估需要读取对应源码验证，修复方案需要理解业务上下文 —— 单次对话的上下文窗口根本装不下。
>
> **解决思路**：将整个流程拆分为 4 个阶段，每个阶段的产出持久化到文件，阶段之间通过文件传递上下文，而非依赖对话记忆。子代理 并发评估进一步提速。

---

## 流程总览

```
阶段 A: 获取与解析 ──→ CR_ITEMS 文件（结构化条目）
    ↓
阶段 B: 批量评估   ──→ CR_EVALUATION 文件（评估报告）
    ↓
阶段 C: 人工确认   ──→ 用户标记修复范围（断点）
    ↓
阶段 D: 执行修复   ──→ 代码变更 + 修复记录
```

**每个阶段都是独立的**，可以单独执行、中断后恢复、或跳过。用户可以说"只做到阶段 B"或"从阶段 C 继续"。

---

## 阶段 A：获取与解析

### 目标
从 CR 页面获取评审结果，解析为结构化的 CR 条目列表，持久化到文件。

### 执行步骤

1. **获取 CR 页面内容**
   - **工具选择策略**：不硬编码使用某个特定工具，而是根据 URL 特征**动态检索当前可用的工具**，选择最合适的：
     1. 先分析 URL 特征（内网/公网、平台类型等）
     2. 使用 `tool_search` 检索当前可用的相关工具（如搜索关键词 `fetch`、`url`、`content`、`external` 等）
     3. 从检索结果中选择最匹配的工具（优先选择能处理对应 URL 类型的工具）
     4. 如果没有找到合适的 MCP 工具，降级使用内置工具（`web_fetch`、`read_ali_doc`、终端 `curl` 等）
   - **降级链路**（按优先级尝试）：
     1. 🥇 匹配到的 MCP 工具（如内容获取类工具）
     2. 🥈 内置工具（`web_fetch` 用于公网、`read_ali_doc` 用于文档平台）
     3. 🥉 终端工具（`运行命令` 执行 `curl` 命令获取页面内容）
     4. ❌ 所有方式都失败 → 提示用户手动粘贴 CR 内容
   - 如果内容过长被截断，分段获取（通过行号范围控制）

2. **解析 CR 条目**
   - 从原始内容中提取每一条 CR 评审意见
   - 为每条分配唯一 ID（CR-001, CR-002, ...）
   - 识别每条涉及的文件路径和行号（如果 CR 工具提供了的话）
   - 对 CR 类型进行初步分类

3. **持久化到文件**
   - 输出路径：`.agent/context/{日期}_CR_ITEMS_{CR简述}.md`
   - 使用下方的 CR 条目格式

### CR 条目格式

每条 CR 条目按以下结构记录：

```markdown
## CR-001
- **文件**: `path/to/File.java`
- **行号**: 42-58（如果有）
- **类型**: [代码质量 | 安全风险 | 性能问题 | 逻辑错误 | 最佳实践 | 可读性 | 其他]
- **原始描述**: [CR 工具给出的原始评审意见，原文保留]
- **严重程度**: [高 | 中 | 低]（基于对系统的影响初步判断）
```

### 阶段 A 完成标志
- CR_ITEMS 文件已创建
- 向用户报告：共解析出 N 条 CR 意见，按类型分布统计
- 询问用户是否继续阶段 B

---

## 阶段 B：批量评估

### 目标
逐条评估每个 CR 意见是否成立，结合本地代码和知识资产判断，输出评估报告。

### 为什么用 子代理 并发
每条 CR 的评估都需要：读取对应源码文件 → 理解上下文 → 判断 CR 意见是否合理 → 给出修复方案。这些操作彼此独立，天然适合并发。而且每个 子代理 的上下文是独立的，不会互相污染。

### 执行步骤

1. **读取 CR_ITEMS 文件**，获取所有 CR 条目

2. **分批派发 子代理**
   - 每批 3-5 条 CR（根据复杂度调整）
   - 每次最多并发 3 个 子代理（平台限制）
   - 每个 子代理 的 prompt 包含：
     - 明确的任务类型（只读调研 + 评估判断）
     - 分配给它的 CR 条目（完整内容）
     - 评估输出格式要求
     - 项目的知识资产路径提示（让 子代理 按需加载）

3. **子代理 评估逻辑**（每个 子代理 独立执行）
   - 读取 CR 涉及的源码文件和相关上下文
   - 如果涉及业务逻辑，查阅 `.notes/` 知识资产
   - 对每条 CR 给出评估结论：
     - ✅ **成立** — CR 意见正确，需要修复
     - ❌ **不成立** — CR 意见不适用于当前场景（说明原因）
     - ⚠️ **部分成立** — CR 方向对但建议不完全准确（说明哪部分对、哪部分不对）
   - 对成立的 CR 给出具体修复方案

4. **汇总评估结果**
   - 收集所有 子代理 的返回结果
   - 合并为完整的评估报告
   - 持久化到文件：`.agent/context/{日期}_CR评审问题评估报告.md`

### 评估报告格式

```markdown
# CR 评估报告
- CR 来源：[URL]
- 评估时间：YYYY-MM-DD
- 总条数：N | 成立：X | 不成立：Y | 部分成立：Z

## CR-001 ✅ 成立
- **文件**: `path/to/File.java`
- **原始描述**: [原文]
- **评估理由**: [为什么成立，结合代码说明]
- **修复方案**: [具体怎么改，包含代码片段]
- **修复复杂度**: [简单 | 中等 | 复杂]
- **修复状态**: 待确认

## CR-002 ❌ 不成立
- **文件**: `path/to/File.java`
- **原始描述**: [原文]
- **评估理由**: [为什么不成立，结合代码和业务逻辑说明]
- **修复状态**: 跳过

## CR-003 ⚠️ 部分成立
- **文件**: `path/to/File.java`
- **原始描述**: [原文]
- **评估理由**: [哪部分对、哪部分不对]
- **修复方案**: [针对成立部分的修复方案]
- **修复复杂度**: [简单 | 中等 | 复杂]
- **修复状态**: 待确认
```

### 子代理 Prompt 模板

派发给每个 子代理 的 prompt 应包含以下结构：

```
【任务类型】只读调研 + 评估判断任务

【必须做】
1. 读取以下 CR 条目涉及的源码文件，理解代码上下文
2. 对每条 CR 给出评估结论（成立/不成立/部分成立）和理由
3. 对成立的 CR 给出具体的修复方案（包含代码片段）
4. 如果涉及业务逻辑判断，查阅 .notes/ 目录下的知识资产

【CR 条目】
{粘贴分配给该 子代理 的 CR 条目}

【输出格式】
按以下格式返回每条 CR 的评估结果：
- CR-ID + 结论（✅/❌/⚠️）
- 评估理由
- 修复方案（如成立）
- 修复复杂度（简单/中等/复杂）

【禁止行为】
- 不要修改任何代码文件
- 不要创建任何文件
- 仅做评估和方案输出
```

### 阶段 B 完成标志
- 评估报告文件已创建
- 向用户展示评估摘要（成立/不成立/部分成立的数量和分布）
- 询问用户是否进入阶段 C 确认修复范围

---

## 阶段 C：人工确认

### 目标
用户审阅评估报告，确认哪些 CR 需要修复、哪些跳过。这是流程中的**人工断点**，确保 AI 不会自作主张修改不该改的代码。

### 执行步骤

1. **展示评估摘要**
   - 列出所有"成立"和"部分成立"的 CR 条目（简要版）
   - 按修复复杂度分组展示
   - 给出建议的修复优先级

2. **产出确认请求（Skill 输出末尾）**
   - Skill 输出末尾附带确认请求，**主会话等待用户反馈**
   - 用户可以：
     - 全部确认修复
     - 选择性确认（如"只修 CR-001、CR-003、CR-005"）
     - 调整某条的修复方案
     - 跳过某条（标记为"跳过"）

3. **更新评估报告**
   - 将用户确认的结果更新到评估报告文件中
   - 将"修复状态"从"待确认"更新为"待修复"或"跳过"

### 阶段 C 完成标志
- 用户已确认修复范围
- 评估报告中的修复状态已更新

---

## 阶段 D：执行修复

### 目标
按照确认的修复清单，逐条执行代码修改。

### 执行策略选择

根据修复的数量和复杂度，选择不同的执行策略：

| 场景 | 策略 | 原因 |
|------|------|------|
| ≤3 条简单修复 | 主对话直接修改 | 上下文足够，无需额外开销 |
| 4-8 条混合修复 | 主对话逐条修改，每条改完标记 | 保持可控，逐步推进 |
| >8 条或含复杂修复 | 派发 子代理 分批修复 | 避免上下文爆炸 |
| 单条复杂修复（跨多文件） | 派发独立 子代理 | 隔离复杂度 |

### 执行步骤

1. **读取评估报告**，筛选"待修复"的条目
2. **按策略执行修复**
   - 每条修复前：读取目标文件的相关代码
   - 执行修改：使用 `file_replace` 等工具
   - 修复后：更新评估报告中该条的"修复状态"为"已修复"
3. **修复完成后的质量检查**
   - 对修改过的文件执行 `read_lints` 检查
   - 如果引入了新的 lint 错误，立即修复
4. **更新评估报告**
   - 所有修复完成后，更新报告的整体状态

### 子代理 修复 Prompt 模板

```
【任务类型】编辑任务

【必须做】
1. 按照以下修复方案，修改对应的代码文件
2. 修改前先 读取文件 读取目标文件确认当前内容
3. 使用 file_replace 执行修改
4. 修改后使用 read_lints 检查是否引入新错误
5. 返回每条 CR 的修复结果

【修复清单】
{粘贴分配给该 子代理 的待修复 CR 条目及修复方案}

【禁止行为】
- 不要修改修复方案之外的代码
- 不要重构或优化不在修复范围内的代码
- 如果修复方案不明确，返回疑问而不是猜测修改

【返回内容】
每条 CR 的修复结果：CR-ID + 修改的文件 + 修改内容摘要 + 是否有 lint 错误
```

### 阶段 D 完成标志
- 所有"待修复"条目已处理
- 评估报告中的修复状态已全部更新
- 无新增 lint 错误
- 向用户报告修复结果摘要

---

## 跨阶段恢复

由于每个阶段的产出都持久化到了 `.agent/context/` 目录，用户可以在任何阶段中断并在新对话中恢复：

- **"继续 CR 评审"** → 扫描 `.agent/context/` 找到最新的 CR 相关文件，判断当前处于哪个阶段，从断点继续
- **"从阶段 B 开始"** → 读取 CR_ITEMS 文件，开始评估
- **"执行 CR 修复"** → 读取评估报告，筛选待修复条目，开始修复
