# Explain-then-Design：需求设计的双轨模式

> 需求设计阶段的产出物形态约定。**不绑定技术栈、不绑定项目。**
> 完整方法论：[references/methodology.md](references/methodology.md)（按需读）

## 核心规则（不可协商）

1. **讲解与设计分离成两份文档**，不混在一份里。
2. **每个结论必须带排除理由** —— 写出「没选的那个方案，以及为什么不选」。
3. **讲解用业务语言**，不写「新增 X 端点」这种实现描述。
4. **末尾必须有「读这份文档的捷径」** —— 碎片时间读者不会从头读。
5. **不确定的标为待确认**，标注「影响什么 + 归属谁」，不猜。

---

## Step 0：判断当前处于哪一步

| 用户表达 | 动作 |
|---|---|
| 「分析这个需求」「这需求要做什么」 | 先出**讲解文档**（Step 1-2），设计文档后跟 |
| 「改哪里」「有什么改动点」 | 已有讲解 → 出**设计文档**；无讲解 → 先补讲解（告知用户） |
| 「为什么要这么做」「这个设计对吗」 | 补**排除理由**（Step 2 的 D 项） |
| 「讲清楚这个需求」 | 纯讲解模式（Step 1-2） |

> **不确认模式**，按上表自动路由。用户明确指定则从命。

---

## Step 1：讲解轨 —— 回答三个必答问题

每个 Story / 每个改动点都要能回答（详见 references）：

| # | 问题 | 要求 |
|---|------|------|
| **A** | **要做什么** | 一句话定义 + **业务因果**（为什么需要它）。禁止功能罗列。 |
| **B** | **怎么做** | 机制 / 流程 / 数据流，落到具体表、端点、服务。 |
| **C** | **为什么** ⭐ | **必须写排除的选项 + 排除理由**。结论会过期，理由不会。 |
| **D** | **不做什么** | 明确排除的干扰项（含「为什么排除」）。防 scope 蔓延。 |

### 讲解文档标准结构

```markdown
# <Story 编号> — <标题>

> 业务讲解 + 设计说明。改动点编号见 <设计文档路径>。
> PRD 原文：<路径>。提测 <日期>。

## 1. 这个业务到底在做什么
   - 一句话定义
   - 为什么需要它（业务因果链，可用箭头图）
   - 关键设计决策 + 为什么这样 / 为什么不那样
   - ⚠️ 已排除的干扰项

## 2. 现有体系怎么做（理解现状才能设计）
   - 现状能力盘点（已有什么，**不用重做**）
   - 缺口在哪
   - 可抄的现成范本
   - 一个常见误判的纠正（如果调研中发现过）

## 3. 本次怎么做（含为什么这样选）
   - 主流程
   - 每个选择带**取舍表**：选项 / 做法 / 排除理由

## 4-5. 待确认 / 下一步
   - 每条标：影响什么 + 归属谁

## 附：读这份文档的捷径
   - 只想了解 A → 读 §X
```

### 粒度约定

- **一 Story 一份讲解文档**（Story 多的大需求，另加 `00-五分钟总览.md`）
- 文件名用中文语义名（`二级流通.md`），不用编号
- 总览负责讲「N 个 Story 之间的关系」，各份负责讲「自己」

## Step 2：三个关键手法

### 手法 1：业务因果优先于功能罗列

**不要**写「PRD 要求做 1、2、3」，要写「因为 X，所以必须做 1、2、3」。

```
代币可在链上自由转让
   ↓
客户可能把币转走，平台账上仍显示持有
   ↓
【后果1】平台持仓不再是事实源 → 校验必然误拒真实客户
【后果2】台账已不能反映真实持仓 → 继续记会产生错误账实差
```

读者理解了因果，就能自己判断「这个改动该不该做」；只给结论，读者只能盲从。

### 手法 2：结论必须带取舍表

```markdown
| 选项 | 做法 | 排除理由 |
|------|------|---------|
| ① （推荐） | ... | — |
| ② | ... | **具体排除原因** |
```

把「选了什么」和「为什么没选别的」放一起，评审时能快速验证判断，事后能追溯决策。

### 手法 3：末尾放「读这份文档的捷径」

```markdown
## 附：读这份文档的捷径

- 只想知道这需求在干嘛 → §1
- 想知道会不会动到基金 → §3.1 的「关键澄清」
- 想知道还有什么没定 → §5
```

碎片时间的读者**不会从头读**。给出入口，他能在 1 分钟内定位到要的那段。

## Step 3：设计轨 —— 改动点文档

讲解轨并行产出，形态是**编号表**（给执行用）：

```markdown
| 编号 | 位置 | 改法 |
|------|------|------|
| M1 | `Class:line` | 具体改什么 |
```

- 编号前缀区分侧（中台 `M` / hub `H` / 网关 `G` / 契约 `C` / 待确认 `Q`）
- **每条引用具体文件:行号**（防臆造的来源标注）
- 讲解文档里的「为什么」在编号表里**不重复**，只留引用

---

## 常见反例

| 反例 | 为什么不合格 |
|---|---|
| 只给 `M1-M30 / H1-H33` 编号表 | 读者知道改哪，不知道在干什么 |
| 讲解里只写「PRD 要求 X」 | 没有因果、没有取舍，读者无法判断对错 |
| 把讲解和设计混成一份长文档 | 碎片时间读不了；更新频率不同会互相干扰 |
| 结论不给排除理由 | 决策不可追溯，三个月后要重做分析 |
| 没有「读这份文档的捷径」 | 碎片读者找不到入口，等于没写 |
| 讲解里出现「新增 X 端点」 | 这是实现描述，不是业务语言 |

## 与现有体系的关系

| 机制 | 关系 |
|---|---|
| `comprehension-ledger`（H2） | **互补，阶段不同**：本模式作用于设计阶段，H2 作用于收尾。本模式的讲解文档可直接作为 H2 输入 |
| `backendflow-spec` / `fullstack-spec` | **被引用**：spec 产出物应遵循本模式。spec 已有「1 页主文档 + 折叠详情」雏形，本模式是其完整形态化 |
| `doc-template` | **不同层**：doc-template 管模板文件，本模式是方法论 |
| `anti-fabrication-two-lines` | **互补**：防臆造管「来源可溯」，本模式管「讲清为什么」 |
| `challenge`（requirement mode） | **互补**：它审「做什么（需求边界）」，本模式管「怎么呈现给人读懂」 |

---

## 一句话总结

> **讲解文档回答「这是什么、为什么这样」，设计文档回答「改哪里」。两份分开写，讲解必须带排除理由，末尾必须给阅读入口。**
