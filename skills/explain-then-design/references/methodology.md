# Explain-then-Design 方法论（完整版）

> SKILL.md 的展开。需要深度理解「为什么这么设计」时读这份。

---

## 一、这个模式解决什么问题

### 现象

传统需求设计文档只产出「改什么」——改动点清单、表结构、接口契约。读者拿到后需要**自己反推业务意图**，而这件事在碎片时间里做不到。

编号清单（`M1`、`H18`、`C4`）对执行者有效，但对**需要理解业务的人无效**。他们读完知道「要改哪 20 个文件」，但不知道「这个业务在干什么、为什么这么设计」。

### 根因

业务理解和技术方案是**两种不同的信息密度需求**。混在一份文档里，一定有一方被牺牲：

- 偏业务 → 技术细节不足，执行者没法干活
- 偏技术 → 业务脉络断裂，读者无法判断「这个设计对不对」

### 具体场景（模式的来源）

2026-10-14，BIG-7709 需求设计过程中，用户提出：

> 我能花在理解这个需求的时间比较碎，我们需求设计的时候，新增一个讲解+设计的模式，不只是梳理设计需求、另外还附带业务讲解，讲解这个业务是要做什么，怎么做，为什么。

**关键约束是「时间碎片化」** —— 不是「不懂技术」，而是**无法长时间连续深挖**。这决定了解讲文档必须：

- 可随时拿起、随时放下（分段自洽）
- 有明确入口（不必从头读）
- 单份篇幅可控（8–15KB，不是 45KB）

## 二、双轨分离的三条理由

### 理由 1：碎片时间的读法不同

讲解要能「随时拿起来读任意一段」，嵌在 45KB 大文档中间做不到。

**判定标准**：打开文档，能否在 30 秒内定位到「回购撤单为什么只能在待受理」这一段？如果不能，就是结构问题。

### 理由 2：更新频率不同

- **讲解**随理解深化而改（今天想明白一个因果，明天补上）
- **设计**随代码而改（改法变了就更新行号）

混在一起会导致：想改讲解，却被设计部分的 diff 淹没；想改设计，又要重排讲解章节。

### 理由 3：读者不同

- 讲解是给**人做决策**用的（产品、架构、评审人、三个月后的自己）
- 设计是给**执行**用的（AI 按编号干活、自己查行号）

## 三、讲解轨的三个必答问题（展开）

### A. 要做什么（What）

**用业务语言，不用技术语言。**

| 不合格 | 合格 |
|---|---|
| 「新增 `POST /v1/rwa/order/list` 端点」 | 「让客户能查到自己的 RWA 订单，并且撤得掉」 |
| 「`RwaProductDetail` 加 `allow_secondary_circulation` 列」 | 「有类代币能在链上自由转让，平台不再管控它的持仓」 |

**检验方法**：把这句话念给产品听，他能不能立刻判断对不对？如果不能，说明还在讲实现。

### B. 怎么做（How）

**机制、流程、数据流**，落到具体的表、端点、服务。

这里是讲「系统怎么运转」，不是讲「改哪个文件」。

**示例**（来自订单管理讲解）：

```
一笔单要经过：客户提交 → 冻结资金/份额 → 中台审核 → 实际扣款
            → 报给上手 → 上手确认成交 → 链上分发 → 结算完成

中台内部切成 9 个状态（对内运维口径），但客户看不懂
  → 对客端要做一次「双轨结算状态封装」：9 个内部状态归并成 7 个对客主状态
```

### C. 为什么（Why）—— **本模式的核心**

**必须写出「排除的选项」和「排除理由」。**

| 只写结论（不合格） | 带排除理由（合格） |
|---|---|
| 「合适性记录走中台 `DynamicPdfGenerator`」 | 「走中台，因为：① 票据的 `SuitabilityRow` 字段与 PRD 逐字对应；② 多语言现成；③ **不用拉 `flp-pdf-creator` 另出 RWA 模板**（少一个外部团队）。排除 hub 方案：它的模板是基金的，RWA 版不存在」 |

**为什么这一步不能省**：结论会过期，理由不会。

三个月后有人问「为什么不用现成的 hub 方案」，只有写出排除理由才能回答。否则要么重做一遍分析，要么盲从。

**书写要求**：
- 排除理由要**具体**（「不方便」不算理由）
- 涉及外部团队的，写清「少拉/多拉谁」
- 涉及取舍的，写清「代价是什么」

### D. 不做什么（范围排除）

**明确排除的干扰项，含「为什么排除」。**

**示例**（来自留痕文件讲解）：

| 项 | 为什么排除 |
|---|---|
| **销售文件** | 截图里有，但产品确认不做；且它属**产品级**文件（随产品走），本就不属订单留痕 |
| **文件摘要清单** | 是**基金独有**产物，**5 份 PRD「摘要」零命中**，与 RWA 无关 |

**为什么重要**：不做排除说明，读者会以为"漏了"，或者在评审时反复问同一件事。写清楚 = 一次说明、永久生效。

## 五、粒度决策

### 一 Story 一份，还是全部合一？

**结论：一 Story 一份 + 总览。**

| 方案 | 适用 | 取舍 |
|---|---|---|
| **一 Story 一份 + 总览** ✅ | Story 数 ≤5、文档总量可控 | 单 Story 读起来不被打断；需要一个总览串关系 |
| 全部合为一份 | 极简单的单 Story 需求 | 会重蹈「碎片时间读不了」的覆辙 |
| 按需拆分 | 复杂度差异极大时 | 结构不统一，读者要重新适应 |

**总览（`00-五分钟总览.md`）负责什么**：

- N 个 Story **合起来**在做什么（一句话）
- 它们之间的**关联**（依赖、耦合、冲突）
- **必须优先拍板**的事（按紧急度排）
- **容易估错**的地方（跨团队/跨工作区依赖）
- 读文档的**路线图**

**各份文档负责什么**：自己那个 Story 的业务因果 + 现状 + 方案 + 待确认。

## 六、三个关键手法（展开）

### 手法 1：业务因果优先于功能罗列

**反例**：

```markdown
❌ PRD 要求：
1. 赎回时不需要校验持仓、不需要冻结持仓，直接下单
2. 不需要记录「客户持币台账」
```

读者只能记住两个孤立的要求，不知道它们为什么存在、是不是同一件事。

**正例**：

```markdown
✅ 代币可在链上自由转让
      ↓
   客户可能把币转走，平台账上仍显示持有 100 个
      ↓
   【后果1】平台持仓不再是事实源
            → 赎回时校验的是平台侧数字，与链上真实持仓对不上
            → 强行校验必然误拒真实客户
   【后果2】台账已不能反映真实持仓
            → 继续记会产生错误账实差，污染持仓事实源
```

**收益**：读者理解了因果，就能自己判断「这个改动该不该做」；只给结论，读者只能盲从。

**进阶**：因果链还能**暴露隐藏的工作量**。上例中，「不冻结」这个后果直接引出了「跳过冻结会炸两条回滚链」这个技术坑——如果只列 PRD 两条要求，这个坑不会被发现。

### 手法 2：结论必须带取舍表

```markdown
| 选项 | 做法 | 排除理由 |
|------|------|---------|
| ① （推荐） | 走中台 `DynamicPdfGenerator` | — |
| ② | 走 hub `flp-pdf-creator` | **模板是基金的，RWA 版不存在，要拉外部团队排期** |
```

**为什么有效**：
- 评审时能快速验证判断（而非只看到一个孤立的结论）
- 事后能追溯决策（三个月后不用重做分析）
- 反向倒逼自己想清楚（写不出排除理由，说明没想透）

**反面**：只列 `① 推荐 / ② 备选`，不写排除理由——等于没做取舍。

### 手法 3：末尾放「读这份文档的捷径」

```markdown
## 附：读这份文档的捷径

- 只想知道**这需求在干嘛** → §1
- 想知道**为什么这么设计** → §1 的「为什么」段
- 想知道**会不会动到基金** → §3.2 的「关键澄清」
- 想知道**还有什么没定** → §4
```

**为什么有效**：碎片时间的读者**不会从头读**。给出入口，他能在 1 分钟内定位到要的那段。

**进阶**：入口项要用**读者的问题**（「会不会动到基金」），不是用**章节标题**（「架构决策」）。前者是读者的真实诉求。

## 七、与现有体系的关系

| 现有机制 | 关系 | 说明 |
|---|---|---|
| `comprehension-ledger`（H2 理解交接） | **互补，阶段不同** | 本模式作用于**设计阶段**，H2 作用于**收尾阶段**。本模式的讲解文档可直接作为 H2 的输入——设计时就讲清了，收尾时不必重讲 |
| `backendflow-spec` / `fullstack-spec` | **被引用** | spec 阶段产出物应遵循本模式。spec 已有「1 页主文档 + 折叠详情」的雏形，本模式是它的**完整形态化**（分离而非折叠） |
| `doc-template` | **不同层** | doc-template 管**模板文件**（assets/*.md），本模式是**方法论**。可作为 doc-template 的一个模板资产 |
| `anti-fabrication-two-lines` | **互补** | 防臆造管「来源必须可溯」，本模式管「讲清楚为什么」 |
| `challenge`（requirement mode） | **互补** | 它审「做什么（需求边界）」，本模式管「怎么呈现给人读懂」 |
| `archify` | **互补** | archify 出时序图（可视化），本模式出讲解文档（叙事化）。两者可并存 |

## 八、反例清单

| 反例 | 为什么不合格 |
|---|---|
| 只给 `M1-M30 / H1-H33` 编号表 | 读者知道改哪，不知道在干什么 |
| 讲解里只写「PRD 要求 X」 | 没有因果、没有取舍，读者无法判断对错 |
| 把讲解和设计混成一份长文档 | 碎片时间读不了；更新频率不同会互相干扰 |
| 结论不给排除理由 | 决策不可追溯，三个月后要重做分析 |
| 没有「读这份文档的捷径」 | 碎片读者找不到入口，等于没写 |
| 讲解里出现「新增 X 端点」 | 这是实现描述，不是业务语言 |
| 待确认项不标「影响什么 + 归属谁」 | 读者不知道要不要管、该找谁 |
| 没有「不做什么」 | 读者以为漏了，或评审时反复问同一件事 |
