# Spec Verifier（Spec 自动验证器）

> **核心定位**：在 Spec → Checkpoint 之间插入自动化验证层，确保 Spec 中的每一个技术声明都有代码库中的事实支撑，消除 AI 幻觉。
> **设计哲学**：Spec 是"承诺"，验证是"兑现检查"——在人类审阅之前，先让机器帮忙过滤掉明显的虚构。

```
需求文档 → AI 分析 → Spec 生成 → [Spec 验证] → 人类确认 → 编码
                                    ↑ 本 Skill
```

---

## 一、触发时机

### 1.1 自动触发（推荐）

在任务执行框架复杂任务流程中，AI 生成 Spec 后、输出给用户确认前，自动执行验证。验证结果附加在 Spec 末尾，一起呈现给用户。

### 1.2 手动触发

用户对已有 Spec 说"验证一下这个 Spec"、"检查 Spec"时触发。

### 1.3 不触发的场景

- 简单任务（单文件修改、纯逻辑修复）不需要 Spec，自然也不需要验证
- Spec 中没有引用任何具体类/方法/配置（纯架构设计讨论）

---

## 二、验证维度

Spec 验证分为四个维度，按优先级排序：

### 2.1 存在性校验（P0 — 必须通过）

**目标**：Spec 中引用的每个类、方法、配置文件必须在代码库中真实存在。

**提取规则**：从 Spec 的以下区域提取待验证实体：
- **集成点**区域中提到的类名、接口名、服务名
- **技术方案**表格中「涉及文件」列的文件路径
- **技术方案**表格中「变更说明」列提到的方法名、字段名

**验证方法**：

```
对于每个提取到的实体：
├── 类/接口名 → 文件搜索 搜索文件是否存在
├── 方法名   → 搜索代码 在对应类中搜索方法定义
├── 配置文件 → 文件搜索 搜索文件路径
└── 配置项   → 搜索代码 在配置文件中搜索 key
```

**判定标准**：
| 结果 | 标记 | 处理 |
|------|------|------|
| 实体存在且唯一匹配 | ✅ EXISTS | 通过 |
| 实体存在但匹配多个（歧义） | ⚠️ AMBIGUOUS | 列出候选，要求 Spec 精确化 |
| 实体不存在 | ❌ NOT_FOUND | 标红，必须修正 |
| 实体是"待新建"的（Spec 中明确标注为新建） | 🆕 TO_CREATE | 通过，但检查其目标路径是否合理 |

### 2.2 签名一致性校验（P0 — 必须通过）

**目标**：Spec 中描述的方法参数、返回值与代码中的实际签名一致。

**提取规则**：从 Spec 中提取形如"调用 `XxxService.doSomething(param1, param2)`"的方法调用描述。

**验证方法**：

```
1. 文件搜索 找到类文件
2. 读取文件 读取对应方法签名
3. 对比 Spec 描述的参数类型/数量与实际签名
```

**判定标准**：
| 结果 | 标记 | 处理 |
|------|------|------|
| 签名完全匹配 | ✅ MATCH | 通过 |
| 参数数量/类型不匹配 | ❌ MISMATCH | 标红，输出实际签名供修正 |
| 方法存在重载，Spec 未明确是哪个 | ⚠️ OVERLOADED | 列出所有重载，要求 Spec 明确 |

### 2.3 模式合规性校验（P1 — 建议通过）

**目标**：技术方案中的实现方式是否符合项目已有的架构模式。

**验证方法**：

```
1. 从 Spec 技术方案中识别功能类型（校验规则、扩展点、策略实现等）
2. 对照 architecture-guard 的设计模式合规表，检查是否使用了正确的模式
3. 如果项目中有对应范本，检查 Spec 方案是否与范本一致
```

**判定标准**：
| 结果 | 标记 | 处理 |
|------|------|------|
| 符合已有模式 | ✅ COMPLIANT | 通过 |
| 未使用推荐模式但有合理理由 | ⚠️ DEVIATION | 提示偏差，建议说明理由 |
| 违反架构模式 | ❌ VIOLATION | 标红，建议调整 |

### Dimension 2.5: Design Cross-Validation（P1 — 建议通过）

**目标**：在 Spec 实体验证通过后、呈现给用户前，执行逻辑层面的可行性验证，**在写代码之前发现设计缺陷**。

**包含三个子维度**：

#### 2.5a 代码链路验证

对技术方案中每个涉及现有代码交互的子任务，追踪至少一层调用链（入口方法 → 直接依赖），验证：
- 声明的调用路径真实连通
- 类型兼容
- 隐式链路（拦截器/AOP/消息监听）不影响预期
- 事务边界覆盖原子操作

将验证结果回填到假设清单。

#### 2.5b Spec 内部一致性检查

检查各章节是否矛盾：
- 每条验收标准都有子任务和测试用例覆盖
- 每个边缘场景都有测试用例覆盖
- 测试用例未出现具体类名/方法名
- 显式约束不与技术方案冲突
- 待验证假设超过总数 50% 时标记"验证不充分"告警

#### 2.5c 反向推演（Pre-mortem）

假设方案已上线且出了问题，逆向推演最可能的 Top 3 故障点；每个故障点检查 Spec 中是否有防护措施，没有则补充到边缘场景表。

#### 2.5d 多视角设计审视

从三个角色视角审视 Spec，发现盲区：

| 视角 | 关注点 | 审视问题 |
|------|--------|---------|
| **开发者** | 可实现性、复杂度、可维护性 | 方案能否合理时间内实现？是否引入不必要复杂度？ |
| **测试者** | 可测试性、可观测性、边界覆盖 | 如何验证每个子任务正确？日志/指标是否足够排查？ |
| **使用者/运维** | 易用性、错误提示、运维负担 | 配置是否直观？出错能否快速定位？ |

发现的问题直接修正到 Spec 对应章节。审视输出追加到交叉验证报告。

#### 交叉验证输出模板

在 Spec 末尾追加「交叉验证报告」：

```
## 交叉验证报告
- **链路验证**：✅ N 条链路已验证 / ⚠️ M 条存在风险（列出）
- **一致性检查**：✅ 无矛盾 / ⚠️ 发现 K 处不一致（列出）
- **反向推演 Top 3 风险**：1. [风险]→[已有防护/需补充] 2. ... 3. ...
- **综合结论**：🟢 可实施 / 🟡 需补充后实施 / 🔴 需重新设计
```

**跳过条件**：小型跨文件修改（≤3 个子任务且不涉及新集成点）可跳过整个 Dimension 2.5；中型任务可只做 2.5a 链路验证；仅大型功能/核心链路/面向用户的功能强制执行 2.5d 多视角审视。

### 2.4 需求覆盖度校验（P1 — 建议通过）

**目标**：Spec 是否完整覆盖了需求文档中的每个要点。

**前置条件**：需求文档已被加载到上下文中。

**验证方法**：

```
1. 从需求文档中提取关键要点（功能点、约束条件、非功能需求）
2. 逐一检查 Spec 中是否有对应的子任务或验收标准覆盖
3. 输出覆盖矩阵
```

**判定标准**：
| 结果 | 标记 | 处理 |
|------|------|------|
| 需求要点在 Spec 中有对应覆盖 | ✅ COVERED | 通过 |
| 需求要点未在 Spec 中体现 | ❌ UNCOVERED | 标红，建议补充 |
| 需求要点被 Spec 显式排除（在「显式约束」中说明） | ⏭️ EXCLUDED | 通过，已有明确理由 |

## 三、执行流程

```
Spec 生成完成
    ↓
Step 1: 实体提取
  → 扫描 Spec 全文，提取所有类名、方法名、文件路径、配置项
  → 区分"引用已有"和"标注为新建"的实体
    ↓
Step 2: 存在性校验（并行）
  → 对每个"引用已有"的实体，使用 文件搜索 / 搜索代码 验证存在性
  → 标记结果：EXISTS / AMBIGUOUS / NOT_FOUND
    ↓
Step 3: 签名一致性校验
  → 对 Spec 中描述了参数/返回值的方法调用，读取文件 对比实际签名
  → 标记结果：MATCH / MISMATCH / OVERLOADED
    ↓
Step 4: 模式合规性校验
  → 对照 architecture-guard 模式表和范本
  → 标记结果：COMPLIANT / DEVIATION / VIOLATION
    ↓
  Step 4.5: 设计交叉验证（Dimension 2.5）
  → 链路验证 + 一致性检查 + 反向推演 + 多视角审视
  → 标记综合结论：🟢 可实施 / 🟡 需补充后实施 / 🔴 需重新设计
    ↓
Step 5: 需求覆盖度校验（如有需求文档）
  → 提取需求要点，与 Spec 子任务/验收标准交叉比对
  → 标记结果：COVERED / UNCOVERED / EXCLUDED
    ↓
Step 6: 生成验证报告
  → 汇总所有维度的结果
  → 附加在 Spec 末尾，一起呈现给用户
```

```markdown
## 🔍 Spec 验证报告

### 总览
- **验证时间**：[时间]
- **验证结果**：✅ 全部通过 / ⚠️ 有告警需确认 / ❌ 存在阻断项需修正

### 📦 存在性校验

| # | 实体 | 类型 | 来源位置 | 结果 | 备注 |
|---|------|------|---------|------|------|
| 1 | `OrderService` | 类 | 集成点 | ✅ EXISTS | `com.xxx.service.OrderService` |
| 2 | `calculateAmount()` | 方法 | 技术方案 #2 | ✅ EXISTS | 在 `RefundService.java:45` |
| 3 | `RepayPlanMapper` | 类 | 技术方案 #3 | ❌ NOT_FOUND | 代码库中未找到此类 |
| 4 | `NewValidationRule` | 类 | 技术方案 #1 | 🆕 TO_CREATE | 目标路径合理 |

### ✍️ 签名一致性

| # | 方法调用 | Spec 描述 | 实际签名 | 结果 |
|---|---------|----------|---------|------|
| 1 | `OrderService.apply()` | `apply(OrderRequest req)` | `apply(OrderApplyRequest request)` | ❌ MISMATCH |

### 📐 模式合规性

| # | 功能 | 推荐模式 | Spec 方案 | 结果 |
|---|------|---------|----------|------|
| 1 | 新增校验规则 | Rule 模式 | 实现 ValidationRule 接口 | ✅ COMPLIANT |

### 📋 需求覆盖度

| # | 需求要点 | Spec 覆盖 | 结果 |
|---|---------|----------|------|
| 1 | 支持批量操作 | 技术方案 #3 | ✅ COVERED |
| 2 | 超时重试机制 | — | ❌ UNCOVERED |
| 3 | 仅支持 V2 接口 | 显式约束 #1 | ⏭️ EXCLUDED |

### 🛠️ 修正建议

1. **[P0]** `RepayPlanMapper` 不存在 → 确认是否需要新建，或是否应为 `RepaymentPlanMapper`（代码库中存在同名类）
2. **[P0]** `OrderService.apply()` 签名不匹配 → 实际参数类型为 `OrderApplyRequest`，非 `OrderRequest`
3. **[P1]** 需求要点「超时重试机制」未被 Spec 覆盖 → 建议在技术方案中补充或在显式约束中说明排除理由
```

## 五、验证策略与效率

### 5.1 并行化

存在性校验的多个实体应**并行搜索**，充分利用工具的并发能力。对于大型 Spec（≥10 个实体），可委派 子代理 并行验证不同维度。

### 5.2 增量验证

如果 Spec 被修正后需要重新验证，只验证**变更的部分**，不重复验证已通过的实体。

### 5.3 验证深度自适应

| Spec 规模 | 验证深度 |
|-----------|---------|
| 小型（≤3 个子任务） | P0 维度必做，P1 维度可选 |
| 中型（4-8 个子任务） | P0 + P1 全做 |
| 大型（>8 个子任务） | P0 + P1 全做，建议委派 子代理 并行 |

### 5.4 阻断 vs 告警

- **P0 维度（存在性 + 签名）有 ❌ 项**：Spec 验证未通过，AI 应主动修正 Spec 后重新验证，再呈现给用户
- **仅有 ⚠️ 告警**：Spec 验证通过（有告警），连同告警一起呈现给用户判断
- **全部 ✅**：Spec 验证通过，直接呈现给用户确认

## 七、自修正机制

当 P0 维度检测到 ❌ NOT_FOUND 或 ❌ MISMATCH 时，AI 应尝试**自动修正**：

### 7.1 NOT_FOUND 修正策略

```
实体不存在
    ↓
模糊搜索（去掉前缀/后缀，搜索核心词）
    ↓
├── 找到相似类名 → 建议替换（如 OrderRequest → OrderApplyRequest）
├── 找到同包下的其他类 → 提示可能的正确名称
└── 完全找不到 → 标记为需人工确认，可能确实需要新建
```

### 7.2 MISMATCH 修正策略

```
签名不匹配
    ↓
读取实际方法签名
    ↓
自动将 Spec 中的描述更新为实际签名
    ↓
标记为已自动修正，附在验证报告中
```

### 7.3 修正后重新验证

自动修正的项目需要**重新验证**，确保修正后的 Spec 依然逻辑自洽。修正后的验证报告中应标注哪些项是自修正的（🔧 AUTO_FIXED）。
