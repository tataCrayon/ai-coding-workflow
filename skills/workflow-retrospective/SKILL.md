# Workflow Retrospective（工作流回顾与自省引擎）V2.0

> **核心定位**：闭合评估环 + 工作流架构全维度迭代引擎。V1 只覆盖"摩擦点趋势分析"，V2 扩展为工作流全方位的记录、审视和迭代能力。
>
> **设计哲学**：对标行业度量驱动理念 + Agile Retrospective 的回顾方法论，但适配 AI Coding 单人工作流的场景。V2 新增架构快照和模块健康度两个维度，使工作流本身变成一个可度量、可演进的工程系统。

## 🎯 核心能力

| 模式 | 适用场景 | 输出 | V2 状态 |
|------|---------|------|---------|
| **A: 趋势报告** | 定期回顾（周/月/按需） | 量化报告 + 趋势图表（文本） | 保持，小幅增强 |
| **B: 专题分析** | 针对某类反复出现的摩擦点深挖 | 根因分析 + 系统性改进方案 | 保持 |
| **C: 改进建议** | 根据趋势数据建议规则/Skill 优化 | 具体的修改建议清单 | 保持 |
| **D: 架构快照** | 记录当前工作流完整架构状态 | 架构版本 + 模块清单 + Agent设计 + 记忆架构 + Hook体系 + 上下文架构 | ★ V2 新增 |
| **E: 模块健康度** | 评估各 Skill/Rule 运行状态 | 使用率、触发准确率、过期标记、维护建议 | ★ V2 新增 |

## 🚦 触发时机

- 用户主动指令："生成观测报告"、"汇总最近的问题"、"工作流回顾"
- 用户主动指令："架构快照"、"记录当前工作流"、"工作流版本"、"模块健康度"
- AI 建议触发：当观测日志目录中日志 ≥5 条且最近一次报告距今 ≥7 天时，可主动建议
- 大重构前触发：用户提到"工作流重构"、"版本升级"时，**主动建议先执行模式 D 记录当前状态**
- 与观测器联动：观测器负责采集，本 Skill 负责消费

## 模式 D：架构快照（★ V2 新增）

> **触发时机**：用户指令"架构快照"、"记录工作流版本"；大重构前必做；建议每次主版本号变更时执行。

### 快照维度

#### D.1 架构版本信息

记录工作流整体的版本演进状态：

| 字段 | 说明 | 来源 |
|------|------|------|
| 版本号 | 当前工作流版本（如 V1.0） | README / VERSION 文件 |
| 版本名称 | 人类可读的版本代号 | README 标题 |
| 快照日期 | YYYY-MM-DD | 当前日期 |
| 架构层数 | 当前架构分为几层 | 架构文档 |
| 上次快照 | 上次快照日期和版本 | snapshot 目录 |
| 关键架构决策 | 本次版本周期内的关键架构变更 | OPT 记录 + 变更日志 |

#### D.2 模块清单

枚举组成工作流的所有模块及其状态：

```
模块类型：
├── 入口文件（AGENTS.md / CLAUDE.md / 平台适配层）
├── 规则层（rules/ 下所有 .md）
├── 技能层（skills/ 下所有 SKILL.md）
├── Hook 脚本（hooks/ 下所有脚本）
├── 知识资产模板（templates/）
└── 文档（docs/）

每个模块记录：
├── 名称
├── 类型（Rule / Skill / Hook / Template / Doc）
├── 版本（如有）
├── alwaysApply（Rule 特有：true / false）
├── 文件大小（行数 / 字节数）
├── 最后修改日期
└── 状态（active / deprecated / needs-review）
```

#### D.3 Agent 设计

记录 Agent 身份和子代理体系的设计状态：

| 维度 | 记录内容 |
|------|---------|
| **主 Agent 身份** | 角色定义、核心原则、行为边界（从 AGENTS.md 提取） |
| **子代理类型** | 有哪些类型的子代理（Explore / general-purpose / Plan / 自定义） |
| **委派协议** | 什么场景委派给什么子代理，委派时传什么参数 |
| **冲突裁决链** | 安全性 > 用户指令 > 可逆性 > 知识资产 > 效率 |
| **熔断策略** | 连续失败次数阈值、行动阶梯、降级规则 |
| **上下文管理** | 热/温/冷层分配、压缩策略、委派决策树 |

#### D.4 记忆架构

记录记忆系统的组织方式：

| 维度 | 记录内容 |
|------|---------|
| **分类体系** | preference / feedback / insight / reference 四类定义和用途 |
| **存储位置** | 项目级 `.agent/memories/`、全局级 `~/.agent/memories/` |
| **索引结构** | MEMORY.md 格式、字段、查找策略 |
| **晋升机制** | insight → memory → rule 的晋升条件和路径 |
| **记忆卫生** | 分层索引质量（核心层≤10/场景层分组/归档层完整）、过时判断、合并策略 |
| **当前容量** | 项目记忆数量、全局记忆数量 |

#### D.5 Hook 体系

记录 Hook 事件和脚本的完整配置：

| Hook 事件 | 类型 | 脚本/内容 | 作用 | 状态 |
|-----------|------|----------|------|------|
| SessionStart | command | `session-start-restore-hooks.py` | 自动恢复 hooks（防 CodeMoss 覆盖） | active |
| Stop | prompt | 12 铁律 L2 Judge | 硬门禁，ok=false 强制继续 | active |
| SessionEnd | command | `session-end-collector.py` | 自动采集会话元数据 | active |
| PreCompact | command | `pre-compact-preserver.py` | 注入压缩保留指令 | active |

#### D.6 上下文架构

记录上下文分层策略的现状：

| 层级 | Token 预算 | 内容 | 加载策略 |
|------|-----------|------|---------|
| 热层 | ~3000 | CLAUDE.md + alwaysApply rules | 每次会话自动注入 |
| 温层 | 按需 | Skills + references + rules-dev | 场景触发加载 |
| 冷层 | 按需检索 | .notes/ + 历史日志 + 记忆 | 关键词/场景检索 |

### 模式 D 执行流程

1. **探查架构文档**：读 README（版本号）、架构文档（层级结构）、BOOTSTRAP.md（部署配置）
2. **枚举模块**：
   - 扫描 `rules/` 目录 → 列出所有 Rule 文件，读 frontmatter 获取 alwaysApply 状态
   - 扫描 `skills/` 目录 → 列出所有 Skill，读 SKILL.md frontmatter 获取版本
   - 扫描 `hooks/` 目录 → 列出所有 Hook 脚本
   - 扫描 `templates/` 目录 → 列出所有模板
3. **提取 Agent 设计**：读 AGENTS.md，提取身份/原则/边界/委派/熔断/上下文管理
4. **提取记忆架构**：读 MEMORY.md 索引，统计记忆数量和分类
5. **提取 Hook 体系**：读 settings.json 中的 hooks 配置
6. **生成快照文件**：写入报告目录

## 模式 E：模块健康度（★ V2 新增）

> **触发时机**：用户指令"模块健康度"、"Skill 使用情况"；建议每 2-4 周执行一次。

### 评估维度

#### E.1 触发频率分析

统计每个 Skill 的实际使用情况：

| Skill | 总触发次数 | 正确触发 | 应触发未触发 | 误触发 | 健康度 |
|-------|:--------:|:------:|:----------:|:----:|:----:|
| unit-test-master | N | N | M | K | 🟢/🟡/🔴 |

数据来源：
- eval-observer 日志中的 Skill 触发记录
- workflow-change-tracker 日志中的 Skill 修改记录
- 用户反馈（"XX Skill 该触发没触发"）

#### E.2 过期检测

| 检查项 | 阈值 | 结论 |
|--------|------|------|
| 连续 2 次回顾零触发 | → 🟡 建议退役评估 |
| 功能被其他 Skill 完全替代 | → 🔴 标记 deprecated |
| 关联的业务/模块已删除 | → 🔴 标记 deprecated |
| 文件最后修改 > 90 天 | → 🟡 建议审视是否仍需要 |
| version 字段缺失 | → 🟡 建议补充版本号 |

#### E.3 Rule 覆盖度

| 检查项 | 健康标准 |
|--------|---------|
| alwaysApply 规则数 | ≤5 个（超过影响热层 Token 预算） |
| 规则间重叠 | 无职责重叠（两个规则管同一件事） |
| 规则场景覆盖 | 所有触发场景有明确规则文件 |
| frontmatter 完整性 | 每个 Rule 有 name/description/alwaysApply |

#### E.4 记忆健康度

| 检查项 | 健康标准 |
|--------|---------|
| 索引容量 | <30 条（超过触发容量监控） |
| 过时记忆 | 无关联代码已删除的 insight 类记忆 |
| 重复记忆 | 无同一主题的重复记忆文件 |
| 晋升遗漏 | 无"应晋升为 Rule 但未晋升"的记忆 |

### 模式 E 执行流程

1. **收集触发数据**：
   - 扫描 eval-observer 日志，提取 Skill 触发/未触发事件
   - 扫描 workflow-change-tracker 日志，提取 Skill 修改记录
2. **过时检测**：逐 Skill 检查最后修改日期、版本字段、引用完整性
3. **Rule 分析**：统计 alwaysApply 数量、检查职责重叠
4. **记忆分析**：统计索引容量、检查过时/重复
5. **生成健康度报告**

## ⚠️ 约束

- **只读分析**：本 Skill 只生成报告和建议，不自动修改规则/Skill 文件
- **数据驱动**：所有洞察必须有日志数据支撑，禁止凭印象下结论
- **改进建议必须具体**：禁止"优化 XX Skill"这种模糊建议，必须说明改什么、怎么改
- **日志不足时降级**：若日志 < 3 条，告知用户数据不足以生成有意义的趋势报告
- **快照不可篡改**：架构快照一旦生成，视为历史记录，不应修改（新状态生成新快照）
- **重构前必须快照**：当用户提到工作流重构时，必须主动建议先执行模式 D

## 🔗 与其他能力的协作

| 上游 | 本 Skill | 下游 |
|------|---------|------|
| `eval-observer`（Rule）→ 产出观测日志 | **聚合分析**（模式 A/B/C） | → 记忆晋升（写入 MEMORY 或升级为 Rule） |
| `task-spawner`（PAUSE 模式）→ 存档中的教训 | **趋势判断**（模式 A） | → `workflow-optimization-log` 验证改进效果 |
| `circuit-breaker`（Rule）→ 熔断记录 | **根因分析**（模式 B） | → `skill-creator` 优化/创建 Skill |
| `workflow-change-tracker` → 变更记录 | **模块健康度**（模式 E） | → Skill 退役/升级决策 |
| 工作流架构（README / AGENTS.md / 架构文档） | **架构快照**（模式 D） | → 版本对比、重构回滚参考 |

## 质量自检

生成报告后，AI 必须检查：
- 每个洞察是否有对应的数据支撑？（禁止无数据的主观判断）
- 改进建议是否具体到可执行？（指明改哪个文件、改什么内容）
- 是否与上期报告做了对比？（如有上期报告）
- 报告篇幅是否合理？（不超过 200 行，聚焦关键信息）
- 模式 D 快照是否覆盖了全部 6 个维度？（架构版本/模块清单/Agent设计/记忆架构/Hook体系/上下文架构）
- 模式 E 健康度是否给出了具体的维护建议？（禁止只标红不写建议）
