# Knowledge Asset Manager (知识资产管家)

本技能旨在建立一个健康的知识闭环，不仅将零散的代码解读转化为结构化资产，更致力于构建一个**动态的知识图谱 (Knowledge Graph)** 和 **统一的业务本体库 (Base Ontology)**。它既能处理新知识的增量入库，也能对存量知识进行定期盘点与重构，还能通过**模板化巡检**持续保障资产与代码的一致性，更能在代码发生变动后**自动校验并更新资产**，确保知识资产始终与代码保持同步。

## 🎯 核心工作流

### 工作流 A：增量固化 (保存新资产)
当用户在对话中要求"把刚才的分析沉淀下来"或"生成一份资产"时触发：

0. **内容来源判定 (协作分析)**：评估当前对话上下文中是否已有足够的分析内容可供沉淀。
   - **已有充分内容**（如刚完成了 `code-business-analyzer` 的全链路分析）：直接进入步骤 1。
   - **内容不足或需要深度代码分析**：主动调用下方【可协作的分析型 Skills】获取内容，再进入步骤 1。本 Skill 不自行做深度代码分析，分析交给专业的分析 Skill。
1. **术语对齐与提取 (Base)**：检查对话中是否出现了新的业务术语、产品名称。如果有，必须同步更新到全局的术语库文件（如 `.notes/foundation/glossary.md`），并在当前资产中严格使用规范名称。
2. **内容结构化与图谱化 (Graph)**：按照下方的【资产 Markdown 格式规范】组织内容，**必须**明确列出该资产的"上游依赖"和"下游影响"，将其编织进现有的知识图谱中，绝不产生"孤岛节点"。
2.5 **四维质量门禁 (Quality Gate)**：落盘前必须按以下四个维度自检并修正，未通过不得进入步骤 3：
   - **代码可追溯性**：`关联代码入口` 中的类名/方法名/配置路径必须可复核，至少包含 1 个已验证代码入口；每个入口写明验证方式（如 `search_file`、`file_grep`、`read_file`、用户提供代码片段）。
   - **知识图谱完整性**：`Graph Links` 不能只是空模板；至少提供 1 条真实可访问的上游/横向/下游链接。确实无关联时，必须写明“已检索，暂无可靠关联”，并在质量自检中标记为待后续补链。
   - **AI 检索友好度**：`AI 检索关键词` 必须覆盖业务术语、代码符号、配置/枚举名、中文口语化叫法和英文/缩写变体；关键词应同步进入 `knowledge-index.md`。
   - **格式规范性**：必须包含元信息、业务背景、核心逻辑、关联代码入口、Graph Links、质量自检六类结构；不得缺章或保留无意义占位符。
3. **归类落盘**：分析内容所属的业务域，使用编辑工具将内容保存到工作区 `.notes/` 下合适的子目录中。
   - **三层归类规则**：
     - Foundation 层（`.notes/foundation/`）：项目级基础认知（技术栈、术语、架构决策），极少变化
     - Patterns 层（`.notes/patterns/`）：可复制的编码范本、操作手册、排查指南，跟随技术栈演进
     - Analysis 层（`.notes/analysis/{domain}/`）：特定业务链路/需求的深度分析，跟随需求生命周期
4. **强制更新索引 (Index)**：**落盘后必须立即执行，不可跳过！** 读取工作区的 `knowledge-index.md`，找到该资产所属层级对应的表格区域，将新资产的「关键词」、「标题」和「相对路径」作为一个新行插入。如果业务域表格不存在，则新建一个表格区域。
5. **强制完成自检**：落盘和索引更新完成后，**必须输出以下检查清单**，逐项确认。任何一项未通过则必须立即补救；不能只写“已检查”，必须说明验证证据或补救动作：

```
✅ 资产落盘自检清单
- [ ] 文件已保存到 `.notes/{layer}/{domain}/` 正确目录下
- [ ] 代码可追溯性达标：`关联代码入口` 至少 1 个入口已验证，且写明验证方式/来源
- [ ] 知识图谱完整性达标：Graph Links 至少 1 条真实链接已验证；如暂无可靠关联，已显式标记待补链
- [ ] AI 检索友好度达标：关键词覆盖业务术语、代码符号、配置/枚举名、中文口语和英文/缩写变体
- [ ] 格式规范性达标：元信息、业务背景、核心逻辑、关联代码入口、Graph Links、质量自检均存在且无空占位
- [ ] 已更新 `knowledge-index.md` 索引表，新增了对应条目
- [ ] 资产中的 Graph Links 指向的目标文件确实存在（无死链）
- [ ] 术语使用与全局术语库一致
```

**四维评分建议**：如用户要求评估资产质量，使用 1~5 星对 `代码可追溯性`、`知识图谱完整性`、`AI 检索友好度`、`格式规范性` 逐项评分，并给出扣分原因和修复建议。

### 可协作的分析型 Skills

当资产内容需要深度代码分析、业务逻辑解读等能力时，`knowledge-asset-manager` 应主动调用以下 Skill 获取分析结果，然后由自己负责格式化、落盘和索引维护：

| 分析需求 | 调用的 Skill | 典型场景 |
|---------|-------------|---------|
| 业务流程/规则/代码解读 | `code-business-analyzer` | "帮我沉淀某个流程的业务规则" |
| 代码概念定位 | `code-concept-tracer` | "帮我沉淀某个概念涉及的所有代码位置" |

> **扩展提示**：如果项目集成了外部知识获取工具（如知识库 MCP、需求管理系统等），可在此表格中追加对应的 Skill 映射行。
>
> **职责边界**：分析型 Skill 只负责产出分析内容（不负责落盘），`knowledge-asset-manager` 只负责格式化、落盘和索引维护（不负责深度分析）。

### 工作流 B：局部存量盘点与优化 (整理少量已有资产)
当用户要求"整理一下某个模块的资产"、"盘点某几个笔记"或"优化局部资产"时触发：

1. **局部扫描**：使用 `list_directory` 扫描 `.notes/` 下的特定子目录，或读取全局索引表获取现有资产清单。
2. **深度阅读与确认**：使用 `read_file` 批量阅读目标资产的内容，评估并确认其健康度：
   - **黑话与术语校验 (Base)**：使用的产品名、业务概念是否与全局术语库一致？是否存在过期的旧称呼？
   - **图谱连通性校验 (Graph)**：是否缺乏上下游业务的关联链接？是否是孤岛节点？
   - **代码溯源校验**：是否丢失了关键的"关联代码入口"链接？
   - **冗余与索引校验**：是否存在讲了同一件事的重复文件？是否尚未登记在索引表中？
3. **输出重构计划**：向用户输出一份明确的《资产整理建议报告》。
4. **执行重构**：**必须等待用户确认后**，使用文件编辑工具对资产进行重写、合并、改名或删除，并同步将最新状态更新至索引表。

### 工作流 C：模板化巡检 (Template-based Inspection)
当用户要求"巡检资产"、"检查资产健康度"、"资产覆盖率"或"全面整理资产库"时触发。巡检采用**"模板-实例"**架构：模板定义检查标准，每次巡检基于模板创建独立的实例文件记录本次发现。

**严禁在单轮对话中强行一次性读取所有文件**（防上下文爆炸），必须转入**任务持久化管理模式**。

#### C.0 巡检范围确认
触发后**必须先询问用户**确认巡检范围：
- **按域巡检**："只检查某个域的资产" → 仅扫描对应子目录
- **按层巡检**："检查所有 foundation 层资产" → 仅扫描 `.notes/foundation/`
- **全量巡检**："全面检查所有资产" → 扫描整个 `.notes/` 目录
- **覆盖率专项**："检查资产覆盖率" → 仅执行覆盖率分析（C.3），不做健康度检查

#### C.1 创建巡检实例
确认范围后，基于下方【巡检任务存档格式】在 `.aicoding/context/` 下创建本次巡检的实例文件：
- 文件名格式：`{YYYYMMDD}_资产巡检_{scope}.md`
- 初始化所有待检查的子目录为 `pending` 状态

#### C.2 分批执行巡检检查项（Map-Reduce 模式）
逐个推进子目录的巡检，每个子目录执行以下**五维健康度检查**：

| 检查维度 | 检查内容 | 严重级别 |
|---------|---------|---------|
| **① 格式合规** | 是否符合【资产 Markdown 格式规范】（含 AI 检索关键词、关联代码入口表格、Graph Links） | ⚠️ Warning |
| **② 术语一致性** | 使用的产品名、业务概念是否与术语库一致 | ⚠️ Warning |
| **③ 图谱连通性** | Graph Links 是否存在死链？是否是孤岛节点？ | 🔴 Error |
| **④ 代码-资产一致性** | 资产中"关联代码入口"表格里的类/方法是否仍然存在？ | 🔴 Error |
| **⑤ 冗余与索引** | 是否存在重复文件？是否已登记在 `knowledge-index.md` 中？ | ⚠️ Warning |
| **⑥ 鲜度检查** | Analysis 层资产的 `last_verified` 字段是否存在（该字段为 Analysis 层必填）？距今是否超过 30 天？超过则标记为 `stale`。AI 加载 stale 资产时须声明"⚠️ 该资产最后验证于 XX，内容可能过期，以代码为准" | ⚠️ Warning |

**执行架构**：

```
                        ┌─ Sub-Agent 1: 检查 foundation/        → 局部报告 1
                        │
Orchestrator (主模型)  ──├─ Sub-Agent 2: 检查 patterns/          → 局部报告 2
        │               │
        │               ├─ Sub-Agent 3: 检查 analysis/{domain1}/ → 局部报告 3
        │               │
        │               └─ Sub-Agent 4: 覆盖率扫描（全局）        → 覆盖率报告
        │
        └── Reduce: 汇总所有局部报告 → 全局巡检报告 + 待修复清单
```

**Orchestrator 职责**（主模型，轻量化）：
1. 使用 `list_directory` 获取 `.notes/` 子目录列表
2. 按子目录切分任务，使用 `task` 工具一次性派发最多 5 个 Sub-Agent
3. 如果子目录 > 5 个，分批派发（第一批完成后再派发第二批）
4. 收集所有 Sub-Agent 返回的局部报告
5. 合并去重，生成全局巡检报告
6. 更新巡检实例文件
7. **Orchestrator 严禁自行读取资产文件做检查**

**Sub-Agent 健康度检查任务 Prompt 模板**：

```
【任务类型】只读调研任务

【任务目标】
对 `.notes/{target_dir}/` 目录下的所有资产文件执行五维健康度检查。

【必须做】
1. 使用 list_directory 列出 `.notes/{target_dir}/` 下的所有 .md 文件
2. 逐个使用 read_file 读取每个资产文件的完整内容
3. 对每个文件执行以下五维检查：

   ① 格式合规（⚠️ Warning）：
   - 是否包含"AI 检索关键词"字段
   - 是否包含"关联代码入口"表格
   - 是否包含"知识图谱关联 (Graph Links)"章节

   ② 术语一致性（⚠️ Warning）：
   - 先读取 `.notes/foundation/glossary.md`（如果存在）
   - 检查资产中的术语是否与术语库一致

   ③ 图谱连通性（🔴 Error）：
   - 检查 Graph Links 中的相对路径链接，验证目标文件是否存在
   - 检查是否是孤岛节点（完全没有 Graph Links）

   ④ 代码-资产一致性（🔴 Error）：
   - 提取"关联代码入口"表格中的所有代码引用
   - 使用 search_file 验证对应的源文件是否存在

   ⑤ 冗余检查（⚠️ Warning）：
   - 检查同目录下是否有标题/内容高度相似的文件

4. 汇总所有发现，按以下格式返回结果

【禁止行为】
- 不要修改或创建任何文件
- 不要读取目标目录以外的资产文件（术语库和代码验证除外）

【返回格式】
---
## 巡检局部报告：{target_dir}
- 检查文件数：{N}
- Error 数：{N}
- Warning 数：{N}

### 🔴 Error
| # | 资产文件 | 检查维度 | 问题描述 | 建议修复方案 |
|---|---------|---------|---------|------------|

### ⚠️ Warning
| # | 资产文件 | 检查维度 | 问题描述 | 建议修复方案 |
|---|---------|---------|---------|------------|

### 文件清单
| 文件名 | 格式 | 术语 | 图谱 | 代码一致性 | 冗余 |
|--------|------|------|------|-----------|------|
---
```

**Sub-Agent 覆盖率扫描任务 Prompt 模板**：

```
【任务类型】只读调研任务

【任务目标】
扫描项目代码库中的核心组件，与 `.notes/` 资产进行交叉比对，计算资产覆盖率。

【必须做】
1. 扫描项目中的核心组件类型（{根据项目技术栈配置}）
   - 例如：Controller、Service、Repository、配置类、扩展点等
2. 使用 list_directory 递归扫描 `.notes/` 目录，获取所有资产文件列表
3. 对每个扫描到的代码组件，检查是否在任何资产文件中被提及
4. 按格式返回覆盖率报告

【禁止行为】
- 不要修改或创建任何文件
- 不要做深度代码分析，仅做存在性匹配

【返回格式】
---
## 覆盖率扫描报告

### {组件类型1} 覆盖率
- 已覆盖：{N}/{Total} ({percent}%)
- 缺失项：[{Name1}, {Name2}, ...]

### 综合覆盖率
- 总计：{N}/{Total} ({percent}%)
---
```

#### C.3 Reduce：汇总全局巡检报告
Orchestrator 收集所有 Sub-Agent 返回的局部报告后：

1. **合并 Error/Warning 列表**
2. **合并覆盖率数据**
3. **跨目录去重**
4. **索引一致性校验**（Orchestrator 自行执行）
5. **生成全局巡检报告**：

```markdown
# 📋 资产巡检报告
- **巡检时间**：YYYY-MM-DD
- **巡检范围**：[全量 / 指定范围]
- **巡检结论**：[健康 ✅ / 需关注 ⚠️ / 需修复 🔴]
- **执行方式**：Map-Reduce（{N} 个 Sub-Agent 并行）

## 一、健康度检查结果

### 🔴 Error（必须修复）
| # | 资产文件 | 检查维度 | 问题描述 | 建议修复方案 |
|---|---------|---------|---------|------------|

### ⚠️ Warning（建议修复）
| # | 资产文件 | 检查维度 | 问题描述 | 建议修复方案 |
|---|---------|---------|---------|------------|

### 各目录健康度一览
| 子目录 | 文件数 | Error | Warning | 状态 |
|--------|--------|-------|---------|------|

## 二、资产覆盖率
（覆盖率 Sub-Agent 的返回结果）

## 三、待修复清单（需用户确认）
- [ ] 修复项 1：...
- [ ] 修复项 2：...
```

6. **更新巡检实例文件**

#### C.4 修复策略决策

| 修复项数量 | 策略 | 执行方式 |
|-----------|------|---------|
| **≤ 5 项** | 当前对话直接修复 | 等待用户逐项确认后执行 |
| **> 5 项** | 渐进修复模式 | 持久化为 Checklist 任务，引导用户在新对话中逐项推进 |

#### C.5 任务归档
全部完成后，将巡检实例文件中的状态更新为 `已完成`。

### 工作流 D：恢复中断的资产整理任务 (Resume Audit/Validate)
当用户在新会话中要求"继续整理资产"、"恢复资产整理任务"、"继续校验"时触发：

1. **扫描存档**：扫描 `.aicoding/context/` 目录，查找包含 `资产巡检`、`资产校验` 等关键词且状态为"进行中"的任务文件
2. **识别任务类型**：巡检 → 恢复到工作流 C，校验 → 恢复到工作流 E
3. **读取并恢复**：提取已完成/未处理的子目录和断点信息
4. **重建待办**：调用 `todo_write` 重建任务列表，从第一个 `pending` 任务继续
5. **无缝衔接**：衔接到对应工作流的分批执行步骤

### 工作流 E：资产校验与自动更新 (Validate & Auto-Update)
当用户要求"校验资产"、"更新资产"、"资产适配"、"代码变动后同步资产"时触发。

与巡检（工作流 C）的核心区别：**巡检是"发现问题 → 报告 → 等用户确认"，校验更新是"发现问题 → 自动修复 → 汇报结果"**。Sub Agent 拥有编辑权限。

#### E.0 校验范围与策略确认
触发后**自动确定**校验范围（无需询问用户）：

**修复策略分级**（Sub Agent 内部自动执行）：

| 问题类型 | 修复策略 | 示例 |
|---------|---------|------|
| 🟢 **事实性错误** | 直接修复 | 类名/方法名变更、文件路径变更、签名变化 |
| 🟡 **格式缺失** | 直接补充 | 缺少 AI 检索关键词、缺少 Graph Links 章节 |
| 🔴 **业务逻辑变更** | 仅报告，不修改 | 核心逻辑描述与代码不一致 |
| ⚫ **资产引用的类/方法已删除** | 标记为 `[已删除]` 并报告 | 类被整体删除、方法被移除 |

#### E.1 创建校验任务
在 `.aicoding/context/` 下创建校验任务实例文件。

#### E.2 分批派发校验 Sub Agent（Map 阶段）

采用与巡检相同的 **Map-Reduce** 架构，但 Sub Agent 拥有**编辑权限**。

**Sub-Agent 校验修复任务 Prompt 模板**：

```
【任务类型】编辑任务

【任务目标】
对 `.notes/{target_dir}/` 目录下的所有资产文件执行代码一致性校验，并自动修复事实性错误。

【必须做】
1. 使用 list_directory 列出 `.notes/{target_dir}/` 下的所有 .md 文件
2. 逐个使用 read_file 读取每个资产文件的完整内容
3. 对每个文件执行以下校验：

   ① 代码引用校验（核心）：
   - 提取"关联代码入口"表格中的所有代码引用
   - 使用 search_file 验证对应的源文件是否存在
   - 如果存在但路径/名称变更 → 使用 file_replace 更新资产中的引用
   - 如果已被删除且无替代 → 在表格中标注 `[已删除]`，记录到报告

   ② 格式完整性补充：
   - 缺少"AI 检索关键词" → 自动生成并补充
   - 缺少"知识图谱关联 (Graph Links)"章节 → 添加空模板章节
   - 缺少"关联代码入口"表格 → 添加空模板表格

   ③ Graph Links 死链修复：
   - 检查相对路径链接，验证目标文件是否存在
   - 已移动 → 更新链接路径
   - 已删除 → 移除该链接并记录

   ④ 业务逻辑一致性检查（仅报告，不修改）：
   - 核心业务规则描述与代码明显不一致 → 记录到"需人工确认"部分

4. 修复完成后，更新资产文件头部的"更新时间"字段

【禁止行为】
- 不要修改资产中的业务逻辑描述
- 不要删除或创建资产文件
- 不要修改目标目录以外的文件（除非修复 Graph Links 反向链接）
- 不要修改代码文件

【返回格式】
---
## 校验修复报告：{target_dir}
- 校验文件数：{N}
- 自动修复数：{N}
- 需人工确认数：{N}
- 无变化文件数：{N}

### ✅ 自动修复项
| # | 资产文件 | 修复类型 | 修复前 | 修复后 | 说明 |
|---|---------|---------|--------|--------|------|

### ⚠️ 需人工确认
| # | 资产文件 | 问题类型 | 问题描述 | 建议处理方式 |
|---|---------|---------|---------|------------|

### ⚫ 已删除标记
| # | 资产文件 | 被删除的引用 | 说明 |
|---|---------|------------|------|

### 文件清单
| 文件名 | 代码引用 | 格式 | 图谱链接 | 业务逻辑 | 状态 |
|--------|---------|------|---------|---------|------|
---
```

## 📋 资产 Markdown 格式规范

> **设计原则**：所有资产的首要服务对象是 **AI Coder**（而非人类阅读者）。格式必须优化为：
> 1. **高检索命中率**：标题、标签、关键词必须覆盖 AI 在搜索时可能使用的搜索词
> 2. **零歧义可执行**：代码路径必须是可直接使用的全路径引用，而非模糊描述
> 3. **快速定位**：AI 拿到资产后能在 3 步内找到对应代码并开始工作

所有经过本技能生成或优化的资产，应遵循以下结构：

```markdown
# [资产标题]

> **更新时间**：YYYY-MM-DD
> **last_verified**：YYYY-MM-DD（Analysis 层必填字段。记录最近一次人工或 AI 验证资产与代码一致性的日期。超过 30 天未更新将被巡检标记为 stale，AI 加载时须声明过期风险）
> **业务域**：{domain}
> **核心实体**：[术语库中定义的标准名称]
> **关联标签**：[关键词1], [关键词2], [同义词/别名]
> **AI 检索关键词**：[列出 AI 搜索时可能使用的所有变体词，含业务术语、代码类名/方法名、枚举/配置名、中英文、缩写、口语化表达]
> **质量状态**：代码已验证 / 部分待验证；图谱已连接 / 待补链；索引已更新 / 待更新

## 1. 业务背景 / 核心意图
(一句话说清楚：这段逻辑解决什么业务问题，为什么存在)

## 2. 核心逻辑 / 规则解析
(使用项目符号或表格，提取清晰的条件→结果→异常)
(对于业务规则，必须包含：判断条件、满足时处理、不满足时的错误码和错误信息)

## 3. 关联代码入口 (AI 可直接使用)
(必须提供全路径类名/模块路径、方法名或可直接读取的配置路径；每条记录必须有验证方式，避免不可追溯)
| 角色 | 代码引用 | 关键方法/配置 | 验证方式 | 说明 |
|------|---------|--------------|----------|------|
| 业务入口 | `com.example.app.XxxServiceFacade` | `submit()` | `search_file` + `read_file` 已验证 | 接口层入口 |
| 核心逻辑 | `com.example.app.XxxDomainService` | `process()` | `file_grep` 已验证方法存在 | 领域服务 |
| 配置文件 | `app-module/src/main/resources/xxx-config.json` | `{bizCode}` | `read_file` 已验证 | 相关配置 |

## 4. 知识图谱关联 (Graph Links)
(必须使用相对路径链接到其他相关资产，形成网状结构；链接必须真实存在，不能只保留示例占位)
- **上游前置概念**：[XX概念](../../foundation/glossary.md) — 关系：提供术语/配置前置理解
- **下游派生/影响**：[XX流程](../domain/flow.md) — 关系：受当前规则影响
- **横向对比/相关**：[同类实现](./similar.md) — 关系：同类实现对比

## 5. 资产质量自检
| 维度 | 评分 | 证据 | 待补 |
|------|------|------|------|
| 代码可追溯性 | ⭐⭐⭐⭐⭐ | 关键类/方法/配置均已验证并记录验证方式 | 无 |
| 知识图谱完整性 | ⭐⭐⭐⭐⭐ | Graph Links 已连接上游/下游/横向资产且无死链 | 无 |
| AI 检索友好度 | ⭐⭐⭐⭐⭐ | 关键词覆盖业务术语、代码符号、配置/枚举名、同义词 | 无 |
| 格式规范性 | ⭐⭐⭐⭐⭐ | 必填章节完整，无空占位 | 无 |
```

## ⚠️ 防错与防腐约束
1. **禁止断链/孤岛**：新建或重命名文件时，**必须**同步更新索引表，并在新文件中建立 Graph Links。Graph Links 不允许只保留示例占位；无法找到可靠链接时必须显式标记“待补链”并说明已检索范围。
2. **术语一致性 (Base Alignment)**：所有生成的资产中的核心概念，必须与全局术语表保持完全一致。
3. **禁止过度脑补**：如果原笔记中缺失某部分代码逻辑且当前上下文中没有，不要凭空捏造，应标记“待验证”并使用代码搜索工具查证后再补全；严禁把推断写成已验证事实。
4. **引用必须可追溯**：资产中出现的类名、方法名、配置项、表名、枚举值，必须尽量记录验证方式；未验证的引用必须标注“用户描述/待验证”。
5. **修改前防线**：大范围合并或删除文件前，必须输出计划并得到用户的明确同意。
