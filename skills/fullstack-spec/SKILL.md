# FullStack Spec：方案签收门禁

解决know-u-time 实战最痛的问题：会话里聊定的方案，下个会话 AI 不认账、文件里找不到。

## 门禁规则（不可协商）

1. **未经用户签收的 L 级方案，一行生产代码都不许写。** mock/示意可以，产线不行。
2. 需求没有用例编号/章节号的，测试不许写（先补文档再写测试）。
3. 需求变更必须进版本：改的是 `docs/product.md`（产品真相，语义化版本 v1.7→v1.8），
   单次变更走 `docs/plans/`（见下）。
4. 用户只给一句模糊话时，先澄清再提案。澄清用 AskUserQuestion 类工具给选项 +
   推荐，不开放式连环问。

## 澄清五问（提案前过一遍，答不上来的就是提案里的「开放问题」节）

1. 这解决谁的什么问题？（一句话用户故事）
2. 不做什么？（本期边界，防 scope 蔓延——比做什么更重要）
3. 成功长什么样？（可验证的验收标准，将来写进测试）
4. 有哪些方案？各自的代价？（至少两案，给推荐 + 理由；方案按个人开发者性价比排序）
5. 什么不能动？（红线：包名/签名/数据 schema 兼容/安全约束）

## 产物一：产品文档（docs/product.md）

- 版本化章节：需求 v1.x 一节一版，旧版不删（可追溯当初为什么这么做）。
- 每个用例有稳定编号（UC-A1、8.3 九条这类），测试名对齐编号（fullstack-trace 消费）。
- 关键决策附「决策记录」：问题、选项、结论、日期。AI 与未来的你都要能查到
  「当时为什么选 A 不选 B」。

## 产物二：变更提案（docs/plans/YYYY-MM-DD-<slug>.md）

五件套（源自 OpenSpec，裁剪到个人项目够用）：

```markdown
# <日期> <标题>
## 1. Proposal        为什么做：用户故事 + 澄清五问的回答 + 红线
## 2. Spec Delta      需求怎么变：ADDED/MODIFIED/REMOVED 逐条（对齐 product.md 编号）
## 3. Design          技术方案：数据流/表结构/接口签名级别（到「能照做」的精度）
## 4. Tasks           任务清单（交给 fullstack-plan 细化，此处先列批次 A/B/C）
## 5. Sign-off         用户签收：方案选项 + 用户原话 + 日期   ← 门禁凭证
```

### 产出物形态：遵循 `explain-then-design`（讲解+设计双轨模式）

> 完整的产出物形态、三必答问题、取舍表写法、自检清单见 `explain-then-design/references/methodology.md`。此处只列本流程的落地要求。

- **讲解轨（人读）**：独立文档。回答三问——要做什么（业务语言）/ 怎么做（机制数据流）/ **为什么（含排除理由 + 取舍表）**；另加「不做什么」（范围排除）与「读这份文档的捷径」。多 Story/多模块需求另出 `00-五分钟总览.md`。
- **设计轨（执行）**：上面这份五件套提案。**Proposal 节是用户签收的唯一必读面**，目标 5 分钟读完。
- **硬性**：讲解轨的每条结论必须带**排除理由**（写出没选的方案及原因）；末尾必须有**阅读入口**（用读者的问题，不用章节标题）。

## 签收动作

提案写完 → 给用户两个以上的方案选项（带推荐）→ 用户明确回复选哪个
（或手绘线框/编号列点，这本身就是签收）→ 把用户原话记进 Sign-off 节 →
才能进 fullstack-plan。用户「先做着吧」不算签收 L 级方案；但用户明确授权
「按规划直接执行」的持续模式（know-u-time 工作流）下，签收 = 用户读过
STATUS 里的方案摘要且未反对，此时在 Sign-off 写明这个依据。

## 与设计的关系

页面/交互类变更不走纯文字方案：Design 节先给流程与信息架构选项，然后进
fullstack-design 的两级 demo 门禁（① UX 灰阶 demo 拍流程 → ② 视觉 mock 拍观感），
两级签收后方案才算成立。用户说不清想要什么时，demo 本身就是澄清工具——
文字聊十轮不如让用户点一下。
