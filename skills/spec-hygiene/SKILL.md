# spec-hygiene：规格文档防腐

> 一句话：**文档不是资产，是负债**。每写一句都要先回答「它会不会在下一次提交后变成假话」。
> 设计文档的价值在于**减少返工**，不在于**留痕迹**。留痕迹交给 git。

## 0. 先判断：这份文档该不该存在

写之前先过这张表。**任何一项答不出「为什么」，就不写。**

| 判据 | 不满足时 |
|---|---|
| 有没有读者？**具体是谁**（不是「以后可能有」） | 不写。给自己看的用 commit message |
| 它解决的是**决策模糊**还是**信息记录**？ | 信息记录 → 放代码旁边或 commit message |
| 里面有没有**代码里读不出来的东西**（取舍理由、排除项、边界）？ | 没有 → 让它从代码生成，别手抄 |
| 会不会**一个月后还在变**？ | 会变 + 读者少 → 别写进文档，写进代码注释 |
| 是不是**第二处**复述同一件事？ | 是 → 删掉旧的，或删掉新的 |

**Google 的经验判据**（Design Docs at Google）：如果一个设计文档本质上在说「我们打算这么实现」而不谈取舍、备选项和决策理由，那**不如直接写代码**。

## 1. 五条铁律

### 铁律 1：单一事实源（一条事实只写一遍）

同一句话在两处存在，就必然有一处先过期。

本项目实测：一个「频率不接调度」的口径，曾在 **6 份文档 + 5 个代码位置**里各写一遍。改一处要追六处，追漏了就是「文档说 A、代码做 B」。

**做法**：写之前先 `grep` 你要写的这句话的关键词。
- 命中 0 次 → 找**最权威的那一处**写（DDL 进数据模型文档、接口进接口契约、枚举进枚举表）
- 命中 ≥1 次 → **要么引用，要么改那一处**，不要在第二处再写一遍

**引用怎么写**：`见 07 §2.1` 而不是把 §2.1 抄过来。

### 铁律 2：能生成的别手写

| 内容 | 从哪来 |
|---|---|
| 接口的请求/响应字段表 | 代码里的类型定义 / `Field(description=...)` |
| 表结构 DDL 列 | ORM 模型 / 迁移脚本 |
| 枚举码值与中文文案 | 代码里的枚举类 |
| 测试覆盖矩阵 | 测试文件里的标记（`BDD 3.2` 之类） |

手抄这些的唯一结果就是漂移。**判据**：如果这段内容在代码里已经逐字存在，就应该让它生成，或者干脆不写。

Google 的说法同源：**「不要让 temptation 让你把正式的接口/数据定义复制粘贴进设计文档 —— 它们冗长、细节无关，而且很快会过期」**。

### 铁律 3：状态不进规格，历史不进正文

| 内容 | 该在哪 |
|---|---|
| 「做到哪了」「已落地」「还剩 3 项」 | 状态文件（本项目是 `STATUS.md`） |
| 「原来是 A，10-15 改成 B」 | **哪里都不写** —— git blame 就是答案 |
| 「待确认」 | 待确认清单（单一处，带编号） |
| 契约：DDL / 接口 / 枚举 / 红线 / 验收标准 | 规格正文 ✅ |

**为什么**：带日期的进度句一定会过期，而过期后没人删。**写前自问**：这句会不会在下一次提交后变成假话？会 → 换地方。

**反例识别**：正文里出现 `2026-10-15 新增`、`原写 X → 改为 Y`、`★`、`已落地`、`本期需补` —— 都是腐烂迹象。

### 铁律 4：「为什么」写在被解释的东西旁边

不要为「为什么这么定」单独开一个流水账文件（CHANGELOG 类型）。理由应该是**读那个东西时自然碰到**的：

- 列为什么要允许 NULL → 写在**那一列的说明**里
- 接口为什么要合并 → 写在**那个接口的契约段**里
- 这个奇怪的判据为什么这么定 → 写在**那段代码的注释/docstring 里**

单独的变更日志的问题是：它复述事实（重复劳动）、会与正文冲突（两处都是「权威」）、没人读（决策者当时在场）。

> 想保留决策史时用 **ADR**：一条决策一个文件、只记 context / decision / consequences / 备选项，**状态为 superseded 时链接到新 ADR，永不改旧的**（Fowler）。ADR 的定位是「决策记录」，不是「变更日志」。

### 铁律 5：版本化文件 > 版本化文档

`v1.1 草稿`、`v2.0 评审版`、`最终版_final` —— 这些都是反模式。**用 git 版本化**，文档本身只写**当前有效**的口径。

一个特例：**如果文档已经转正生效，就把抬头从「草稿·待确认」改掉**。留着「草稿」而全项目当权威引用，等于给自己留了一个「以后可以不算数」的借口 —— 本项目踩过。

## 2. 一个事实写在哪：分层地图

按**读者需要它来解决什么**分层，不按「文件的逻辑结构」分层。

| 层 | 回答什么 | 何时读 |
|---|---|---|
| 事实源（外部快照） | 需求原话、原型、排期 | 有争议时回原处 |
| **数据模型** | 表长什么样、枚举有哪些值 | 建表/加列/写查询 |
| **接口契约** | 路径、入参、响应、错误边界 | 写调用方或实现方 |
| **验收基线** | 什么算做对了（可测的断言） | 写测试 / 判定完成 |
| **待确认清单** | 什么还没定、卡在谁那里 | 动手前扫一眼，避免实现未决分支 |
| 规范（命名/路由/审计列） | 怎么写才一致 | 起新模块时 |
| **状态** | 做到哪了 | 问进度时，**只有一处** |

**上下游交互文档的额外规则**：一份只写「对方要做什么」和「边界」，**契约本身指向接口契约文档**。不要把请求/响应示例抄进对外文档 —— 那会变成两个会漂的副本，对方按旧的实现了你都不知道。

## 3. 减重流程：文档已经太重了怎么办

Google 的建议：**Minimum Viable Documentation** —— 一小份新鲜准确的文档，胜于一大堆状态各异的「文档」。文档要像盆景一样经常修剪。

按顺序做，每一步都跑一次校验脚本（有的话）：

1. **先杀整块重复层** —— 找出「记录覆盖关系」「记录变更史」「罗列接口清单」这类纯粹派生出来的文件，整层删掉。它们的价值已被代码/测试覆盖。
2. **同一事实合并到权威处** —— 逐条 `grep` 高频事实（某个开关、某个时刻、某个枚举），只留最权威的一份，其余改引用。
3. **删已关闭项的叙述** —— 待确认清单里「已解决」的条目压成一行结论，长篇论证删掉（结论已在它落地的文档里）。
4. **删划线死行** —— `~~删除线~~` 的整行是纯负担，删掉。
5. **删「考古」段落** —— 「原来是 X，改成 Y，因为…」在正文里一律删，现行口径直接写。
6. **删「本期需补」「待补」这类进度列** —— 进度归状态文件。
7. **合并对外文档里的契约副本** —— 指向权威契约。

**判据（每份文件问一遍）**：如果删了它，谁会缺什么具体信息？答不出具体的人 + 具体的信息 → 删。

**Google 的默认策略**：拿不准就删。删错了 git 里有，恢复很便宜；留着错的会误导人。

### 3.1 删掉「派生台账」之后，怎么补回它原来提供的信息

这是减重里唯一需要动脑的一步。台账（如「BDD → 测试」覆盖表）删掉后，那个「一眼看出哪些没验」的能力会丢。**用脚本重建，不要用手抄重建**：

1. **在真源里打标记**：让每个测试在 docstring 首行或函数上方注释里写下它覆盖的编号（`BDD 3.7：…` / `# BDD: 5.7`）。标记跟着测试走，测试删了标记自动消失。
2. **校验脚本双向核**：
   - 标记指向不存在的编号 → **报错**（悬空引用）
   - 定义了但没有任何标记、**且没声明豁免** → **警告**（真缺口：可能漏写测试，也可能该补豁免）
3. **豁免要有清单**：设计文档末尾放一张「本期不验」表，**逐条**写编号 + 为什么。「本期不验（范围已定）」这种笼统写法要把编号拆成独立行 —— 否则脚本识别不到（本项目实测踩过）。

**关键点**：豁免清单里「为什么」的判据必须是**现在仍然成立的事实**。如果一条 BDD 的前置在实现里根本不存在了（例：「查重异常 = 不创建」，但建线索阶段压根不查重），那不是「本期不验」，是**这条 BDD 该重写或删掉**。

### 3.2 补标记的操作姿势

别用正则盲扫「`def test_` 后面的 block」。正确做法：

1. 从**旧台账备份**里取权威映射（那是唯一验证过的人工判定），不要自己猜哪条测试对应哪条 BDD。
2. 只给**缺标记**的补，已有标记的一律不动 —— 尤其是函数上方的 `# BDD: 5.7` 注释，它可能离 `def` 好几行，粗暴插入会造出重复标记。
3. 补完**跑一遍测试**（改的是 docstring，正常不该有影响，但要确认），再跑校验脚本。
4. 函数已改名/已删的映射要单独处理 —— 台账会指向不存在的函数，这是台账腐烂的直接证据。

## 4. 反模式清单（见到就改）

| 反模式 | 症状 | 改法 |
|---|---|---|
| **派生台账** | 手写的「需求→测试」覆盖表、手写的字段清单 | 删除；需要就让它从代码/测试生成 |
| **变更流水账** | CHANGELOG 越写越长，每条几百字 | 删；理由写进被解释的对象旁边；要决策史用 ADR |
| **状态散落** | 图里画着「已完成」、卡头写「零代码」 | 状态只留一处 |
| **进度列** | 表格里「本期需补」「是否已做」 | 删列 |
| **句子里塞历史** | 「（2026-10-15 起改为…）」 | 删括注，只写现行 |
| **同一契约多份副本** | 接口示例在 3 份文档里各写一遍 | 留一份权威，其余引用 |
| **草稿永久化** | 抬头写「草稿·待确认」但全项目按它实现 | 转正或删掉 |
| **为未来预留** | 「待确认项」写了 2000 字 | 结论一行 + 卡在谁那里 |
| **手工路径清单** | 路由规范文档里手抄 16 条接口路径 | 指向接口总表 |
| **形容词化验收** | 「性能良好」「体验流畅」 | 改可测断言，或删除 |

## 5. 写之前的自检清单

新建/修改任何设计文档前，逐条回答：

- [ ] 读者是谁？（写出具体角色，不是「团队」）
- [ ] 这条信息在代码里读得到吗？读得到 → 别写
- [ ] 这句话 `grep` 过了吗？别处已有 → 引用或改那一处
- [ ] 它会不会一个月后就过期？会 + 读者少 → 写进代码注释
- [ ] 我是在写**契约**还是**状态**？状态 → 状态文件
- [ ] 我是在写**现行口径**还是**变更史**？变更史 → git blame
- [ ] 引用到的路径/表名/接口真的存在吗？（跑校验脚本，别靠记忆）

## 6. 校验机制：让机器抓漂移

人靠不住，必须有脚本。最小可用的三道门：

| 门 | 核什么 | 例子 |
|---|---|---|
| **生成块** | 手写表格 vs 代码是否同步 | 接口字段表由代码生成，脚本检测过期 |
| **事实一致性** | 文档里出现的路径/表名/测试名在真源里存不存在 | 起 app 拿 OpenAPI；导 models 拿表名；`pytest --collect-only` 拿用例名 |
| **叙述** | 规格正文里有没有进度句与考古句 | 正则匹配「日期 + 已落地/已完成」 |

**关键**：校验脚本报出来的东西必须修，不能进白名单就算了 —— 白名单是漂移的蓄水池。

## 7. 已知的取舍（本 skill 不假装这些没代价）

| 取舍 | 代价 | 为什么还是这么选 |
|---|---|---|
| 删掉「需求→测试」覆盖表 | 不再有一页看清「哪些还没验」 | 台账会过期，而测试跑不通过会立刻炸。用测试标记代替台账 |
| 删掉变更日志 | 追溯「为什么当初这么定」要靠 git log | 变更日志读的人少、写的成本高、且必然与正文冲突。真的需要时补 ADR |
| 「为什么」散落在各处 | 想纵览所有决策理由要到处翻 | 但每一处都**在需要它的时候出现**。集中版的代价是所有地方都要维护 |
| 状态只有一处 | 别人不知道去哪找 | 入口文档只写一句话指向它 |

## 参考

- Google [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)：强调 trade-offs 与 alternatives，明确「别把接口/表结构复制进文档」「如果只是实现手册就不必写文档」「10–20 页是上限，超出就拆分」
- Google [Documentation Best Practices](https://google.github.io/styleguide/docguide/best_practices.html)：Minimum Viable Documentation / Update Docs with Code / **Delete Dead Documentation**（"Default to delete"）/ Duplication is Evil
- [Diátaxis](https://diataxis.fr/)：按读者需要分四类（tutorial / how-to / reference / explanation），不同类型不能混写。**explanation 讲理由，reference 只陈述事实** —— 本项目「规格 vs 理由」分离的理论依据
- [Martin Fowler · Architecture Decision Record](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html)：一条决策一个短文件，只记 context / decision / consequences / 备选项；**accepted 后永不修改，被取代时新建并链接**
- [adr.github.io](https://adr.github.io/)：ADR 模板族（Nygard / MADR / Y-Statement）；MADR 特别强调「备选项与取舍是理解决策理由的关键」
