# 案例：一份 442 KB 的 spec 是怎么变成负担的

> 锐正募资模块（2026-10-07 ~ 10-28，单人前后端，21 天）。
> 数据全部来自当时的真实文件与 grep，不是估算。

## 起点：文档结构

```
rzdoc/
├── Agents.md           15 KB   项目入口
├── README.md            6 KB   导航
├── STATUS.md           36 KB   状态
├── CHANGELOG.md        80 KB   变更日志（37 条，平均 724 字/条）
├── docs/design/       168 KB   规格（00/01/07/09 + 06/01~04）
└── docs/task/          30 KB   任务卡 13 张（「BDD → 测试」覆盖表）
                        442 KB
```

配合的校验脚本：`specgate.py` 三道门（生成块 / 事实一致性 / 叙述），`specgen.py` 从代码生成字段表。

## 三个负作用，按危害排序

### 负作用 1：变更日志复述事实，制造第二权威

`CHANGELOG.md` 里一条典型的记录（v1.106，875 字）讲「渠道弹窗删掉频率配置」。同一件事当时同时存在于：

| 位置 | 内容 |
|---|---|
| `CHANGELOG.md` v1.106 | 完整的决策叙述 |
| `design/09` S15 | 结案结论 |
| `design/07` §2.1 | `frequency` 列的说明 |
| `design/06/01` §2 | 频率不可配 |
| `design/06/04` ID9/ID10 | 前端不消费 |
| `design/01` BDD 1.6 | 验收断言 |
| `STATUS.md` §5.2 | 进度 |

**改这一件事要动 7 处。** 漏一处的后果不是「文档旧了」，是**两处都自称权威、互相矛盾**。

而且这个 CHANGELOG **从来没进过 git**（`git status` 显示 `??` 未跟踪）。一个不受版本管理的「历史记录」，本身就是自相矛盾的。

### 负作用 2：派生台账比它记录的东西更容易过期

`docs/task/` 13 张卡片，每张是「BDD 编号 → 覆盖它的测试函数全名」的手工表。实测：

- `design/01` 定义 **83** 条 BDD
- 测试源码里带 `BDD x.y` 标记的有 **36** 条（43%）
- 台账说「都挂上了」，但那 47 条里多数其实有测试，只是没打标记

**台账与真实覆盖率脱节，且没有任何机制发现这个脱节** —— 它是手抄的，没有上游真源。

而真正的验收信号（`pytest` 通过 / 不通过）从来不需要这张表。

### 负作用 3：状态写进规格，必然过期

`design/00` 抬头写着「**v1.1 草稿 · 待确认**，尚未纳入工作流红线」，但全项目 4 处按它当权威引用、代码全部照它实现。

同一份文件 §5 有一列叫「**本期需补**」：

| 规范条目 | 现有落点 | 本期需补 |
|---|---|---|
| 审计 `created_by`/`updated_by` | 无 | 扩展 `TimestampMixin` |

「无」「本期需补」在写完当天就已经不成立了（代码里早就有）。这就是**进度写进契约**的必然结果。

## 减重后

| 动作 | 减掉 |
|---|---|
| 删 `CHANGELOG.md` | −80 KB |
| 删 `docs/task/` 整层 | −30 KB |
| `09` 已结项一行化 + 删尾部实测小作文 | −45 KB（63 → 18 KB） |
| `06/02` §4.1 请求响应示例改指向权威契约 | −3 KB |
| `06/02` §4.2 删 14 行 `route` 码表（权威在 `07`） | −0.7 KB |
| `06/02` §6 删 15 条划线死行 + 重排 | −2 KB |
| `00` §6 删（5 条 S 已在 `09` 登记） | −0.7 KB |
| `00` 删手工接口一览（16 条路径，权威在 `06/04`） | −2.3 KB |
| `00` §5 删「本期需补」列 | −0.4 KB |
| 6 份文档删末尾「变更记录」节（内容全是「历史已删，见 CHANGELOG」） | −0.7 KB |
| **合计** | **442 → 266 KB（−40%）** |

## 删掉之后丢了什么：如实记录

| 丢掉的 | 真的损失 | 补偿 |
|---|---|---|
| BDD → 测试 的映射表 | 不再有一页看清「哪些还没验」 | 测试跑挂了会立刻炸；需要时 ``grep -r "BDD 5\." tests/`` 自己拼 |
| 变更日志的 37 条决策史 | 追溯「为什么当初这么定」要靠 `git log` | 理由本身还在被解释对象的旁边（列说明 / 契约段 / 迁移 docstring） |
| 「改一处连带改哪几份」清单 | 得靠自己 `grep` | 校验脚本会报失效引用 —— 这才是真兜底（清单本身早就没人维护，成了空引用） |

**没有损失**的：所有契约（DDL / 接口 / 枚举 / 验收断言）一字未动。删的全是复述、台账、进度、考古。

## 从这次经历提炼出的判据

1. **能 grep 到第二次的，就是重复**。重复必有先后，先后必有矛盾。
2. **手抄的东西一定会漂**，无论抄得多认真。能生成就生成，不能生成就指向源。
3. **带日期的进度句 100% 会变成假话**。写的时候觉得「记录一下」，一个月后它就是负债。
4. **默认删**。删错的恢复成本（git）远低于留着错的误导成本。
5. **校验脚本是唯一靠得住的兜底**。人写的清单会忘，脚本每次跑。
6. **对外文档只写「对方要做什么」，契约指向权威处**。给对方抄一份请求示例，等于答应维护两个副本。
