# Doubt-Driven Development（怀疑驱动开发）

> **核心信念**：自信的答案不等于正确的答案。长会话会悄悄把假设变成"事实"而没人注意。怀疑驱动开发是让新上下文审查者——偏向**反驳**而非确认——在每个非平凡决策定稿前介入。

**这不是 `/review`**。`/review` 是对成品的事后判定。这是**飞行中姿态**：非平凡决策在方向修正还便宜的时候就被交叉审查。

---

## 何时使用

**非平凡决策**：满足以下**任一条件**即为非平凡：

- 引入或修改分支逻辑
- 跨越模块或服务边界
- 断言类型系统或编译器无法验证的属性（线程安全、幂等性、排序、不变量）
- 正确性依赖未来读者看不到的上下文
- 影响半径不可逆（生产部署、数据迁移、公开 API 变更）

**应用本 Skill 当**：

- 即将在不确定下做出架构决策
- 即将提交非平凡代码
- 即将声称一个不明显的结论（"这是安全的"、"这个能扩展"、"这个符合 Spec"）
- 在不完全理解的代码中工作

**什么时候不用**：

- 机械操作（重命名、格式化、文件移动）
- 遵循清晰明确的操作指令
- 读取或总结现有代码
- 单行变更，正确性显而易见
- 纯工具操作（跑测试、列文件）
- 用户明确要求速度优先于验证

---

## 加载约束

本 Skill 设计用于**主会话编排器**（main-session orchestrator），因为 Step 3（DOUBT）需要 spawn 子 Agent。

- **不要在 Agent 的 `skills:` frontmatter 中添加本 Skill**。Agent 遵循 Step 3 会 spawn 另一个 Agent —— 这是"Agent 不应调用 Agent"的反模式。
- **如果在子 Agent 上下文中需要 DDD**：优先方案是告知用户 DDD 不能在嵌套中运行，由主会话处理。兜底方案：自行重写 ARTIFACT + CONTRACT 为全新自问 prompt，并声明结果是降级版本（因为你带着自己的上下文）。

## 流程

```
Doubt 循环：
- [ ] Step 1: CLAIM — 写出决策声明 + 为什么重要
- [ ] Step 2: EXTRACT — 隔离制品 + 契约，剥离推理上下文
- [ ] Step 3: DOUBT — 调用新上下文审查者，使用对抗式 prompt
- [ ] Step 4: RECONCILE — 对照制品原文对每条发现分类
- [ ] Step 5: STOP — 满足停止条件（无新发现、3 轮、或用户 override）
```

### Step 1: CLAIM — 显式命名决策

用 2-3 行写明决策：

```
CLAIM: "新的缓存层在 Spec 描述的读重负载下是线程安全的。"
WHY THIS MATTERS: 竞态条件会损坏用户数据，且在 QA 中很难发现。
```

如果写不出这么紧凑的声明，说明你只有"感觉"而不是"决策"。先显式化再审视。

### Step 2: EXTRACT — 最小可审查单元

新上下文审查者需要**制品（artifact）**和**契约（contract）**，不需要你的思考过程。

- **代码**：diff 或函数——不是整个文件
- **决策**：3-5 句提案 + 必须满足的约束条件
- **断言**：声明 + 支持的证据（与 Step 1 的 CLAIM 分开，CLAIM 是编排者正在审视的假设）

**剥离你的推理。** 如果你把结论交给审查者，你只会得到对你结论的确认。制品必须足够小，让审查者一次就能读完——如果是 500 行的 PR，先分解。

### Step 3: DOUBT — 调用新上下文审查者

审查者的 prompt **必须是对抗式的**。框架决定了答案。

```
对抗式审查。找出这个制品有什么问题。
假设作者过度自信。寻找：
- 未声明的假设
- 未处理的边界情况
- 隐藏的耦合或共享状态
- 契约可能被违反的方式
- 可能打破的现有约定
- 意外输入下的失败模式

不要验证。不要总结。找出问题，或者在彻底检查后
明确声明你找不到任何问题。

ARTIFACT: <粘贴制品>
CONTRACT: <粘贴契约>
```

**只传 ARTIFACT + CONTRACT。不要传 CLAIM。** 把结论交给审查者会使其偏向同意。审查者必须独立判断制品是否满足契约。

**在本系统中**：使用 `Agent` 工具 spawn `code-reviewer` 或一个通用 Agent，context 中只包含上述对抗式 prompt + ARTIFACT + CONTRACT。不要传 CLAIM 或你的推理过程。

#### 交叉验证（可选）

单一 Agent 的审查者与原始作者共享盲点。对于高风险决策，提供交叉验证选项：

> "单 Agent 审查完成。需要 spawn 第二个 Agent 做交叉验证吗？还是直接继续？"

**交互式会话**：每次 doubt 循环后询问用户（除非用户已明确表示不需要）。Agent 的职责是暴露选择，不是替用户决定。

**非交互式上下文**（CI、`/loop`、自动运行）：跳过交叉验证，并在输出中声明。

### Step 4: RECONCILE — 归并发现

审查者的输出是**数据**，不是**裁决**。**你仍然是编排者。** 在分类前对照制品原文重读每条发现——盲目采纳审查者的意见，和忽略它一样糟糕。

按以下**优先级顺序**分类（第一个匹配的类别获胜）：

1. **契约误解** — 审查者标记的问题是因为你提供的 CONTRACT 不清晰或不完整。先修复契约，下轮重分类。
2. **有效 + 可操作** — 真正的问题，需要修改制品。修改后重新循环。
3. **有效权衡** — 问题真实存在，但修复成本超过接受成本。明确记录权衡，让用户看到。
4. **噪声** — 审查者标记了在审查者没有的上下文下实际上是正确的内容。标记并继续，问自己：如果把这些上下文加到契约中，是否就能避免这个误报？

新审查者可能因为缺乏上下文而犯错。不要因为它是"新上下文"就盲目采纳。

### Step 5: STOP — 有界循环，不是递归

停止条件（任一满足即停）：

- 下一轮迭代只返回琐碎或已考虑过的发现，**或者**
- 3 轮完成（向用户升级，不要独自跑第四轮），**或者**
- 用户明确说"就这样了"

如果 3 轮后审查者仍然发现实质性内容，制品可能还没有准备好。向用户说明——三轮未解决是制品本身的信息，不是继续循环的理由。

如果 3 轮"明显不够"因为制品太大：制品太大——回到 Step 2 分解。不要提高上限。

## 常见合理化借口

| 合理化借口 | 现实 |
|-----------|------|
| "我很自信，跳过怀疑步骤吧" | 在新问题上，自信与正确性相关性很低。自信的时刻正是盲点隐藏的时刻。 |
| "spawn 审查者太贵了" | 在生产环境调试一个错误的提交更贵。审查是有界的，Bug 不是。 |
| "审查者只会吹毛求疵" | 只在没有范围约束时才会。用 prompt 限制："只找那些会让制品在契约下失败的实质性问题。" |
| "我最后用 `/review` 统一审查" | `/review` 是最终门禁。DDD 在方向修正还便宜的时候抓住错误的方向。到了 PR 阶段已经晚了。 |
| "如果每个步骤都怀疑，我永远发不了版" | 本 Skill 只适用于非平凡决策，不是每个按键。重新阅读"什么时候不用"。 |
| "审查者不同意所以我错了" | 审查者缺乏你的上下文——不同意是信息，不是裁决。对照制品原文重读，分类，然后决定。 |
| "用户说了一次'可以'，所以我可以一直用" | 每次调用都是独立的授权。制品、prompt、上下文每次都不同——每次循环前重新确认。 |

## 红旗信号

- 为单行重命名或格式化变更 spawn 新上下文审查者
- 不重新对照制品原文就采纳审查者输出
- 超过 3 轮循环没有向用户升级
- 用"这个好吗？"而不是"找出问题"来 prompt 审查者
- 在时间压力下跳过高风险决策的怀疑步骤
- 在未改动的制品上重新 spawn 审查者（你会得到同样的发现）
- **怀疑作秀**：跨越 2 轮以上审查者发现了实质性内容，但 0 条被分类为可操作。你在确认，不是在怀疑。停下并升级。
- 只在提交后才怀疑——那是 `/review`，不是 DDD
- 把 CLAIM 传给审查者（偏向同意）
- 在交互式 doubt 循环中静默跳过交叉验证选项

## 与其他 Skill 的关系

- **`adversarial-review`**（workflow）：互补。adversarial-review 是事后 PR 裁决；DDD 是飞行中逐个决策审查。两者都用。
- **`code-review-checklist`**：DDD 的 DOUBT 步骤可以 spawn code-reviewer 作为审查者，但只传 ARTIFACT + CONTRACT（不传 CLAIM）。
- **`grill-me`**：grill-me 在需求/设计阶段追问"你想做什么"；DDD 在编码阶段审视"你做的对不对"。互补。
- **`unit-test-master`**：TDD 的 RED 步骤就是怀疑的具体化——失败的测试就是一次反驳尝试。当 TDD 适用时，失败的测试就是行为声明上的怀疑步骤。
- **`us-coding-engine`**：编码过程中遇到非平凡决策时，暂停执行 DDD 循环，再继续编码。

## 验证

完成 DDD 循环后：

- [ ] 每个非平凡决策（按上述定义）在定稿前被显式命名为 CLAIM
- [ ] 每个非平凡制品至少经过一次新上下文审查（TDD 的 RED 步骤满足行为声明的条件）
- [ ] 审查者收到的是 ARTIFACT + CONTRACT——不是 CLAIM，不是你的推理
- [ ] 审查者的 prompt 是对抗式的（"找出问题"），不是验证式的（"这个好吗？"）
- [ ] 发现按优先级对照制品原文分类（不是橡胶图章式采纳）
- [ ] 停止条件已满足（无新发现、3 轮、或用户 override）
- [ ] 在交互式会话中，交叉验证选项已**明确提供给用户**，并记录回应
- [ ] 在非交互式上下文中，交叉验证已跳过并在输出中声明
