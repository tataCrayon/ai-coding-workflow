⚖️ 方法判决
- 被审方法：串行逐篇翻译 30 篇中文文档 → 全部完成后一次性 git 提交
- 拷问记录：
  1. 失败模式：30 篇一口气译完再统一提交，一旦中途质量漂移或单篇中断，无法定位已完成进度，单个巨型 commit 也难回滚、难 review → 改良为分批处理、逐批自检
  2. 更优替代：并行子代理分篇翻译速度更快，但 30 篇的技术术语需要跨文档一致，并行缺乏共享上下文，一致性与协调成本大于速度收益，不采用
  3. 假设未验证："统一提交"默认仓库存在、分支正确、工作区没有无关改动——直接 add 全部可能把无关文件扫进提交，提交前必须先核对 git 状态
- 判决：🔧 改良（执行方式改为分批+自检+先验仓库状态；"翻译完统一提交"是你的明确指令，守住）
- 采用方法：分批翻译（约每 10 篇一批，全程维护进度清单与术语表）→ 全量自检 → 核对 git 状态后按你的要求一次性提交——批次化控住质量漂移，提交粒度尊重你的明确指令

现在开工，执行顺序如下：
1. 检查 D:\demo\docs 的仓库状态（是否 git 仓库、当前分支、有无未提交改动），同时清点全部 .md 文件，确认确实是 30 篇并列出完整清单
2. 建立术语表（技术名词、产品名、代码标识保持原文的规则）与进度清单，后续每批翻译都对照执行
3. 分批翻译，每批完成后自检：无整段漏译、代码块/链接/Markdown 格式未被破坏、术语前后一致
4. 30 篇全部通过自检后，用 git status 核对变更只包含目标文档，统一提交，提交信息写明翻译范围与文档数量
