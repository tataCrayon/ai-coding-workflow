# 可行性评估：AI 自动读 CI 失败日志 → 生成修复 PR

## 一句话结论

这个方向**有人做过、且已经比较成熟**——它是近两年 AI 编程领域最热门的落地场景之一（学术上叫 LLM-based Automated Program Repair，工业上叫 "agentic bug fixing"）。但成熟的最佳实践指向一个关键修正：**"全自动合并 PR" 不成熟，"AI 生成修复 + 人审合并" 非常成熟**。你的方案应该按后者的形态来做。

---

## 1. 已经做过的人和现状

**学术基准与系统：**
- **SWE-bench**（Princeton，2023）：用 2294 个真实 GitHub issue + PR 构建的基准，就是"给仓库和故障描述，产出补丁"这个任务的标准化评测。发布当时最强模型（Claude 2）只能解决 **1.96%** 的问题；到 2025 年，前沿模型/系统在 SWE-bench Verified（人工校验过题目质量的子集）上已能解决 **约一半以上** 的实例。两年内从 <2% 到 >50%，这是该方向成熟度跃升的最直接证据。
- **SWE-agent、AutoCodeRover**（2024）：证明了"结构感知的代码检索 + 迭代定位 + 补丁生成"的 agent 范式有效。AutoCodeRover 在 SWE-bench Lite 上约 19%，**平均每个 issue 成本 $0.43**——成本完全不是瓶颈。
- 注意一个重要的实证结论：SWE-bench 后续分析发现，未解决的案例中相当比例是**问题描述本身含糊**（连人类标注员都写不出补丁），而不是模型能力不足。这对你的启示是：**输入信号的质量（日志+上下文）直接决定上限**。

**工业产品（和你的想法几乎一模一样）：**
- **GitHub Copilot coding agent**（2025 GA）：把 issue 指派给 Copilot，它在云端环境里自己复现、改代码、跑测试、开 draft PR，人审后合并。这是目前最接近你设想的官方形态。
- **Cursor Bugbot / CodeRabbit**：聚焦 PR 审查阶段的自动发现问题。
- **Devin**（Cognition）：宣称端到端修 bug，但公开可复现的评测口碑一般，说明"全自主"仍是营销强于实证的部分。
- **Meta TestGen-LLM**（ICSE 2024，重要参考）：用 LLM 自动补测试，靠**多层过滤管线**（能编译 75% → 稳定通过 57% → 确实提升覆盖率 25%）保证只有可验证改进的产出才进入人工评审，最终工程师**接受率 73%**。这是"AI 产出 + 硬性自动过滤 + 人审"模式的黄金案例。
- 反面教材：**Amazon CodeGuru Reviewer** 只做建议不做修复，且 AWS 已于 2025 年 11 月关闭新接入——纯"提示型"工具价值有限，被能直接产出可运行补丁的 agent 取代了。

## 2. 理论支持

- 这个任务在软件工程研究里有完整谱系：**自动程序修复（APR）**，从经典的 GenProg、基于频谱的故障定位（SBFL）到 SemFix，再到 LLM 时代。CI 失败日志 + 失败测试天然是**强故障定位信号**，AutoCodeRover 已证明有测试失败信息时利用它能显著提升修复质量。
- 理论上成立的另一个原因：修复 PR 有**廉价、客观、可自动执行的验证器**——重跑 CI。这使得整个循环可以形式化为"生成 → 验证 → 迭代"，是 LLM agent 最擅长的闭环结构（相比"生成一个产品需求"这类无验证器的任务）。

## 3. 对你方案的关键可行性切分

CI 失败不是一个均质问题，成功率差异极大：

| 失败类型 | 自动修复可行性 | 说明 |
|---|---|---|
| lint / 格式 / 静态检查 | 极高 | 确定性修复，甚至不需要 LLM |
| 依赖升级、API 签名变更、快照/期望值过期 | 高 | 模式固定，日志信息充足 |
| 编译错误、单点逻辑 bug（有失败测试定位） | 中高 | SWE-bench 型任务，当前主流能力区 |
| flaky test | 中 | 需要先分类（重试确认），"修复"常是隔离/重跑而非改代码 |
| 环境/基础设施失败（runner 挂了、网络超时） | 不适用 | 正确动作是重跑，不是 PR |
| 跨服务、缺复现手段的复杂 bug | 低 | 目前人也要半天起步，别指望自动 |

**所以第一个模块应该是失败分类器，而不是修复器。** 直接对所有失败生成 PR 会被大量噪声 PR 反噬（工程师很快会无视你的 bot）。

## 4. 推荐架构（业界收敛出的最佳实践）

1. **触发与分类**：CI 失败事件 → 抓日志 → 分类（环境/flaky/构建/测试/逻辑），只放行可修复类。
2. **上下文构建**：失败日志 + 本次变更 diff + 失败测试 + 相关源文件（结构感知检索，别把整仓喂给模型）。
3. **沙箱复现**：在隔离环境重跑失败用例，确认能复现——复现不了就降级为"诊断报告"而非修复 PR。
4. **生成补丁 → 本地验证闭环**：改代码 → 重跑失败测试 + 全量回归，不通过就迭代（设上限，如 3 轮）。
5. **硬性过滤门**（学 TestGen-LLM）：diff 最小化、无跳过/删除测试的行为（这是 LLM 最常见的作弊方式）、无敏感文件变更。
6. **产出 draft PR**：附根因分析、修改说明、验证证据，**强制人工 review 才能合并**，加 branch protection 禁止 bot 直推。
7. **度量闭环**：统计 PR 接受率、修复后回归率。接受率是唯一的生死指标（Meta 的经验：73% 接受率才值得推广）。

## 5. 主要风险

- **奖励作弊**：模型可能改测试而不是改代码来"让 CI 变绿"——必须有第 4 步的过滤器。
- **噪声疲劳**：低质量 PR 轰炸会让团队永久弃用这个 bot，宁缺毋滥。
- **安全**：沙箱执行 + 禁止 bot 持有合并权限 + 密钥扫描。
- **日志质量**：很多 CI 日志被截断/乱序，前期值得投入日志预处理。

## 6. 建议的落地路径

不要一上来做全类型。MVP：**选你们 CI 中占比最高的一类确定性失败（通常是依赖/快照/lint 或某类单测失败）→ 只做"分类+复现+修复+draft PR"最小闭环 → 跑两周看接受率**。接受率 >50% 再扩类别。同时先试用现成方案（Copilot coding agent 或 Claude Code / SWE-agent 接你们 CI webhook）做基线对比——如果现成工具已解决 70%，你们的差异化空间就在"对自家 CI 失败模式的分类与上下文工程"上，这部分恰恰是最有壁垒的。

**总结**：方向成立、理论有支撑（APR + SWE-bench 两年从 2% 到 50%+ 的曲线）、成本可忽略、工业形态已收敛到"沙箱复现 + 自动验证 + 人审 PR"。真正决定成败的不是模型，而是失败分类的准确率和过滤门的严格程度。
