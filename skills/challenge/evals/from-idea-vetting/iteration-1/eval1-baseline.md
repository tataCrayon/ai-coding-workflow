# 评估：自研 Markdown 转微信公众号排版工具

**先说结论：方向靠谱，但"从零自己写"大概率不划算。** 这个领域不是无人区，而是已经非常拥挤的成熟赛道——仅我查到的活跃开源方案就有十几个，其中最头部的项目上周还在更新。你的真实需求（团队技术文档一键发公众号）大概率可以通过"选一个现成工具 + 做少量集成"来满足，自研的价值只应体现在团队文档流程的对接层，而不是排版引擎本身。

## 一、有没有人做过？有，而且很多

我刚在 GitHub 上实际检索了一遍（截至 2026-09），按相关度给你列几个代表性的：

| 项目 | Star | 活跃度 | 定位 |
|---|---|---|---|
| **doocs/md** | ~13,300 | 非常活跃（本周有提交） | 微信公众号 Markdown 编辑器，支持自定义主题样式、图床、AI 助手，Web 端即用 |
| **wechatsync/Wechatsync** | ~6,300 | 活跃 | 浏览器插件，一键同步文章到公众号/知乎/掘金/WordPress 等多平台 |
| **mdnice/markdown-nice** | ~4,700 | 已停更（2023 底） | 经典的主题排版编辑器，"排版即Nice" |
| **lyricat/wechat-format** | ~4,500 | 维护中 | Markdown → 微信特制 HTML，纯前端、可自部署 |
| **geekjourneyx/md2wechat-skill** | ~3,600 | 非常活跃（本月有提交） | **CLI 工具，"一键排版发布到公众号"**：40+ 主题、AI 配图、批量发布、多账号管理，还配套了 MCP Server、Obsidian 插件、飞书文档版本 |
| **caol64/wenyan-mcp** | ~1,300 | 维护中 | 写作/发布工作台，提供 MCP 接口给 AI Agent 用 |

注意 md2wechat-skill 这一家：CLI + 多账号 + 批量发布 + MCP + 飞书文档直转，这基本就是你描述的"团队沉淀文档一键发公众号"的完整形态。也就是说，**你想做的核心功能已经有人做完了，而且做得比较细。**

## 二、这个想法里"靠谱"和"不靠谱"的部分

**靠谱的部分（需求真实存在）：**
- 技术团队"文档沉淀在内部（Git/飞书/Confluence），对外要发公众号"是普遍痛点，公众号后台自带的编辑器对 Markdown/代码块/图片的支持确实很差。
- 团队文档往往有固定的品牌样式（字体、配色、代码主题、文末引导），这个"统一排版规范"的诉求是现成通用工具覆盖不完全的。

**不靠谱的部分（自研的隐性成本）：**
1. **排版引擎比看起来难做对。** 公众号会清洗 HTML：只接受内联样式，class/style 标签、position、伪类、部分 CSS 变量全被剥掉。要处理好嵌套列表、代码块高亮、表格、Mermaid 图转图片、公式，这些坑每一个现成项目都踩过了。
2. **发布 API 有硬门槛。** 公众号草稿箱/发布接口要求认证服务号、配置 IP 白名单，`freepublish` 发布能力对未认证或新账号受限；图片必须先上传到微信素材库（外链图片会被防盗链处理）。这些是合规与权限问题，写代码解决不了。
3. **自研 = 长期维护债。** 微信编辑器行为一变（历史上发生过多次），你的工具就静默坏掉。mdnice 停更后大量用户流失就是前车之鉴。两个人各花一周写的"临时脚本"，最后往往变成没人敢删的内部遗产。

## 三、我的建议：把自研预算砍到只剩"胶水层"

按这个顺序验证，大概率走不到自研那一步：

1. **先试现成方案（1 天）**：团队文档如果是 Markdown 存在 Git 里，直接试 `md2wechat-skill`（CLI、支持批量和多账号）或自部署 `lyricat/wechat-format` + 浏览器插件 Wechatsync。如果文档在飞书，它有现成的飞书版本。
2. **只定制主题，不造引擎（1-2 天）**：这些工具几乎都支持自定义 CSS 主题。把你们团队的品牌排版规范做成一个主题文件，这是性价比最高的"自研"部分。
3. **胶水层按需自研（3-5 天）**：如果现成工具唯一缺的是"从我们文档库自动拉取 → 转换 → 进草稿箱"，那就写一个薄脚本：调你们文档平台的 API 拿 Markdown → 调上面工具的转换/发布能力 → 失败时通知人审核。这个脚本几百行，坏了也好修。
4. **只有以下情况才考虑真正自研**：你们要的不是"发一篇公众号"，而是产品化能力（比如给多个团队/客户提供带审批流的发布平台）、或团队文档格式特殊到所有现成工具的主题系统都表达不了。即便如此，也应该基于 `doocs/md` 这类开源项目 fork 改造，而不是从 Markdown 解析器写起。

## 四、动手前建议先确认的几件事

- 你们公众号是**认证服务号还是订阅号**？没有认证的话，发布 API 这条路直接不通，只能"半自动"（工具生成带样式 HTML，人工粘贴），这会大幅改变选型。
- 团队文档的**源头格式**到底是什么？纯 Markdown 在 Git 里，还是飞书/Confluence 富文本？富文本转 Markdown 的损耗（图片、画板、代码卡片）往往是真正的难点。
- 发一篇的**全流程耗时**现在是多少？如果现状是"人工排版 40 分钟/篇、每周发 2 篇"，省一半时间就值得做胶水层；如果每周只发一篇且没人抱怨，这个想法可以先放一放。

一句话总结：**想法本身对应真实痛点，值得做；但"自己写一个排版工具"是错误的切分方式——引擎用开源的，主题自己做，只写连接团队文档库和发布流程的那层胶水。** 建议先花一天跑一遍 md2wechat 或 doocs/md，拿你们一篇真实技术文档试试效果，再决定要不要投入任何开发。
