# Change Documenter（变更留痕文档生成器）

> **核心定位**：基于 git diff 的标准化变更文档生成，附带回滚计划。
> 不仅"列出改了什么"，更要评估**"行为变化的影响范围和回滚路径"**。
> 金融系统变更必须可追溯、可回滚，文档是合规审计的关键依据。

---

## 一、执行流程

```
用户请求到达（已完成代码变更，需要留痕文档）
    ↓
Step 1: Git diff 收集 —— 读取变更范围的 git diff
    ↓
Step 2: 变更分析 —— 分类分析变更内容，识别行为变化
    ↓
Step 3: 风险评估 —— 评估变更风险等级，生成回滚计划
    ↓
Step 4: 文档生成 —— 按模板输出结构化变更文档
    ↓
Step 5: 输出 → 08-code-change-summary.md
```

---

## 二、Step 1：Git Diff 收集

### 2.1 确定变更范围

根据用户描述确定 diff 范围：

| 场景 | Git 命令 | 说明 |
|------|----------|------|
| 已 commit 但未 push | `git diff HEAD~1` | 最近一次提交的变更 |
| 多次 commit | `git diff HEAD~N` | 最近 N 次提交的变更 |
| 未 commit 的工作区变更 | `git diff` | 工作区暂存区差异 |
| 特定分支对比 | `git diff main..feature-branch` | 分支间全量差异 |
| 特定文件变更 | `git diff -- path/to/file` | 指定文件的变更 |

> 如果用户未指定范围，默认使用 `git diff HEAD~1`（最近一次提交）。
> 如果是跨多天多次提交的变更，建议用户指定 commit range 或分支对比。

### 2.2 Diff 信息提取

从 diff 中提取：

- **变更文件清单**：新增/修改/删除的文件列表
- **变更类型**：每个文件的变更类型（新增/修改/删除/重命名）
- **变更行数**：每个文件的增删行数统计
- **关键变更点**：识别方法签名变更、接口变更、配置变更等高风险改动

---

## 三、Step 2：变更分析

### 3.1 变更分类

将所有变更按以下维度分类：

| 类别 | 说明 | 示例 |
|------|------|------|
| 接口变更 | API 接口的新增/修改/删除 | 新增 /api/v1/order 接口 |
| 数据模型变更 | 表结构/Entity/DTO 的变更 | 新增 rwa_order 表 |
| 业务逻辑变更 | Service 层核心逻辑的变化 | 订单校验规则调整 |
| 配置变更 | 配置文件/环境变量的变化 | 新增 Redis 连接配置 |
| 依赖变更 | pom.xml/package.json 等依赖变化 | 新增 fastjson2 依赖 |
| 基础设施变更 | Filter/Interceptor/网关配置变化 | 新增鉴权拦截器 |

### 3.2 行为变化识别（核心能力）

重点识别**行为层面的变化**，而非仅仅是代码层面的改动：

```
问自己：这个变更让系统的行为发生了什么变化？
    ↓
对每个关键变更点：
- Before（变更前行为）：系统原来怎么做的
- After（变更后行为）：系统现在怎么做
- 影响：哪些用户/流程/接口受到影响
```

### 3.3 关键文件筛选

控制文档篇幅，只聚焦最关键的变更：

| 筛选规则 | 说明 |
|---------|------|
| 关键文件数量 | 3-10 个（超过 10 个时按影响度排序取前 10） |
| 行为变化条目 | 3-5 个（只记录最重要的行为变化） |
| 低风险变更 | 配置调整、注释修改、格式化等低风险变更合并为一条简述 |

---

## 四、Step 3：风险评估与回滚计划

### 4.1 风险等级判定

| 风险等级 | 条件 | 示例 |
|---------|------|------|
| 🔴 高风险 | 涉及资金流向、核心接口签名变更、数据结构破坏性变更 | 金额计算逻辑变更、主键策略变更 |
| 🟡 中风险 | 涉及业务逻辑调整、新增接口/表、鉴权变更 | 新增订单状态、调整校验规则 |
| 🟢 低风险 | 纯新增功能、配置调整、注释修改 | 新增查询接口、日志级别调整 |

### 4.2 回滚计划生成

对每个中高风险变更生成回滚方案：

| 回滚维度 | 内容 |
|---------|------|
| 回滚方式 | git revert / 手动修改 / 配置回退 |
| 回滚步骤 | 具体操作步骤（命令级别） |
| 回滚验证 | 回滚后如何验证系统恢复正常 |
| 回滚影响 | 回滚本身可能造成的副作用 |
| 数据回滚 | 涉及数据变更时的数据回滚方案（金融场景必须覆盖） |

> **金融铁律**：涉及资金/交易的变更，回滚计划必须包含**数据回滚方案**，不能仅靠代码回滚。

## 五、Step 4：文档模板

输出文件：`08-code-change-summary.md`

```markdown
# 变更留痕文档

## 1. 背景
- 变更原因（需求/修复/优化）
- 关联需求编号/链接
- 变更发起人

## 2. 变更范围
| 文件 | 变更类型 | 增删行数 | 变更简述 |
|------|---------|---------|---------|

### 2.1 关键文件（详细）
对每个关键文件（3-10个），列出：
- 变更内容摘要
- 变更意图
- 关联的其他文件

## 3. 行为变化（Before / After）
| # | Before（变更前） | After（变更后） | 影响范围 |
|---|-----------------|----------------|---------|
| 1 | 系统原行为描述 | 系统新行为描述 | 受影响的用户/流程/接口 |
| ... | ... | ... | ... |

## 4. 风险评估
| 变更项 | 风险等级 | 风险描述 | 影响面 |
|--------|---------|---------|-------|

## 5. 验证计划
- 功能验证：需验证的功能点列表
- 接口验证：需验证的接口列表
- 数据验证：需验证的数据一致性点

## 6. 回滚计划
| 变更项 | 回滚方式 | 回滚步骤 | 回滚验证 | 数据回滚方案 |
|--------|---------|---------|---------|-------------|

### 6.1 快速回滚命令
```bash
# 回滚到变更前的 commit
git revert <commit-hash>
```

## 7. 变更统计
- 变更文件总数：N
- 增加行数：+M
- 删除行数：-K
- 关键变更点：3-5
```

## 六、篇幅控制

| 控制项 | 限制 | 超限处理 |
|--------|------|---------|
| 文档总行数 | ~200 行 | 低风险变更合并简述，减少篇幅 |
| 关键文件详细条目 | 3-10 个 | 按影响度排序取前 10 |
| 行为变化条目 | 3-5 个 | 只记录最重要的行为变化 |
| 回滚计划条目 | 仅中高风险项 | 低风险变更无需回滚计划 |
