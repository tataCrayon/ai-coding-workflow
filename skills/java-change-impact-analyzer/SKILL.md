# Java Change Impact Analyzer

> **执行目标**：系统分析变更的影响范围，同时评估变更方案本身的设计质量。
> 不仅分析"变更波及哪些文件"，更评估"变更方案本身是否优雅"。
> 完整的代码美学标准见项目编码规范文档。

**铁律**：修改方法签名/参数/查询条件/业务逻辑前 → 先执行本 skill → 输出变更影响清单 → 再逐项修改。

---

## 触发时机

用户要求修改以下内容时**必须调用**：
- 方法签名（参数、返回值）
- 查询条件（SQL、持久化配置）
- 业务逻辑（Service、Manager）
- 接口定义（Controller、Facade、远程服务接口）
- 数据结构（DTO、VO、Request、Response、Entity）
- 架构相关：扩展点接口、策略组件、领域服务、插件实现

## 免分析条件（Fast Path）

当变更满足以下**全部条件**时，可跳过完整分析，直接修改：
1. 修改范围 ≤1 个文件
2. 不涉及方法签名变更
3. 不涉及接口定义变更（Controller、Facade、远程服务）
4. 不涉及扩展点（扩展点接口、SPI、插件实现）
5. 不涉及数据结构变更（DTO、VO、Entity 字段）
6. 不涉及持久化层变更

**典型免分析场景**：添加日志、修改文案、增加判空、调整常量值、内部逻辑优化（不改方法签名）。

> 不确定时，宁可执行分析也不要跳过。

---

## Layer 0：变更方案质量评估（首先执行）

在分析影响范围之前，先审视变更方案本身是否合理：

- [ ] **方案合理性**：是解决问题的最佳方式？是否存在更简洁的设计？
- [ ] **打补丁风险**：在修复根因，还是在症状上贴创可贴？是否应该先重构再修改？
- [ ] **SOLID 符合度**：
  - 新增参数是否导致方法签名膨胀（>3 个参数）？→ 考虑 Parameter Object
  - 是否违反单一职责？→ 考虑拆分方法
  - 是否应该通过扩展（新增类/扩展点）而非修改？→ 开闭原则
- [ ] **命名质量**：新增的方法/参数/字段命名是否精确表达业务意图？
- [ ] **坏味道预警**：是否引入 Feature Envy、Long Parameter List、God Method 等？

**如果方案存在严重问题，醒目标注并建议用户先优化方案再执行修改。**

## 七层影响检查清单

对每一层逐项检查，标注 ✅ 无影响 / ⚠️ 需同步修改，跳过不相关的层。

### Layer 1：方法签名

- [ ] 搜索所有调用方（`搜索代码` 搜方法名）
- [ ] 检查重载方法和接口/实现关系
- [ ] 列出需同步修改的调用方文件和行号

### Layer 2：DTO/VO/Request/Response

- [ ] 参数类型或返回值变更后，哪些数据结构类需同步修改？
- [ ] 序列化/反序列化是否受影响？

### Layer 3：持久化层

- [ ] 在 `*sqlmap.xml` 或等效配置中搜索方法名/参数名
- [ ] 检查 `resultMap`/`resultType` 是否需更新
- [ ] WHERE 条件和占位符是否需更新

### Layer 4：业务调用链

- [ ] 上下游调用链影响（`get_method_call_chain` 追踪）
- [ ] 策略/插件的路由分发逻辑（如"选择第一个匹配的实现"类机制）
- [ ] 事务边界是否受影响

### Layer 5：接口暴露

- [ ] HTTP/远程服务/Dubbo 对外接口是否受影响？
- [ ] API 兼容性是否被破坏？

### Layer 6：测试影响

- [ ] 哪些 `*Test.java` / `*IntegrationTest.java` 会编译失败或断言失败？
- [ ] Mock 配置是否需同步更新？

### Layer 7：扩展点 / 插件实现（跨工程）

**铁律**：修改核心层接口/业务逻辑时，**必须**检查所有插件工程的扩展点实现。

- [ ] 扩展点接口变更 → 搜索该接口的所有实现类
- [ ] 跨工程搜索：在各 plugin 工程中查找实现
- [ ] 插件注册影响：检查插件注册/装配逻辑
- [ ] 新增扩展点方法 → 所有插件工程需同步实现（或提供默认实现）

**搜索策略**（将 `XxxExtension` 替换为项目实际的扩展点接口名）：
```bash
搜索代码 query="class.*implements.*XxxExtension" include_pattern="*.java"
搜索代码 query="class.*extends.*Default.*Extension" include_pattern="*.java"
```

## 架构快速检查清单

修改代码前逐项勾选：

- [ ] 是否修改了核心层的接口/类？→ 必须检查各 plugin 工程
- [ ] 是否修改了扩展点接口？→ 必须搜索所有实现类（跨工程）
- [ ] 是否修改了领域服务或策略组件？→ 必须检查路由/分发逻辑
- [ ] 是否修改了插件工程？→ 必须检查是否影响其他插件或核心层
- [ ] 是否新增了扩展点方法？→ 必须在所有插件工程中同步实现
- [ ] 是否修改了通过容器获取的 Bean？→ 必须检查跨工程兼容

---

## 违规检测

- ❌ 修改方法签名前未调用本 skill
- ❌ 跳过 Layer 0 方案质量评估
- ❌ 修改查询条件未检查持久化配置
- ❌ 修改参数未检查 DTO/VO
- ❌ 修改接口未检查调用方
- ❌ 修改核心层接口未检查插件工程实现类
- ❌ 修改扩展点接口未搜索所有实现类
- ❌ 修改领域服务/策略组件未检查路由分发逻辑
- ❌ 方案存在严重设计问题但未向用户提出改进建议

## 与其他 Skill 的协作

- **任务执行框架（复杂任务流程）**：复杂任务分析评估阶段强制调用本 skill 做完整影响分析
- **任务执行框架 (Fast Track)**：Fast Track Step 1.5 条件调用（仅涉及方法签名变更/跨文件联动/扩展点时），执行轻量扫描（Layer 1 + Layer 7）
- **code-business-analyzer**：先理解业务逻辑，再调用本 skill 分析影响范围
- **cr-review-pipeline**：CR 评审中发现跨文件影响时，调用本 skill 评估波及范围
- **code-review-checklist**：本 skill 的 Layer 6 "受影响的测试"清单 → 维度 6 验证测试覆盖
- **task-spawner**：影响范围过大时，影响清单可流向 `task-spawner` 创建执行任务
