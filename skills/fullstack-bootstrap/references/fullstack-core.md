# FullStack 核心：原则、分级、上下文工程

> 本文是包内技能共享的原则底座；SKILL.md 只放可执行动作，原则沉在这里按需读。

## 六条原则（跨项目不变）

1. **真相源唯一且持久**：进度、需求、设计、坑、映射，全部是仓库里的 Markdown 文件，
   随代码 commit。没写下来 = 不存在。任何「我们之前说好的」都必须能指到一个文件行。
2. **Evidence over claims**：任何「完成/通过/修复」必须附带本轮新鲜运行的证据
   （测试输出末尾、命令退出码、实机截图路径）。禁止采信子代理转述或上一轮的旧证据。
3. **任务拆到 2-5 分钟粒度再执行**：任务带精确文件路径 + 验证命令 + 预期输出。
   计划要写到「一个没有项目上下文的执行者也能照做」——执行者往往是下一个会话的 AI。
4. **主对话是稀缺资源**（上下文 40-60% 利用率）：研究/跑测试/实机验收交给子代理，
   只收结构化结论；计划与状态压实回磁盘文件，让磁盘当内存，不靠长对话记住事。
5. **每阶段有强制门禁**：spec 未签收不写码（品味类视觉改动先 mock 拍板）；
   测试没亲眼看到红过不算写了测试；连续 3 次修不好 → 停下怀疑方向（架构/需求问题），
   不许第六次试同样的招。
6. **收工必有回写**：代码完成后对照真相源修订文档（STATUS/test-map/design.md），
   归档已完成的 plan。流程是闭环，不是单向流水线——防 spec 腐化。

## 分级操作（S/M/L）

见 fullstack-bootstrap SKILL.md。补充判定细则：

- 触发 L 级的信号：需要新表/新依赖/新页面/改已有接口语义/动视觉语言/预估 >1 会话。
- L 级内再分批：每个批次 = 一个可独立提交、可独立验证的单元（know-u-time 的
  「批次 A/B/C」模式）。批次大小以「一次会话能干完且能回归验证」为准。
- 用户只给了一句模糊需求时，先走 fullstack-spec 的澄清，不许直接跳 implement。

## 上下文工程三产物（HumanLayer 模式，L 级用）

```
research → （子代理做，主对话收一页纸摘要）
plan     → docs/plans/YYYY-MM-DD-<slug>.md（任务 2-5 分钟粒度 + 文件路径 + 验证命令）
implement→ 逐任务执行，每完成一个任务就把状态压回 plan 文件（勾选 + 一行结论）
```

「把进度压回 plan 文件」是跨会话不丢工作的关键动作：上下文压缩/换会话/换机器后，
新会话读 plan 文件即可精确续作（哪些任务已完成、卡在哪、下一步动哪个文件）。

## 完成声明门禁（verify 的理论依据）

声明「完成」前五步：
1. 定证据命令（什么命令的什么输出能证明完成？）
2. 本轮亲手跑（不是上轮、不是听子代理说）
3. 读完整输出（含退出码、失败摘要、测试计数）
4. 核对计数与基线（测试数对齐 STATUS 记录， analyze 告警清零）
5. 带证据汇报（贴输出末尾几行，而非只说「全绿」）

## 坑账本与记忆的分工

- **仓库内 pitfalls.md**：项目性坑（构建命令、环境变量、某 API 的怪癖）——任何工具/
  任何会话都能读到，随 git 走。
- **agent 记忆目录**：用户偏好、协作反馈、跨项目的方法论——跟人不跟项目。
- 两者都写时，仓库文件放事实，记忆放指针。换机工作流以仓库文件为准。
