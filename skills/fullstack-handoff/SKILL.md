# FullStack Handoff：磁盘当内存，30 秒接上

上下文压缩/换会话/换机器后，新会话不读对话历史也能精确续作——这是唯一目标。

## 收工流程（顺序执行，缺一不可）

1. **更新 docs/STATUS.md**：「当前阶段」一段话 + 「下次会话的下一步」编号列表
   （具体到「读哪个 plan 文件 / 从哪个任务继续」）。这是唯一进度真相源。
2. **压实 plan 文件**：勾选已完成任务 + 一行结论；卡住的任务写卡在哪、试过什么。
3. **dev-log 追加**：本会话做了什么/为什么/踩了什么坑（只追加不修改旧小节）。
4. **坑账本**：新坑按「现象→根因→对策」入账；第二次踩的老坑升级处理。
5. **提交**：按项目提交风格，文档与代码同 commit（或紧邻 commit）。
6. **agent 记忆**（若宿主支持）：只写 durable 的东西——用户偏好、环境状态、
   下次还需要的决策指针。会话内的临时上下文不写。

## activeContext：不新建文件，STATUS.md 即 activeContext

Cline Memory Bank 用独立 activeContext.md；本工作流把它并进 STATUS.md 的
「当前阶段 + 下一步」两节，避免两个文件内容漂移。若单次 L 级变更跨多会话，
plan 文件本身就是 activeContext（勾选状态即进度）。

## 恢复流程（新会话开始，与 bootstrap 分工）

1. 读 STATUS.md（30 秒判断项目状态）。
2. 若在做 L 级变更：读对应 plan 文件的勾选状态。
3. 若涉及 UI/设计：读 docs/design.md 评审记录最后一节。
4. 干活前用一句话向用户复述：「上次到 X，本次计划 Y」——对齐后才动手。
5. STATUS 没有「下一步」= 交接失败，先按 bootstrap 的接手流程补齐再干活，
   并把这次交接失败当 P0 坑记入账本。

## 中断保护（上下文将满时的应急序）

感觉上下文接近压缩点时，立即降级为「先压实再继续」：
STATUS 下一步更新到当前精确位置 → plan 勾选 → 再继续干活。
宁可多花两分钟压实，不可赌 compaction 摘要保住细节——摘要保不住
「T7 卡在 excel 序列化格式上，试过 csv 不行」这种关键细节。
