# Architecture Guard（架构守卫）

> **执行目标**：以架构合规性为首要目标审视代码结构，优先检查模块边界和依赖方向。
> 不仅检查"是否符合架构规范"，更要评估**"设计是否优雅"**。
> 参考范本时要**批判性继承**——范本本身可能存在坏味道，应识别并改进，而非盲目复制。

> **核心定位**：事前约束。在代码修改/创建之前，帮助 AI 判断"改哪里、怎么改才符合架构"，并找到现有的类似实现作为范本。
> **触发方式**：**询问式触发**。AI 感知到当前任务可能需要架构守卫时，先向用户输出建议并询问是否执行，用户确认后才执行完整检查。
> **与 `change-impact-analyzer` 的关系**：互补而非替代。architecture-guard 管"应该改哪里、怎么改"（事前），change-impact-analyzer 管"改了会影响什么"（事中）。

## 一、感知与询问机制

### 1.1 何时应该感知到需要架构守卫？

AI 在规划代码修改方案时，如果发现以下任一信号，应主动向用户询问：

| 信号 | 说明 |
|------|------|
| **新建源文件** | 需要判定文件应该放在哪个模块、哪个包/目录路径下 |
| **跨模块修改**（≥2 个模块的文件） | 需要校验依赖方向是否合法 |
| **涉及扩展点/插件模式** | 新增/修改扩展点接口或实现 |
| **不确定代码放哪** | AI 自身对模块归属拿不准时 |
| **新增设计模式实例** | 新增 Rule、Strategy、Handler 等模式化组件 |

### 1.2 询问模板

当感知到上述信号时，AI 应输出以下询问（可根据场景裁剪）：

```
🏗️ 架构守卫提示：当前任务涉及 [新建文件 / 跨模块修改 / 扩展点变更]，建议执行架构守卫检查：
- 📍 模块归属判定（确认文件放在正确的模块）
- 🔗 依赖方向校验（确保不产生反向依赖）
- 📐 设计模式合规（确认符合项目架构模式）
- 📋 范本参考（搜索类似业务的现有实现作为参考）

是否执行？(Y/跳过)
```

用户确认后，按下方流程执行。用户选择跳过则直接进入代码编辑。

## 二、模块归属判定

### 2.1 模块职责矩阵

> {在此填写项目的模块职责矩阵，按代码职责→目标模块→典型包路径组织}
>
> 参考格式如下表，请根据项目实际模块结构填写：

| 代码职责 | 目标模块 | 典型包/目录路径 |
|---------|---------|----------------|
| API 接口层（Controller / Handler） | `{api-module}` | `controller/` 或 `handler/` |
| 业务逻辑层（Service / Manager） | `{service-module}` | `service/` 或 `domain/` |
| 数据访问层（Repository / DAO） | `{data-module}` | `repository/` 或 `dao/` |
| 数据模型（DTO / VO / Entity） | `{model-module}` | `model/` 或 `dto/` |
| 基础设施（配置 / 工具类 / 中间件集成） | `{infra-module}` | `config/` 或 `infrastructure/` |
| 扩展点接口定义 | `{core-module}` | `extension/` 或 `spi/` |
| 扩展点默认实现 | `{base-module}` | `extension/impl/` |
| 产品/租户特定扩展实现 | `{plugin-module}` | `extension/{product}/` |

### 2.2 判定流程

```
收到"新建文件"请求
    ↓
问自己：这个类/文件的职责是什么？
    ↓
查上方矩阵 → 确定目标模块
    ↓
查目标模块中同域的现有文件 → 确认包路径和命名规范
    ↓
输出判定结果
```

### 2.3 判定结果模板

```
📍 模块归属判定：
- 代码职责：[如：订单域的参数校验规则]
- 目标模块：`{target-module}`
- 目标路径：`{target-package-or-directory}`
- 命名建议：`OrderValidationRule.java`
- 参考范本：`PaymentValidationRule.java`（同模块同域的现有实现）
```

## 三、依赖方向校验

### 3.1 合法依赖方向

> {在此绘制项目的合法依赖方向图，从上到下单向依赖}
>
> 参考格式如下，请根据项目实际分层结构填写：

```
{plugin-layer}（插件/扩展层）
    ↓ 可以依赖
{base-extension-layer}（基础扩展层）
    ↓ 可以依赖
{service-layer}（业务逻辑/能力实现层）
    ↓ 可以依赖
{core-layer}（核心引擎/领域模型层）
    ↓ 可以依赖
{infrastructure-layer}（基础设施层）
```

### 3.2 违规依赖检测

以下依赖方向**严格禁止**：

| 违规类型 | 示例 | 正确做法 |
|---------|------|---------|
| 核心层依赖插件层 | 核心模块 import 插件模块的类 | 通过接口/扩展点解耦 |
| 基础扩展层依赖产品插件层 | 基础扩展模块 import 特定产品插件的类 | 在 base 定义接口，产品层实现 |
| 插件间互相依赖 | 插件 A import 插件 B 的类 | 提取公共逻辑到基础层 |
| 下层依赖上层 | Service 层 import Controller 层的类 | 调整依赖方向或提取接口 |

### 3.3 校验方法

检查修改计划中的 import/依赖语句，确认：
1. 每个文件的 import 只引用**同层或下层**模块的类
2. 不存在上述违规依赖表中的任何模式

## 四、设计模式合规检查

### 4.1 模式识别与合规

当新增功能时，根据功能类型判断应使用的设计模式：

| 功能类型 | 应使用的模式 | 违规信号 |
|---------|------------|---------|
| 算法/策略可变 | 策略模式（Strategy 接口 + 多实现） | 用 switch-case / if-else 硬编码多种算法 |
| 流程中各步骤可变 | 模板方法（抽象基类 + 钩子方法） | 在一个方法中重复相似流程但细节不同 |
| 外部服务调用 | DI 容器 + 配置注入 | 直接 new 外部服务客户端 |

> {在此添加项目特定的设计模式合规规则，例如：}
> - 如果项目使用扩展点框架：多产品差异化逻辑 → 扩展点模式
> - 如果项目使用规则引擎：校验规则 → Rule 模式
> - 如果项目使用事件驱动：异步操作 → Event/Listener 模式

### 4.2 合规检查输出

```
📐 设计模式合规：
- 功能类型：[如：新增一个订单校验规则]
- 应使用模式：策略模式（实现 ValidationRule 接口）
- 合规状态：✅ 符合 / ⚠️ 建议调整
- 调整建议：[如有]
```

## 五、范本参考（核心能力）

这是本 Skill 最重要的能力之一：**自动搜索项目中类似业务的现有实现，作为新代码的设计参考**。

### 5.1 范本搜索策略

根据当前任务的业务域和代码类型，按以下优先级搜索范本：

| 优先级 | 搜索范围 | 说明 |
|:------:|---------|------|
| 0 | **项目编码范本文档** | 先查阅项目是否有编码范本文档（如 `.notes/patterns/canonical/` 或类似目录），如果有，直接使用范本作为代码骨架参考 |
| 1 | **同模块 + 同业务域** | 如：在 `order/validation/` 中找订单相关的现有校验实现 |
| 2 | **同模块 + 相近业务域** | 如：在 `payment/validation/` 中找支付相关的实现（支付和订单模式相似） |
| 3 | **其他模块/插件 + 同业务域** | 如：在其他插件模块中看同业务域怎么做的 |
| 4 | **基础层的默认实现** | 如：`DefaultValidationRule.java` 等默认实现 |

### 5.2 搜索执行方法

```bash
# 步骤 0：查阅项目编码范本（最高优先级）
# 检查项目中是否有模式范本文档目录

# 步骤 1：确定业务域关键词（如 order、payment、user）
# 步骤 2：在目标模块中搜索同域文件
search_file: "{target-module}/**/{domain}/**/*.{ext}"

# 步骤 3：如果是扩展点类，搜索同类型的现有实现
file_grep: query="extends Default.*" include_pattern="*.java"

# 步骤 4：如果是 Rule/Strategy，搜索同类型的现有实现
file_grep: query="implements.*Rule|implements.*Strategy" include_pattern="*.java"
```

### 5.3 范本参考输出

```
📋 范本参考：
- 业务域：订单（order）
- 代码类型：校验规则（ValidationRule）

推荐参考文件（按相关度排序）：
1. 🥇 `order/validation/OrderAmountRule.java`
   → 同模块同域，最直接的参考
2. 🥈 `payment/validation/PaymentLimitRule.java`
   → 同模块相近域，可参考校验模式
3. 🥉 `core/validation/DefaultValidationRule.java`
   → 基类默认实现，了解可覆写的钩子方法

建议阅读 🥇 文件，了解：
- 类继承结构和覆写方式
- 使用了哪些钩子方法
- import 了哪些依赖
```

### 5.4 范本应用原则

找到范本后，AI 应该：
1. **阅读范本文件**：理解其类结构、继承关系、覆写方式
2. **提取模式骨架**：识别出可复用的代码结构（继承哪个基类、覆写哪些方法、import 哪些依赖）
3. **适配新需求**：在范本骨架基础上，填充新功能的具体逻辑
4. **保持一致性**：命名规范、包/目录路径、注释风格都与范本保持一致

## 六、完整执行流程

```
AI 规划修改方案时感知到信号（新建文件/跨模块/扩展点）
    ↓
输出询问：是否执行架构守卫？
    ↓ 用户确认
Step 1: 模块归属判定
  → 确定每个新建/修改文件应在哪个模块
    ↓
Step 2: 依赖方向校验
  → 检查修改计划中的依赖关系是否合法
    ↓
Step 3: 设计模式合规
  → 检查新增功能是否使用了正确的设计模式
    ↓
Step 4: 范本参考
  → 搜索类似业务的现有实现
  → 阅读范本，提取模式骨架
  → 输出参考建议
    ↓
输出架构守卫报告（汇总以上四步结果）
    ↓
继续后续流程（change-impact-analyzer → 代码编辑 → review）
```

## 八、与其他 Skills 的协作

| 协作对象 | 协作方式 |
|---------|---------|
| `change-impact-analyzer` | architecture-guard 先确定"改哪里"，change-impact-analyzer 再分析"改了影响什么" |
| `code-review-checklist` | 事后 Review 时可回溯架构守卫报告，验证实际代码是否符合 |
| `task-spawner`（PAUSE 模式） | 架构守卫报告可作为进度存档的一部分，传递给新对话 |
