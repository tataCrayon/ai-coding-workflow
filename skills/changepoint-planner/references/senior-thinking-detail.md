# Senior-thinking-detail（资深开发者思维详解）

> changepoint-planner Step 3 的深度思考模板与输出规范。

---

## 兼容性分析 Checklist

```
[ ] 旧接口签名是否保持不变？
[ ] 新增字段是否为可选/有默认值（向后兼容）？
[ ] 是否需要并行运行期？如有，切换机制是什么？
[ ] 是否需要灰度迁移？如有，灰度维度（租户/流量/地区）？
[ ] API 版本策略：V1 保留多久？V2 何时成为唯一版本？
[ ] 是否需要数据迁移脚本？
[ ] 是否需要回滚方案？
```

**兼容性结论格式**：`向后兼容——{具体策略}` 或 `不兼容——{迁移方案 + 过渡期}`

---

## 设计模式选择指南

| 场景特征 | 推荐模式 | 反模式信号 |
|---------|---------|-----------|
| 算法/策略可替换 | **Strategy**（多实现同一接口，DI 切换） | switch-case 硬编码 |
| 流程骨架固定、步骤可变 | **Template Method**（父类骨架 + 钩子方法） | 子类重复相似流程 |
| 状态变化需通知多方 | **Observer**（事件源与监听者解耦） | 循环调用依赖方 |
| 未来新增变体、核心不修改 | **Extension Point**（核心层接口 + 插件实现） | 修改核心代码适配新变体 |

**项目约定优先**：已有扩展点框架或规则引擎时，优先使用项目约定模式。

---

## 可扩展性评估标准

| 评估项 | 达标 | 不达标信号 |
|--------|------|-----------|
| 新增变体成本 | 只需加实现类，不改核心代码 | 需修改 if-else/switch 分支 |
| 扩展点层级 | 核心层接口 → 基础层默认 → 插件层差异化 | 接口和实现同层 |
| 配置化程度 | 新变体通过配置/DI 接入 | 必须改代码才能接入 |

## 上下游影响模板

```
上游调用方：XxxService.methodA() → [需适配/无需适配]
下游依赖方：XxxRepository.query() → [受影响/不受影响]
跨仓库影响：finhub-platform/ApiGateway → [需同步/无需]
数据库影响：[表结构变更/无]
```

> Java 方法签名变更时，调用 `java-change-impact-analyzer` 做七层检查，结果填入此模板。
