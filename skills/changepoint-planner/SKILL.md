# Changepoint Planner（改动点规划器）

> **执行目标**：将 User Story 映射到具体的代码改动点，并像资深开发者一样思考——不只回答"改哪里"，更要回答"改完之后会怎样"。
> **核心差异**：普通改动点分析只列文件清单；本 Skill 在基础清单之上叠加 4 层资深开发者思维（兼容性、设计模式、可扩展性、上下游影响），确保改动方案经得起实战考验。

**铁律**：任何涉及修改/扩展现有功能的任务，必须先执行改动点规划，再动手改代码。

---

## 一、触发时机

### 1.1 关键词触发

用户表达中包含以下任一关键词时触发：
- "改动点分析"、"分析改哪里"、"改动点规划"、"确认变更范围"
- "兼容性分析"、"设计模式选择"、"改动范围"、"变更点"、"影响分析"
- 任何提及修改或扩展现有功能的表述，即使没有显式要求改动点分析

### 1.2 场景触发

当 AI 规划修改方案时发现以下信号，应主动建议执行本 Skill：
- 涉及修改现有流程（而非全新功能）
- 涉及扩展已有接口或数据结构
- 涉及多模块联动改动
- 涉及可能影响上游调用方或下游依赖方的改动

## 二、执行流程（4 步）

### Step 1: 读取需求来源

按以下优先级获取 User Story：

1. **任务上下文目录的 `02-user-stories.md`**（最优先）——直接读取已结构化的 US 列表
2. **任务上下文目录的 `TASK-CONTEXT.md`**——从差距分析(P0/P1/P2)和子任务拆解提炼 US
3. **当前对话中的需求文档或功能描述**——从 PRD、飞书文档、自然语言描述提炼 US
4. **向用户索要**——如果以上都没有，要求提供需求来源（PRD 文档路径或功能描述）

> **提炼规则**：每个 User Story 必须有编号（US-01、US-02 等）和明确的功能描述。从 TASK-CONTEXT 提炼时，每个 P0/P1 差距条目对应一个 US。

### Step 2: 基础改动点识别

对每个 User Story，识别基础改动点清单：

| 字段 | 说明 |
|------|------|
| **Change-point ID** | `CP-US{xx}-{nn}` 格式，如 CP-US01-01 |
| **所属模块** | 哪个模块/包 |
| **所属层级** | Controller / Service / Repository / DTO / Config 等 |
| **涉及文件** | 具体文件路径（新建的标注 `[NEW]`） |
| **变更类型** | `new` / `modify` / `delete` |
| **变更说明** | 一句话描述做什么变更 |

**识别方法**：
1. 从 User Story 描述中提取功能动词和名词
2. 搜索代码库中相关的类、方法、配置
3. 判断是新增、修改还是删除
4. **🔴 事实校验硬约束**：对于 `modify` 类型的改动点，`涉及文件` 列出的路径必须在代码库中真实存在——使用 Grep/Glob 验证后再填入。不存在则标记为 ❌ NOT_FOUND 并提醒修正，禁止凭记忆假设文件存在
5. 为每个 User Story 生成编号连续的改动点

### Step 3: 资深开发者思维（核心差异化能力）

> 详细模板和示例见 `references/senior-thinking-detail.md`

对 Step 2 中标记为 `modify` 的每个改动点，逐一执行 4 维度深度思考：

#### 3.1 兼容性维度

**核心问题**：修改现有流程后，旧流程还能正常工作吗？

思考清单：
- [ ] 这是对现有流程的修改还是替代？
- [ ] 旧流程的调用方是否需要同步适配？
- [ ] 是否需要并行运行期（新旧流程同时生效）？
- [ ] 是否需要灰度迁移策略（按租户/按流量逐步切换）？
- [ ] 数据结构变更是否向后兼容（新增字段 vs 修改字段 vs 删除字段）？
- [ ] API 接口变更是否需要版本管理（V1/V2 并存）？

#### 3.2 设计模式维度

**核心问题**：用什么模式来实现这个改动最合适？

思考清单：
- [ ] 这是一个"策略可变"的场景吗？→ 考虑 Strategy 模式
- [ ] 这是一个"流程中某些步骤可替换"的场景吗？→ 考虑 Template Method 或扩展点
- [ ] 这是一个"状态变化需要通知多方"的场景吗？→ 考虑 Observer 模式
- [ ] 这是一个"未来可能新增变体"的场景吗？→ 考虑 Extension Point 模式
- [ ] 当前项目已有的模式规范是什么？→ 优先遵循项目约定

#### 3.3 可扩展性维度

**核心问题**：当前设计能否支撑未来的同类变更？

思考清单：
- [ ] 如果未来需要加一个新的变体（新策略/新产品/新规则），当前设计是否只需加一个实现类？
- [ ] 扩展点是否放在了正确的层级（核心层定义接口，基础层提供默认实现，插件层做差异化）？
- [ ] 是否存在硬编码的条件分支，未来新增变体时需要修改核心代码？
- [ ] 配置化程度是否足够（新变体能否通过配置而非代码变更接入）？

#### 3.4 上下游影响维度

**核心问题**：改了这个点，谁会被波及？

思考清单：
- [ ] 上游调用方（谁调了我）：需要同步修改吗？接口签名是否兼容？
- [ ] 下游依赖方（我调了谁）：我改的参数/返回值是否影响下游的处理逻辑？
- [ ] 跨仓库影响：是否需要同步修改另一个仓库的代码？
- [ ] 数据库影响：表结构变更是否影响查询、索引、迁移脚本？

> **子步骤**：当改动涉及 Java 方法签名变更、跨文件联动时，调用 `java-change-impact-analyzer` Skill 执行七层影响检查，将其输出作为本维度的输入。

### Step 4: 生成改动点文档

将 Step 2 和 Step 3 的成果合并，生成 `03-changepoints.md` 到任务上下文目录。

**输出格式要求**：
- 每个改动点必须有 **reason** 字段（使用 markdown 引用块 `>` 格式），说明"为什么要改"
- 每个标记为 `modify` 的改动点必须附 4 维度思考结论
- 按模块分组，便于审阅

**文档结构**见 `references/senior-thinking-detail.md` 的输出模板。

## 三、产出确认请求（Skill 输出末尾）

改动点文档生成后，在 Skill 输出末尾**必须**附带确认请求，格式如下：

```
🔴 改动点确认请求 — 共 N 个改动点，请逐项审阅：
| CP ID | ✅同意 | ⚠️需调整 | ❌取消 |

确认后才进入下一步（技术方案设计或编码）。未获确认的改动点不得进入编码阶段。
```

> **平台适配说明**：Claude Code Skill 工具是单次调用，Skill 内部无法暂停等待用户。Human Gate 由**主会话**负责——Skill 输出确认请求后返回，主会话等待用户反馈，再根据反馈决定下一步。

**未获确认的改动点不得进入编码阶段**。这是防止范围蔓延和错误改动的关键门禁。

> **Reason**: {为什么要改，引用 User Story 或需求原文}

#### 资深开发者思维

**兼容性**: {结论 + 策略}
**设计模式**: {推荐模式 + 原因}

## 五、与其他 Skill 的协作

| 协作对象 | 协作方式 |
|---------|---------|
| `java-change-impact-analyzer` | Step 3.4 上下游影响维度的子步骤，涉及 Java 方法签名变更/跨文件联动时调用 |
| `architecture-guard` | Step 3.2 设计模式维度的参考源，复用其设计模式合规表；新建文件时可触发模块归属判定 |
| `spec-verifier` | 改动点确认后进入技术方案阶段，Spec 生成后由 spec-verifier 验证 |
| `task-spawner` | 改动点过多或跨仓库时，可将改动点清单持久化为任务文件 |
| `code-business-analyzer` | Step 2 搜索代码库前，先理解业务逻辑分布 |

**典型工作流顺序**：

```
User Story → changepoint-planner → Human Gate → Spec → spec-verifier → 编码
                                     ↑
                            java-change-impact-analyzer（按需）
                            architecture-guard（按需）
```

## 六、质量自检

生成改动点文档后，AI 必须执行以下自检：

- [ ] 每个 User Story 是否至少有一个改动点对应？
- [ ] 每个改动点是否都有 reason 字段（引用块格式）？
- [ ] 每个 `modify` 类型改动点是否附了 4 维度思考结论？
- [ ] reason 是否追溯到 User Story 编号或需求原文？
- [ ] 是否有遗漏的模块或层级（特别是基础设施层、配置层）？
- [ ] 上下游影响是否覆盖了跨仓库场景（如有）？
- [ ] 设计模式选择是否与项目已有约定一致？
