# Comprehension Ledger — 理解账本

> **问题**：AI 写完了代码，合入了，上线了——而你（需求的主人）对业务和实现没有印象。
> 下次迭代要改这条链路时，等于从零开始。这就是**理解债**：每做一个需求，欠一笔。
>
> **解法**：把理解变成有借有还的账。每个需求记一笔**理解资产**（已通过的自测题）或**理解负债**（答错的题）；负债有利息（进入复习队列），还清才销账。

本 Skill 是**有状态的门禁系统**：一个人类可直读的 markdown 账本 + 四个寄生在其他工作流节点上的钩子。它不替代你的开发流程，而是寄生其上——每个节点只插一行。

## 心智模型

```
理解债（每做完一个需求就累积）
   │
   ├── 还债动作 = H2 理解交接（讲一遍 + 看图 + 自测）     ← 学习科学：生成效应/双重编码/测试效应
   │
   └── 利息    = H3 间隔复习（每个新需求开工时还 ≤2 题）  ← 学习科学：间隔重复/提取练习
                     │
                     ├── 答对 → Leitner 盒 0→1→2（隔 1/2/5 个需求），连对 2 次毕业
                     └── 答错 → 回盒 0；同一题连错 2 轮 → 触发「补课」（AI 重讲链路）
```

**调度单位是"需求次数"不是天数**——工程师的时间节拍是需求，且每开需求必经方案阶段，复习天然搭车。

## 存储（唯一状态文件，人可直读）

```
.agent/understanding/ledger.md          ← 理解账本（本 Skill 的全部状态）
.agent/understanding/capability-map.md  ← 能力一页纸（可选，H4 刷新对象）
```

账本格式见 [references/ledger-format.md](references/ledger-format.md)。铁律：**markdown 直读，禁止迁去 jsonl/sqlite**——账本的首要读者是人，AI 只是记账员。

## 首次使用（bootstrap）

第一次调用本 Skill 时（或用户说"初始化理解账本"）：

1. 创建 `.agent/understanding/ledger.md`（格式模板见 references）。
2. 向用户输出一段 ≤10 行的介绍：理解债是什么、四钩子怎么寄生、复习节奏（每需求 ≤2 题）。
3. 询问宿主工作流：用户的主开发流程是自定义 SOP、还是某专家包、还是没有流程？把对应的一行钩子指令写进宿主文件（见下节"接入宿主"）。

## 四个寄生钩子协议

钩子是本 Skill 的执行面。每个钩子寄生在一个**宿主节点**上，宿主文件只多一行 `> 🎓 [ledger 钩子] …`，业务逻辑零改动。

### H1 边界问答 —— 宿主：方案签收门禁前

1. 把技术方案中**非平凡决策**转成「如果…会怎样」边界题；**选题材于重要性而非凑数**——只出能检验"是否理解主流程/核心业务"的题，数量不设硬上限，以"用户愿意逐条回答"为预算上限（题目多到用户放弃逐条应答，等于没问）。
   - 好题：「如果下游推送了中间态但无成交数据，会发生什么？」
   - 差题：「这次用了哪个设计模式？」（背诵题，无信息量）
2. 用户口答；**答不上的点回填进方案主文档**——文档的信息量由理解缺口驱动，而非由"完整"驱动。
3. 用户原话与答案要点记入方案的 Sign-off 节。

> 为什么有效：提问在先的 pretesting effect + 签收前暴露理解分歧，成本最低的纠偏时机。

### H2 理解交接三件套 —— 宿主：需求收尾（verify 之后）

产出全部 **human-facing**（整条开发链唯一的非 AI-facing 产物）：

1. **一页讲给同事的说明（≤400 字）**：不讲给 AI 听，讲给一个没跟过这个需求的同事听。业务上在干什么（3 句内）、改动落在哪条链路（点名上下游）、最容易理解错的一个点。禁止罗列文件清单、禁止贴代码。
2. **基于实际代码的时序图**：从代码反查（不是从设计文档抄），每个节点带 `file:line`。只画主链路 + 1 个关键异常分支，≤12 个节点——顺带验证文档与代码无漂移。有 Mermaid 渲染能力就用，没有就出 Mermaid 源码。
3. **3 道自测题**：基于本次设计的**为什么**，不是"改了哪几个文件"。用户口答，AI 批改纠偏；答错的题与链路写入账本复习队列（盒 0）。

收尾写入账本：需求一节 + 答错题入队。

### H3 间隔复习 —— 宿主：新需求开工第一步

1. 读账本复习队列，取**到期题 ≤2 道**，用户口答。
2. 答对：盒 0→1→2（分别隔 1/2/5 个需求复习）；**连续 2 次答对毕业**，题转入「理解资产」清单。
3. 答错：回盒 0（下个需求就复习）。
4. **补课模式**：同一题连续 2 轮答错 → 判定「不是遗忘是没懂」→ AI 重新讲该链路（画图、引用业务文档），讲完重新出题。
5. 队列空：输出一行「复习队列空」，不阻塞、不造题。

### H4 能力地图保鲜 —— 宿主：工作流/Skill 增删时

用户的工作流能力清单（Skill/Rule/脚本）发生变化时，输出一行提醒：「能力一页纸已过期（`.agent/understanding/capability-map.md`），建议刷新」。
地图格式：A 主流程包 / B 被流程调用的能力件 / C 独立运维工具 / D 元工作流 / E 其他场景 / 归档去向表。
> 治理的不只是业务理解债，还有**工作流自身的理解债**——"我都有哪些能力了？我都不知道了"。

## 接入宿主工作流

按用户的现状选一种，把钩子行写进宿主文件（CLAUDE.md / AGENTS.md / 流程 SKILL.md）：

| 用户现状 | 接法 |
|----------|------|
| 有明确开发流程（spec→design→impl→verify） | H1 插在方案签收前，H2 插在 verify 后，H3 插在 spec 开工首步 |
| 没有固定流程 | 在 CLAUDE.md 写一行：「完整需求收尾时执行 comprehension-ledger 的 H2 三件套；新需求开工时执行 H3 复习」 |
| 已有专家包/SOP 体系 | 同上行，但钩子行插在包内对应阶段文件，保持「钩子只插一行」铁律 |

## 铁律（不可协商）

1. **账本 human-facing**：markdown 直读，禁止迁去 jsonl/sqlite。
2. **不评分不 KPI**：只记通过/不通过 + 错题入队；禁止对用户输出任何负面评价——目标是理解，不是考试。用户答不上来是**信息**（说明文档该补这个点），不是**失败**。
3. **钩子只插一行**：宿主文件只见 `> 🎓 [ledger 钩子] …` 门禁行，宿主业务逻辑零改动。
4. **复习 ≤2 题/需求**：超过会变成考试地狱，用户将绕开整个体系——宁可少，不可多。
5. **毕业即止**：毕业题不再考；账本有界（毕业出队），不无限膨胀。
6. **题目来自真实决策**：自测题基于方案里"为什么这样设计"，禁止出文件名背诵题。

## Token 预算

- 常驻成本：账本不进上下文，只在钩子触发时读；本 Skill 元数据 ~150 tokens。
- 每次钩子执行注入 ≤2K tokens。
- 账本每需求 ~15 行，毕业出队有界。

## 与相关实践的关系

- **学习科学依据**：testing effect（Roediger & Karpicke 2006）、spaced repetition（Leitner 盒）、pretesting effect、generation effect、dual coding（Paivio）。完整论证见 [references/design-notes.md](references/design-notes.md)。
- **不是代码审查**：CR 查代码质量，本 Skill 查人的理解状态。
- **不是文档生成器**：文档是副产品；主产物是"人能讲清这条链路"这个状态本身。
