# 任务持久化统一模板

> **PAUSE 和 TASK 使用同一套模板**，仅通过 `类型` 字段区分。统一格式确保两种场景的任务文件都包含完整的推理链和上下文，新对话拿到任务文件后能独立完成任务。

```markdown
# 任务：{任务简述}
- 创建时间：YYYY-MM-DD
- 类型：进度存档 | 子任务
- 状态：待执行 | 进行中 | 已暂停 | 已完成

## 🎯 任务目标
{遵循 task-execution.md 命名规范：[动作] + [目标对象] + [具体内容]。必须具体到类名/方法名/文件名}

## 🗺️ 业务背景
{简述完整的业务链路和当前状态。让新对话的 AI 理解"为什么要做这件事"。
不要只写 1-3 句话的冷结论——如果背景复杂，宁可多写几段也不要遗漏关键信息}

## 🧠 推理链与关键上下文

> **这是防止新对话"从零开始重新分析"的关键章节。** 把对话中已经走过的弯路、得出的正确结论、排除的方案都记下来。
> 对标 Chudi 的 context.md（活状态文档）和 continues CLI 的工具活动记录。

### 已确认的事实
{对话中通过代码分析、搜索、阅读等方式确认的事实，附确认方式}
- {事实 1} — 确认方式：{通过 读取文件 查看 XxxService 第 120 行确认}
- {事实 2} — 确认方式：{通过 搜索代码 搜索 "YyyEnum" 确认只有 2 处引用}

### 已排除的方案
{对话中讨论过但被排除的方案，附排除原因——避免新对话重走弯路}
- {方案 A}：排除原因 — {为什么不行，具体到哪个类/方法/约束导致不可行}

### 关键决策
{对话中做出的重要决策，附决策依据}
- {决策 1} — 原因：{为什么这么选，参考了什么}

### 工具活动摘要
{对话中执行的关键搜索/读取/分析动作及其发现，让新对话知道"前任做了什么"}
- 搜索了 `XxxService` 的所有调用方 → 发现 3 处调用：{列出}
- 读取了 `YyyConfig` → 发现关键配置项：{列出}
- 分析了 `ZzzProcess` 的流程 → 确认节点顺序为：{列出}

## 📁 关联上下文（必须阅读的文件）
{新对话的 AI 必须优先使用 读取文件 读取以下文件以建立视界}
- `path/to/file1` — {一句话说明该文件是什么、为什么要读}
- `path/to/file2` — {一句话说明该文件是什么、为什么要读}

## ✅ 已落地的资产
{已经修改/创建的文件清单。TASK 类型初始为空，完成后补充}
- [已修改/创建的文件路径 1]：[简述做了什么改动]
- [已修改/创建的文件路径 2]：[简述做了什么改动]

## 📍 当前断点（仅 PAUSE 类型需要）
- **停驻点**：目前正在处理哪个文件/哪个方法？
- **最新阻碍**：当前面临的具体问题是什么？
- **下一步动作**：接手后应该立即做什么？

## 📋 任务项清单
{具体的、可逐项执行的任务列表。每项遵循 task-execution.md 命名规范}
- [x] {已完成项}
- [ ] {待完成项：[动作] + [目标对象] + [具体内容]}

## 🚫 边界与约束
- **动作约束**：{例如：只读检查不修改代码 / 允许直接修改代码}
- **质量约束**：{例如：日志必须使用占位符、异常处理块必须有堆栈日志}
- **范围约束**：{例如：仅关注 X 模块，不要越界修改 Y 模块}

## ✅ 验收标准
{明确的完成条件，让 AI 知道"做到什么程度算完成"}
- {验收条件 1}
- {验收条件 2}

## 🚀 新会话接手后的第一步动作
{明确的 Action Item，例如："首先 读取文件 读取关联上下文中的所有文件，然后按任务项清单逐项执行"}
```

### 模板使用说明

| 字段 | PAUSE（进度存档） | TASK（子任务） |
|------|-----------------|--------------|
| 状态初始值 | `进行中` 或 `已暂停` | `待执行` |
| 📍 当前断点 | **必填** — 记录停驻点和阻碍 | **省略** — 子任务从头执行 |
| ✅ 已落地的资产 | **必填** — 记录已完成的改动 | **初始为空** — 完成后补充 |
| 🧠 推理链 | **必填** — 保存对话中的推理过程 | **必填** — 保存对话中梳理出的思路 |
| 🚫 边界与约束 | 可选 | **必填** — 明确新对话的行动边界 |
