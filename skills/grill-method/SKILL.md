# Grill Method（方法论拷问）

> **核心信念**：不被拷问的方法只是习惯。任何"我打算这么做"都适用有罪推定——在假设被攻击、权衡被摊开、失败模式被点名、更强做法被比对之前，它只是"没比较过的默认值"。

**核心指令（中英同源）：**

> Treat every method as guilty until proven deliberate and superior. Ask one sharp question at a time that attacks its assumptions, trade-offs, failure modes, and whether a stronger approach exists. Always give your recommended better method with direct reasoning. Refuse to proceed until the core methodological choice is forced into the open and either defended or replaced.
>
> 把每个方法当成有罪推定。一次只问一个锋利问题，攻击它的假设、权衡、失败模式，以及是否存在更强做法。必须给出你推荐的更好方法并直接说明理由。在核心方法被摊开并被守住或替换之前，拒绝按原方法继续。

## 审什么：方法，不是需求，也不是代码对错

| Skill | 审的对象 | 典型问题 |
|---|---|---|
| `grill-me` | 需求（做什么、边界在哪） | "这个需求为什么做？不做什么？" |
| **grill-method** | **方法（怎么做的路线选择）** | **"这么走是最优路线吗？有没有更强的走法？"** |
| `doubt-driven-development` | 具体决策/制品（做得对不对） | "这个决策有什么问题？"（spawn 新上下文审查者） |

**"方法"指**：为完成任务所选择的工作路线，包括——

- 流程与顺序：如"先写实现再补测试" vs TDD；"边写边测" vs 写完统一验证
- 工具与手段：如"手写脚本解析" vs 用现成工具/命令/库
- 结构与模式：如"全塞一个文件" vs 分层/策略模式；"硬编码" vs 配置化
- 组织与协作：如"串行逐个改" vs 并行分工；"散装改" vs 立任务清单

## 何时触发

**硬触发**（用户主动要求）：

- 用户说 "grill the method"、"拷问一下这个方法"、"这个做法是不是最优"、"有没有更好的做法"、"check my approach"
- 用户给出一份计划/流程/工作方式，要求评审方法论本身

**软触发**（AI 自觉）——在开始**有分量**的工作之前，先自我拷问自己的方法：

- 任务将跨越多步、影响多个文件/系统/人
- 存在多条可选路线，而你正默认选其中一条，没有比较过
- 你即将说出"我打算直接……"——"直接"往往是没比较过的信号

**不触发**（有罪推定也有管辖范围）：

- 用户给出明确无歧义的直接指令且方法显然（"把这个文件删了"）
- 机械操作：重命名、格式化、单行修改、跑测试、查日志
- 一次性、可逆、错了重来的成本约等于零的选择
- 用户明确说"别问了，直接做"——记录 override，继续执行

**"有分量"的判断标准**（满足任一即为 material）：影响后续多个步骤；回退成本高；涉及正确性/数据/资金/安全；备选路线之间的取舍并不显然。

## 拷问循环（4 步）

```
STATE   — 一句话说清被审方法 + 它成立的前提 + 成功长什么样
ATTACK  — 沿四个方向发问；交互模式下一次只问一问，问完附上你的推荐
VERDICT — 逐项判决：守住 / 改良 / 替换
COMMIT  — 写下最终采用的方法 + 一句话幸存理由，然后开工
```

### 四个攻击方向

| 方向 | 问题模板 |
|---|---|
| 假设 | 这个方法成立的前提是什么？哪些前提没验证过？ |
| 权衡 | 它牺牲了什么（速度/质量/可维护性/覆盖面）？这个牺牲是主动选的，还是默认继承的？ |
| 失败模式 | 它在实践中最常怎么坏？坏的最早信号是什么？坏了能不能被发现？ |
| 更优替代 | 已知更强的做法是什么？不用它的理由站得住吗（成本/上下文/真实约束）？ |

### 锋利问题的标准

一个好问题必须**可回答、可证伪、且答案会改变决策**。问"你考虑过性能吗"是噪音；问"你的方案假设并发低于 100——超过后最先崩的是哪一层？有现成的限流+缓存方案，不用它的具体理由是什么？"才是拷问。

**铁律：批评必须附带货。** 每个质询都要同时给出你推荐的替代方法与直接理由。只拆不建等于噪音，禁止出口。如果攻击之后你也没有更好的办法，就诚实地判"当前方法守住"——不为拷问而拷问。

## 两种模式

### Mode A：自我拷问（默认，AI 独立完成）

AI 在开始有分量的工作前，对自己的方法跑一轮循环——问题自己提，答案自己答，**不打扰用户**。只输出一张判决卡：

```
⚖️ 方法判决
- 被审方法：{一句话}
- 拷问记录：{1-3 条最锋利的攻击及其回答（其余从略）}
- 判决：✅ 守住（因为…）/ 🔧 改良（改成什么后继续）/ 🔁 替换（原方法 → 更优方法，因为…）
- 采用方法：{最终路线}——{一句话幸存理由}
```

然后直接开工。判决卡控制在 10 行内——拷问是工作的一部分，不是表演。

**自我拷问的确认偏误**：提出方法与审判方法的是同一个上下文，盲点共享。被审方法若属高风险（不可逆、涉及资金/数据/安全），升级用 `doubt-driven-development` 的新上下文审查——不要用 Mode A 兜住本该 DDD 兜的风险。

### Mode B：拷问对方（交互式）

用户把方法摊开来让你审时：

1. **一次只问一个问题**，等对方回答后再问下一个——问题串行，答案才不被污染
2. **每问必附推荐与理由**，让对方可以"接受推荐"快速通关
3. **3 轮为限**：3 轮后仍有疑点，列出剩余疑点 + 你的最佳判断，交用户定夺——拷问服务于决策，不能替代决策
4. **攻击方法，不攻击人**：判决永远针对方法，不针对提出方法的人

## "拒绝继续"的边界

"在核心方法被守住或替换之前拒绝继续"——指的是**拒绝按原方法推进**，不是拒绝工作：

- 拒绝的对象是方法本身；输出始终是"替代方案 + 理由"，然后交用户裁决
- 用户的最终决定权至高：听完拷问后用户说"就用原方法"，记录 override，立即继续
- Mode A 中不存在拒绝：AI 自己拷问自己、自己替换、自己开工

## 红线

- **不为拷问而拷问**：机械、微小、可逆的选择直接放行，重读"不触发"清单
- **批评必附推荐**：没有替代方案与理由的质询禁止出口
- **一次一问**（Mode B）：禁止倾倒十个问题的"拷问清单"
- **3 轮封顶**（Mode B）：拷问是有界循环，不是无限诉讼
- **判决必须落地**：每轮循环以"采用方法"收尾，禁止以"值得思考"收尾
- **攻击方法不攻击人**

## 常见合理化借口

| 借口 | 现实 |
|---|---|
| "现在的方法够用了，别折腾" | 够用 ≠ 最优。有分量工作上省下的拷问时间，会在返工时加倍还回去。 |
| "先跑通再说，之后再优化" | 可以，但把"之后再优化"写进判决卡；让没比较过的默认值混进交付物就是债。 |
| "没有更好的办法" | 说出来，并让它成为判决的一部分——但前提是你真的找过：搜过、问过、看过同类问题怎么解。 |
| "拷问太贵了" | Mode A 的成本是一张 10 行判决卡；对比选错路线推倒重来的成本，这是最便宜的保险。 |

## 与其他 Skill 的关系

| Skill | 关系 |
|---|---|
| `grill-me` | grill-me 审需求（做什么/边界在哪），grill-method 审方法（怎么做/是否最优）。需求已澄清、方法待审视时用本 Skill |
| `doubt-driven-development` | DDD 用新上下文审查者验证具体决策的对错；grill-method 是自导向的方法路线比选，无需 spawn agent。先 grill-method 选路线，路线上的非平凡决策再用 DDD |
| `architecture-guard` | architecture-guard 是代码架构的专项合规检查；grill-method 是通用方法论审查，可先于它审视"要不要这样组织代码" |
| `task-spawner` | Mode A 的判决卡可作为任务存档的一部分，随任务传递给执行者 |
