# Doc Template（文档模板管理器）

> **核心定位**：全局文档模板管理中枢（不绑定特定项目）。既是一个**文档生成工具**（AI 读取代码库自动填充模板占位符），也是一个**模板管理工具**（创建 / 添加 / 修改模板）。
>
> **模板目录**：本 SKILL.md 同级的 `assets/`（随本 Skill 目录分发，位于本文件同级 `assets/`）。下文所有 `<SKILL>/` 即指该目录，**不要写死绝对路径**。

## 模板清单（唯一权威表）

> 选模板、定输出位置、定章节数**只看这一张表**，其余章节不再重复。

| 模板文件 | 回答的问题 | SOP 编号 | 默认输出 | 章节规模 |
|---------|-----------|---------|---------|---------|
| `<SKILL>/assets/requirement-doc-template.md` | **要做什么**：用户故事、EARS 需求表、来源标注、五层追问、阻塞项、AI 友好度评分卡 | `01` | `01-requirements.md` | 12 章 + 附录 |
| `<SKILL>/assets/tech-design-doc-template.md` | **怎么实现**：配置项变更、领域模型、状态机、接口设计、监控发布、边界兜底、安全合规 | `03`（含 DDL 另存 `04`） | `03-technical-design.md` | 7 章 + 附录 |
| `<SKILL>/assets/test-report-template.md` | **测了什么 / 能否上线**：范围与排除理由、用例清单、关键场景、覆盖率、执行结果、缺陷、结论 | `05` | `05-unit-test-report.md` | 8 章 + 附录 |
| `<SKILL>/assets/release-doc-template.md` | **今晚怎么发 / 出事怎么退**：Story 链接 + 发布内容摘要、应用与依赖顺序、按环境替换的值 / SQL / Nacos / 定时任务、监控与一致性稽查、应急回滚、上线 Checklist | `09` | `09-release-doc.md` | 6 章 |

**阶段边界**：需求文档只写 What；技术方案只写 How（方案层：指标设计、灰度思路、回滚方向）；测试报告只写验证结果；**发布文档只写执行层**（具体 SQL、具体配置值、具体 CMDB 任务、具体勾选动作）。四者不互相抄。

四者是 SOP 上下游：`01 需求 → 03 技术方案 → 05 测试报告 → 09 发布文档`。用户一次要全套时按此顺序生成。

## 执行流程

### Step 0: 意图识别与模式选择

根据用户意图自动选择模式，**不需要向用户确认模式**：

| 用户表达 | 模式 |
|---------|------|
| "写需求文档 / 需求分析 / PRD 转需求"、"写技术方案 / 设计文档 / 技术设计"、"写测试报告 / 单测报告"、"写发布文档 / 上线文档 / 发布单 / 上线checklist"、"生成文档 / 用模板写" | **USE** |
| "添加模板 / 新增模板"（在现有模板上加章节、字段） | **ADD** |
| "创建模板 / 新建模板 / 从头设计模板" | **CREATE** |
| "修改模板 / 改模板 / 优化模板 / 优化这个 skill" | **MODIFY** |

**复合意图**：按顺序执行（如"先写发布文档，再优化模板"），一个模式完成后再切下一个。**一次要整套**（"生成全套文档"）时按 `01 → 03 → 05 → 09` 顺序逐份产出，每份完成后先让用户确认再继续。

### Step 1: USE 模式 — 使用模板生成文档

#### 1.1 选模板 + 定落点

按「模板清单」表选模板并 `Read` 全文。落点规则：

| 场景 | 落点 |
|------|------|
| 项目有 `docs/sop-traces/{需求ID}/` | `docs/sop-traces/{需求ID}/{编号}-xxx.md`，沿用已有目录，**不另开平行目录** |
| 项目有其它 SOP 目录约定 | 按项目约定（读项目 `CLAUDE.md` / `AGENTS.md` 确认） |
| 都没有 | `docs/sop-traces/{需求ID}/{编号}-xxx.md`（新建） |
| 用户指定路径 | 以用户为准 |
| 用户说"先看看 / 预览 / 不要落文件" | 只在对话中输出，不写文件 |

#### 1.2 收集信息：先扫代码，再问人

| 信息项 | 来源 | AI 可推导？ |
|--------|------|------------|
| 关联 PRD 与参考材料 | `01-requirements.md` 优先；无则用户输入 | 部分 |
| 需求概述 / 交付能力 | 用户输入 + 需求文档 + 本批次 commit | 部分 |
| 涉及模块 / 文件 | 代码扫描 | 是 |
| 接口 / Controller / 错误码 | 代码扫描 | 是 |
| 实体 / 字段 / 状态机 | 代码扫描 | 是 |
| Nacos 配置 / Redis Key / MQ Topic / 定时任务 / 分布式锁 | 代码扫描 + 项目 bootstrap 配置 | 是 |
| DDL / DML | 代码 + `sql/`、`db/` 目录 | 是 |
| 监控指标 / 日志关键字 | `log.info/warn/error` 语句 + 异常类 | 是 |
| 发布窗口 / 回滚决策人 / 审批人 | 用户输入 | 否 |
| 灰度策略 / 业务决策 / 数据口径 | 用户输入 | 否 |

**扫描策略**（按优先级）：

1. **模块定位**：`Grep` 关键词/类名，定位 Controller / Service / Mapper / Entity
2. **接口推导**：从 `@RequestMapping` / `@PostMapping` 等注解生成接口列表；**路径要按项目实际前缀补全**（如 项目在 `WebConfig` 统一添加 `/<app-prefix>/api`）
3. **实体推导**：从 Entity/DO 生成字段表与 Mermaid `erDiagram`
4. **状态机推导**：从状态枚举 + 转换逻辑生成状态定义与 Mermaid `stateDiagram-v2`
5. **配置推导**：`Grep` `@Value` / `@ConfigurationProperties` / `@FeignClient(url=...)` / Redis Key 常量 / MQ 注解 / `@XxlJob`
6. **错误码推导**：搜索 `ErrorCode` / `ResultCode` 枚举与 i18n key
7. **上下游推导**：从 Feign Client / MQ Producer·Consumer 推导依赖方向
8. **日志关键字推导**（发布文档专用）：从本次改动文件里的 `log.error` / `log.warn` / 抛出异常处提取**真实存在**的文案或异常类，作为监控关键字，不要编通用词

> **⚠️ 重要原则**：AI 可推导的信息**不要反问用户**，直接扫代码填。只有业务决策、时间窗口、责任人这类代码里没有的信息才问。

#### 1.3 AI 自动填充

按占位符类型处理（语法见「模板文件规范」）：

| 占位符 | 处理方式 |
|--------|---------|
| `<!-- AI:auto:xxx -->` | 扫代码库直接填，不需要确认 |
| `<!-- AI:fill:xxx -->` | 按指引生成草案，**事实类内容**（工单号、镜像 tag、执行结果）标注「待确认」 |
| `<!-- 手动填写:xxx -->` | 留空并写「待人工补充」，不猜 |
| `<!-- 例如：... -->` | 是示例行，填充时**整行替换**，不要把示例留在成稿里 |

#### 1.4 生成后自检（必做，不可跳过）

写完文件后逐项核对，不合格就改，不要在对话里说"已完成"却漏项：

| # | 自检项 | 判定 |
|---|--------|------|
| 1 | 残留示例行 | grep `例如：` 应为 0 处（正文解释性举例除外） |
| 2 | 残留占位符 | 除 `手动填写` 项外，不应有未替换的 `AI:auto` / `AI:fill` |
| 3 | `[必填]` 章节完整性 | 每个必填章节非空，或明确写"本期无 + 原因" |
| 4 | Mermaid 可渲染 | 无中文标点混入语法、无空图、节点 ID 不含空格/括号 |
| 5 | 事实可复核 | 接口路径带全前缀、类名/文件路径/配置 Key 真实存在（抽查 2 条） |
| 6 | 阶段边界 | 需求文档无实现细节；技术方案无测试结论；发布文档无方案论证 |
| 7 | 人工补充清单 | 文末列出需人工确认项（见 1.5） |

#### 1.5 人工补充提醒

生成文档后，在末尾追加：

```markdown
---
### ⚠️ 需人工补充/确认的项
1. <!-- 阻塞项，如：发布窗口与回滚决策人 -->
2. <!-- 事实待核，如：CMDB job 号、镜像 tag -->
3. <!-- AI 推断待验，如：状态机是否符合业务意图 -->
---
```

### Step 2: ADD 模式 — 给现有模板加内容

1. `Read` 目标模板全文
2. **字段级**（表格加一行、加一个占位符）：直接执行；**章节级**：先说明插入位置与内容，确认后执行
3. `Edit` 最小差异修改，保持编号连续、占位符语法一致
4. 若新增了章节，同步更新 SKILL.md「模板清单」的章节规模
5. 输出变更摘要（改了什么、影响哪些已生成文档）

### Step 3: CREATE 模式 — 创建新模板

1. 先确认三件事：**回答什么问题 / 在 SOP 哪一环 / 与现有四份的边界在哪**（重叠就要先想清楚怎么切）
2. 参考现有模板规范（占位符三类、`[必填]` 标注、表格优先、Mermaid）
3. 写入 `<SKILL>/assets/{用途}-doc-template.md`，命名：`{用途}-doc-template.md`
4. 更新 SKILL.md：模板清单表 + Step 0 触发词 + 变更记录
5. 若项目有导出副本目录（如 `docs/doc-templates/`），同步写入并说明

### Step 4: MODIFY 模式 — 修改现有模板

1. `Read` 目标模板全文
2. **文案微调**直接改；**结构变更**先说明范围再改
3. **最小差异原则**：不重写整份文件；改完保持占位符语法、章节编号、`[必填]` 标注一致
4. 展示变更摘要 + 修改后的章节骨架预览
5. 版本号 +1（模板内部 `附录：文档变更记录` 与 SKILL.md 变更记录**两处都要改**）

### Step 5: 优化整个 Skill（MODIFY 的全局变体）

用户说"优化这个 skill"时，按这四类体检：

| 检查面 | 看什么 | 典型问题 |
|--------|--------|---------|
| 去重 | 同一信息是否在多处重复表述 | 模板选择规则散落 3 处，改一处忘两处 |
| 语法统一 | 占位符、章节标注是否只有一套 | `<!-- AI:xxx -->` 与 `<!-- AI:auto:xxx -->` 混用，AI 无法按类型分流 |
| 覆盖度 | SOP 每一环是否都有模板 | 有 01/03/05，缺 00/02/06/07/08/09 |
| 工程化 | 路径是否写死、导出副本是否靠手抄 | 写死 `~/.claude/skills/...`；导出副本与源文件不同步 |

改完后**必须**：同步 `assets/` 四份模板的头部说明、同步导出副本、更新变更记录。

## 模板文件规范

1. **文件头**：用途 + 与相邻模板的分工 + 占位符说明 + 章节约定，五行以内
2. **占位符三类**（只用这三类，不自创）：
   - `<!-- AI:auto:xxx -->` — AI 可从代码库/配置/日志自动推导，不需人工确认
   - `<!-- AI:fill:xxx -->` — AI 按指引生成草案，事实类内容需人工确认
   - `<!-- 手动填写:xxx -->` — 代码里没有，必须人工提供
   - 三者的区别是**责任归属**：auto 出错算 AI 的，fill 出错需人复核，manual 是人的输入
3. **章节标注**：`[必填]` / `[选填]` / `[有则必填]`（无变更时写"本次无变更 + 已核对方式"，不允许沉默跳过）
4. **表格优先**：信息结构化，便于 AI 填充与人工核对
5. **示例行写 `<!-- 例如：... -->`**，填充时整行替换（生成后自检第 1 项）
6. **Mermaid**：状态机 / 时序 / ER / 流程统一 Mermaid，禁止 PlantUML / ASCII 艺术（GitLab、GitHub、Typora、VS Code 均原生支持，AI 可直接生成）
7. **模板自身不带项目绑定**：项目特有章节（多租户、KYC/AML 等）以「可增删」表述，不写死平台名

## 质量基线（写模板/生成文档时的专业要求）

| 场景 | 硬要求 |
|------|--------|
| 接口路径 | 写**全前缀**（含 context-path 与网关前缀），并说明前缀由谁拼接 |
| SQL | DDL 带「耗时/锁表风险 + 可回滚性」；DML 必须幂等可重跑（`WHERE NOT EXISTS`）+ 前置校验 + 执行后自检 |
| 配置变更 | 必须区分「需变更」与「已核对无需变更」，后者写原因 |
| 监控 | 关键字必须来自真实日志文案；配「正常区间 / 告警阈值 / 出现后的动作」三件套 |
| 一致性 | 至少一条可执行的对账 SQL，而不是"关注数据一致性" |
| 回滚 | 分层写（应用 / 配置 / DML / DDL / 网关）+ 触发阈值 + 决策人；不可回滚项必须给降级替代 |
| Checklist | 每行带「执行人 + 时间 + 证据」，可事后追溯；任一未勾不得进入下一阶段 |
| 依赖关系 | 用顺序结论表写死「谁先谁后」，不允许发布当晚临场判断 |

### 发布文档（09）专属红线

| 禁止 | 原因 | 正确写法 |
|------|------|---------|
| 元说明（「本文只写发布与运维需要的事实」「详见设计文档，本文不再重复」） | 读者看标题就知道；重复出现更显啰嗦 | 直接写事实。文档定位放交付消息里，不放进正文 |
| 变更史（「2026-11-12 更新：重构移除…新增…」） | 属于 commit message / 文档变更记录表 | 什么都不写；需留痕写文末变更记录表 |
| 三环境坐标大全（入口域名 / DB 主机 / Nacos 地址三列表） | 运维手上有环境清单，占了篇幅还不准 | 只写**同一内容在不同环境取值不同**的项（§3.1） |
| Story 展开成 PRD + 仓库分工矩阵 | 发布时只需要"哪些需求在这个批次里" | Story 编号 + 标题 + wiki 链接 + 一行备注 |
| 把技术方案 §五 整段抄过来 | 方案层讲为什么，执行层讲怎么做 | §四 只留"日志前缀 + 判定口径 + 稽查 SQL" |
| 「关注错误日志」「注意数据一致性」 | 无法执行 | 真实日志前缀 + 聚合口径 + 可跑的对账 SQL |

## 反模式

- ❌ 用户说"写技术方案"时，直接在对话里输出文本而不读模板
- ❌ AI 能从代码推导的信息反复问用户（"要不要我搜一下 Controller？"）
- ❌ 生成文档不标注需人工补充的项，也不做生成后自检
- ❌ 修改模板时重写整个文件而非最小差异修改
- ❌ 为了凑章节在没变更的地方编造 SQL / 配置 / 指标
- ❌ 发布文档里写"关注错误日志""注意数据一致性"这类无法执行的话
- ❌ 发布文档正文写元说明、变更史、三环境坐标大全（见「发布文档专属红线」）
- ❌ 把技术方案 §五 的监控发布章节整段复制进发布文档
