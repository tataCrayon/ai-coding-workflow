# Grill-Me（深度追问）

> **核心信念**：代码里找不到答案的问题，才是最危险的问题。动手写代码之前，先把需求里"代码无法告诉你"的部分追问清楚——业务意图、边界条件、异常路径、合规约束、隐性假设。

## 什么时候触发

**硬触发**（用户主动要求）：
- 用户说"grill me"、"追问我"、"先想清楚"、"别急着动手"
- 用户说"帮我澄清需求"、"确认边界"、"需求追问"

**软触发**（AI 自觉判断）——以下场景应主动建议使用本 Skill：
- 新功能/新需求描述模糊，缺少"为什么不"/"什么时候不"/"失败了怎么办"
- 需求文档只有正面描述（"做什么"），缺少反面描述（"什么不做"/"异常怎么处理"）
- 涉及资金/资产/权限变更的操作——涉及真实利益的操作，合规和边界必须先追问
- 跨模块/跨系统接口的改造——不同模块的行为差异可能隐含业务边界

## 追问框架（五层追问法）

按以下五层从外到内依次追问，**不要跳层**。每一层至少产出 2 个追问问题。

### 第一层：Why（为什么做，为什么现在做）

追问业务意图和存在理由——代码不会告诉你"为什么"。

| 追问维度 | 典型问题模板 |
|---------|-------------|
| 业务动机 | 这个需求解决什么业务痛点？不做会怎样？ |
| 时机判断 | 为什么现在做而不是下个版本？有什么外部驱动力（监管/客户/竞争）？ |
| 替代方案 | 有没有不用改代码就能解决的方案？手动流程/配置变更/第三方工具？ |
| 价值量化 | 成功后可观测的业务指标是什么？怎么度量"做对了"？ |

### 第二层：What Not（什么不做，边界在哪）

追问需求的反面——代码不会告诉你"什么时候不该执行"。

| 追问维度 | 典型问题模板 |
|---------|-------------|
| 排除边界 | 哪些场景明确**不**属于本次需求？最常见的"误触发"场景是什么？ |
| 前置条件 | 操作执行的前置条件是什么？条件不满足时是报错还是静默跳过？ |
| 停止条件 | 什么情况下需要中断/回滚？谁来决定中断？ |
| 合规红线 | 是否涉及合规/安全约束？红线是什么？触碰后怎么处理？ |

### 第三层：When Wrong（失败了怎么办）

追问异常路径——代码不会告诉你"出错了之后业务上期望什么"。

| 追问维度 | 典型问题模板 |
|---------|-------------|
| 操作失败 | 如果关键操作失败了，业务上期望什么？重试？标记？人工介入？ |
| 部分成功 | 如果操作只完成了一半（如数据写入成功但状态更新失败），期望什么？ |
| 下游影响 | 如果本操作失败，下游依赖方会怎样？需要通知谁？ |
| 用户体验 | 用户看到的是"失败提示"还是"处理中"？需要多久后才告知结果？ |

### 第四层：Who & Where（谁受影响，哪里受影响）

追问影响范围——代码不会告诉你"改了这个还有谁会受影响"。

| 追问维度 | 典型问题模板 |
|---------|-------------|
| 上下游 | 改了这个接口/流程，下游有哪些消费者会受影响？是否需要灰度？ |
| 外部差异 | 不同外部系统/供应商对这个场景的行为是否一致？不一致怎么办？ |
| 数据一致性 | 改了逻辑后，存量数据是否需要迁移/修复？新旧数据能否共存？ |
| 多租户/多环境 | 是否涉及多租户或多环境差异？每个租户/环境的行为是否一致？ |

### 第五层：How Deep（深层假设和隐性约束）

追问那些"所有人都知道但没人写下来"的东西。

| 追问维度 | 典型问题模板 |
|---------|-------------|
| 隐性假设 | 你有没有默认假设"某个条件永远成立"？如果它不成立呢？ |
| 序列化约束 | 操作是否有顺序依赖？并发执行会怎样？ |
| 精度与类型 | 数值计算是否涉及精度问题？最小单位是什么？用什么数据类型？ |
| 依赖链 | 是否依赖外部审批/确认流程？审批超时/被拒怎么办？ |

## 执行流程

### Step 0：读取项目知识

追问前先读项目知识资产，避免重复追问代码里已有答案的问题：
1. 读取 `.notes/foundation/glossary.md`——对齐术语
2. 读取 `.notes/knowledge-index.md`——定位相关资产
3. 如果需求涉及特定业务域，读取对应的分析资产

**原则**：能用代码/资产回答的问题不要追问用户，只追问"代码里找不到答案"的问题。

### Step 1：五层追问

按五层框架依次追问。每层追问：
1. 先检查代码/资产能否回答——能回答的跳过
2. 生成至少 2 个追问问题
3. 将所有问题整理为结构化清单

**输出格式**：

```markdown
# 🔥 Grill-Me 追问清单

> 针对需求：{需求描述一句话}
> 代码/资产已有答案的维度已跳过，仅列出需要人类判断的问题。

## 第一层：Why（业务意图）
| # | 追问 | 为什么追问（代码无法回答的理由） | 优先级 |
|---|------|------|------|
| W1 | {问题} | {理由} | 🔴必须 / 🟡建议 |

## 第二层：What Not（边界排除）
| # | 追问 | 为什么追问 | 优先级 |

## 第三层：When Wrong（异常路径）
| # | 追问 | 为什么追问 | 优先级 |

## 第四层：Who & Where（影响范围）
| # | 追问 | 为什么追问 | 优先级 |

## 第五层：How Deep（隐性假设）
| # | 追问 | 为什么追问 | 优先级 |

## 📊 追问总结
- 🔴 必须回答：{N} 个（不回答就不要动手）
- 🟡 建议回答：{N} 个（不回答可能在后续踩坑）
- 💬 代码已有答案已跳过：{N} 个维度
```

### Step 2：等待回答

将追问清单呈现给用户，等待逐条回答。对于 🔴 必须回答的问题：
- **未回答就动手写代码 = 高风险行为**
- {涉及资金/资产/权限}的 🔴 问题未回答时，**必须拒绝执行**

### Step 3：答案归档

用户回答后：
1. 将答案整理为「需求边界备忘」，保存到 `.notes/analysis/{domain}/` 下（如有活跃任务则保存到任务文件）
2. 更新 `knowledge-index.md` 索引
3. 答案中涉及新术语的，同步更新 glossary

## 🛑 红线

- **涉及资金/资产/权限变更**的操作，**🔴 问题未回答前禁止编写代码**
- **接口签名变更**的 🔴 问题未回答前禁止修改接口
- **不要追问代码里已有答案的问题**——先查代码/资产，只追问人才能回答的
- **不要连续追问超过 15 个问题**——超过时优先追问 🔴 必须回答的，🟡 建议回答的可分批
- **不要替代用户做业务决策**——追问是为了让用户做出明确决策，不是让 AI 替用户决策

## 与其他 Skill 的关系

| 关联 Skill | 关系 |
|-----------|------|
| `code-business-analyzer` | grill-me 先追问边界，code-business-analyzer 再分析代码实现 |
| `spec-verifier` | grill-me 的答案可作为 Spec 输入，spec-verifier 校验 Spec 完整性 |
| `knowledge-asset-manager` | grill-me 产出的答案归档由 knowledge-asset-manager 落盘 |
| `code-review-checklist` | grill-me 产出的边界约束可在 CR 时作为检查维度 |

## 协作声明

- **上游输入**：无（grill-me 是需求澄清入口，不依赖其他 Skill 输出）
- **下游输出**：
  - **code-business-analyzer**: 追问答案中的业务边界 → code-business-analyzer 在分析时纳入约束
  - **spec-verifier**: 追问答案中的需求要点 → spec-verifier 校验 Spec 需求覆盖度
  - **knowledge-asset-manager**: 追问答案归档 → knowledge-asset-manager 落盘到 .notes/
