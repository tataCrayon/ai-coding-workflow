# Workflow Optimization Log（工作流优化记录引擎）

> **核心定位**：工作流变更的完整生命周期管理——从"为什么要改"到"改了什么"到"效果如何"，确保每次优化都有完整留痕、可回溯、可恢复。
>
> **与 workflow-retrospective 的分工**：retrospective 管"摩擦点趋势"（哪里有问题），本 Skill 管"优化过程本身"（做了什么优化、为什么这样做、排除了什么方向）。两者互补：retrospective 的改进建议可以作为本 Skill 的优化立项输入；本 Skill 的变更记录可以作为 retrospective 的评估数据源。

## 🎯 核心能力

| 模式 | 适用场景 | 输出 | 触发方式 |
|------|---------|------|---------|
| **A: 记录变更** | 每次修改 Skill/Rule/工作流文件 | 变更日志条目 | Rule `workflow-change-tracker` 强制触发；或用户指令"记录变更" |
| **B: 优化立项** | 启动一轮系统化优化 | 优化项目档案（含调研→评估→实施→验证→回顾计划） | 用户指令"优化立项"；或 retrospective 改进建议驱动 |
| **C: 优化回溯** | 查看历史优化、恢复中断的优化 | 回溯报告 / 恢复断点 | 用户指令"查看优化历史"/"恢复优化" |
| **D: 优化回顾** | 一轮优化完成后复盘效果 | 优化回顾报告 | 优化项目状态变为"已完成"后触发；或用户指令"优化回顾" |

## 🚦 触发时机

- **Rule 强制触发**：`workflow-change-tracker` 检测到工作流文件变更时，自动触发模式A
- **用户显式指令**："优化记录"、"优化立项"、"优化回溯"、"优化回顾"、"OPT日志"
- **retrospective 建议**：workflow-retrospective 报告中的改进建议，可由用户确认后转化为模式B优化立项
- **eval-log 驱动**：eval-observer 日志中的改进建议指向具体 Rule/Skill 缺陷时，可转化为模式B

## 📁 存储结构

```
.agent/eval/
├── logs/                          # eval-observer 观测日志（已有）
├── workflow-changes/              # 工作流变更日志（新增）
│   ├── INDEX.md                   # 变更索引（所有 OPT 条目的快速查找表）
│   ├── YYYYMMDD_OPT-{序号或语义}.md  # 单条变更日志
│   └── ...
├── last-retrospective.md          # retrospective 时间戳（已有）
└── log-template.md                # eval-log 格式规范（已有）
```

> 存储位置选择理由：放在 `.agent/eval/` 下而非单独目录，因为优化记录本质上是评估生态的一部分——与 eval-logs（记录摩擦点）和 workflow-retrospective（聚合趋势）在同一评估闭环中。

## 🔒 不可协商规则

1. **模式A 零遗漏**：每次对工作流文件的实质性修改都必须触发模式A记录（由 Rule `workflow-change-tracker` 保障）。无日志的变更视为违规。
2. **问题驱动**：所有优化必须有明确的问题描述——没有问题的变更是可疑的。
3. **模式B 调研强制**：系统化优化必须包含调研阶段，搜索权威资料/行业实践。无调研的优化标注"调研不足（风险：可能不是最优方案）"。
4. **排除方向必填**：模式B 必须记录排除了什么方向及原因。即使只讨论了一个方案，也写"无替代方案讨论"。
5. **验证闭环**：模式B 完成后必须触发模式D回顾。效果不达预期时必须迭代。
6. **主对话零开销**：模式A 的变更记录是附随动作，不打断主对话（与 eval-observer 同原则）。

## 模式A：记录变更（单条变更日志）

> 最轻量的模式。每次对工作流文件的修改都必须产出一条变更日志，确保零遗漏。

### 执行流程

1. **识别变更类型**：新增Skill / 修改Skill / 新增Rule / 修改Rule / 流程调整 / 架构重构 / 模板更新
2. **识别触发来源**：用户需求 / eval-log驱动 / retrospective建议 / 主动优化 / 紧急修复
3. **描述解决的问题**（**必须有**——没有问题的变更是可疑的）
4. **列出修改的文件清单**（路径 + 改动摘要）
5. **生成序号**：读取 INDEX.md 中最大序号 +1，格式 OPT-{三位序号}
6. **写入变更日志**：按 [change-log-template.md](references/change-log-template.md) 格式写入 `.agent/eval/workflow-changes/YYYYMMDD_OPT-{序号}_{简述}.md`
7. **更新索引**：追加条目到 `.agent/eval/workflow-changes/INDEX.md`
8. **向用户输出确认**：1-2 行确认，不打断工作流

### 序号生成规则

- 全局递增序号，从 `OPT-001` 开始
- 读取 `INDEX.md` 中最大序号 +1
- 简述使用 2-5 个中文关键词，遵循任务命名规范

## 模式B：优化立项（系统性优化循环）

> 重量级模式。启动一轮完整的优化循环：问题识别 → 调研 → 方案评估 → 实施 → 验证 → 回顾。
>
> **对标经典工程方法**：评估→测试→发现问题→优化迭代

### 执行流程

#### Step 1：问题识别与立项

1. **问题来源判定**：
   - eval-log 中的改进建议（工作流缺陷指向具体 Rule/Skill）
   - workflow-retrospective 报告中的改进建议（高频摩擦点/系统性问题）
   - 用户直接提出的优化需求
   - AI 主动发现的模式（如 Skill 触发率持续偏低）

2. **问题描述规范化**：
   - 当前状态（What's wrong）
   - 影响范围（Who/What is affected）
   - 期望状态（What should be）
   - 可衡量的改进目标（如："该类摩擦点出现频次降低 50%"）

#### Step 1.5：架构版本联动（涉及架构变更时强制执行）

> 当优化项目涉及架构层变更（新增/删除 Skill/Rule/Hook、修改 AGENTS.md、调整上下文分层策略等）时，**必须**执行以下联动步骤，确保架构快照与变更记录双向关联。

1. **读取当前架构版本**：从 `ai-coding-workflow/ARCHITECTURE_VERSION` 或最近的架构快照文件（`.agent/eval/retrospective/` 目录）中提取当前版本号
2. **创建优化前快照**：如果距上次快照 ≥7 天或本次变更涉及架构层，调用 `workflow-retrospective` 模式 D 生成优化前快照
3. **在 OPT 记录中记录架构版本**：
   - `architecture_version_before`: 当前架构版本号（如 V1.0）
   - `architecture_version_after`: 预期变更后的版本号（如 V1.1）——仅在重大架构变更时升级版本号
4. **版本号升级规则**：
   - **小版本**（V1.0→V1.1）：新增/修改 Skill/Rule/Hook，架构层级不变
   - **中版本**（V1→V2）：架构层级调整、新增层级、核心原则变更
   - 版本号由优化项目发起人（用户或 AI）建议，用户确认后生效

#### Step 2：调研阶段（**强制执行，不可跳过**）

> **硬约束**：优化不能闭门造车。每轮优化立项必须包含调研阶段。

1. **搜索权威资料**：
   - Anthropic 官方文档（Claude Code 最佳实践、Agent SDK 指南）
   - Google SRE / Design Doc Review 等行业权威实践
   - 主流 AI coding 工具最佳实践（Cursor/Cline/Aider 等）
   - 相关论文/博客（如 Context Engineering、Spec-driven development）

2. **记录调研来源**：每个来源附 URL 或文档路径
3. **记录关键发现**：行业做法是什么、与我们现状的差异在哪
4. **最小调研量**：至少搜索 2 个不同来源的相关资料。少于 2 个来源时标注"调研不足"

#### Step 3：方案评估

1. **列出候选方案**：2-3 个方案（含"保持现状"作为基线）
2. **评估优劣**：彻底程度 / 实施复杂度 / 对现有生态的影响 / 可逆性
3. **记录排除方向**：**必填**——每个排除方向写明排除原因
4. **选定方案**：明确最终选定方案及选择理由

#### Step 4：实施阶段

1. 按选定方案修改 Rule/Skill/流程文件
2. 每次文件修改后，Rule `workflow-change-tracker` 自动触发模式A记录
3. 实施过程中发现新问题 → 记录并决定是否调整方案

#### Step 5：验证阶段

1. **功能验证**：在真实任务场景中触发修改后的 Rule/Skill，观察行为是否符合预期
2. **回归验证**：确认修改没有破坏其他 Skill/Rule 的正常运行
3. **效果衡量**：对比优化前后的摩擦点频次/Skill 触发准确率等指标
4. 效果不达预期 → 回到 Step 4 调整，或回到 Step 3 换方案

#### Step 6：回顾阶段（触发模式D）

1. 优化项目状态更新为"已完成"
2. 触发模式D，生成优化回顾报告

## 模式C：优化回溯

> 回溯历史优化记录、恢复中断的优化项目。

### C1：查看优化历史

1. 读取 `.agent/eval/workflow-changes/INDEX.md`
2. 支持按维度过滤：时间范围 / change_type / trigger / status
3. 输出回溯报告：每次变更的动机、方案、排除方向、验证结果

### C2：恢复中断的优化

1. 找到 INDEX.md 中 status 为"进行中"的条目
2. 读取对应变更日志详情
3. 确定断点位置（哪个阶段未完成）
4. 重建计划，从断点继续

### C3：查看特定变更的详情

用户指定变更ID（如 OPT-003）时：
1. 读取对应变更日志条目
2. 输出完整变更详情

## 模式D：优化回顾

> 一轮优化完成后（或用户主动要求）的复盘。对比优化前后的效果，确认改进是否落地。

### 执行流程

1. **确定回顾对象**：指定的变更ID或优化项目
2. **收集前后对比数据**：
   - 读取变更日志条目（问题驱动、方案、排除方向）
   - 查找关联的 eval-log（优化前后的摩擦点记录）
   - 查找关联的 retrospective 报告（优化前后的趋势数据）
3. **效果评估**：
   - 预期改进目标是否达成？
   - 关联摩擦点是否减少？
   - 是否引入了新问题？
   - 排除方向是否仍然正确？
4. **生成回顾报告**：追加到变更日志末尾或单独写 `YYYYMMDD_OPT-{序号}_review.md`
5. **更新变更日志状态**：效果达标 → status="已完成"；效果不达标 → status="需迭代"
6. **架构版本对比**（当涉及架构变更时）：读取优化前后的架构快照，对比差异（新增/删除/修改了哪些模块），评估架构演进是否符合预期

## 🔗 与其他能力的协作

**上游输入**：
- **workflow-change-tracker**（Rule）→ 检测到工作流文件变更 → 触发模式A
- **workflow-retrospective** → 改进建议 → 可转化为模式B优化立项
- **eval-observer** → 日志中改进建议指向 Rule/Skill 缺陷 → 可转化为模式B
- **skill-creator** → Skill 创建/修改完成 → 触发模式A

**下游输出**：
- **workflow-retrospective** → 变更记录 + 回顾报告 → 作为 retrospective 评估数据源和改进落地追踪
- **task-spawner** → 优化项目档案 → 可通过 PAUSE 模式跨会话存档
- **MEMORY.md** → 优化教训 → 可晋升为记忆

## ⚠️ 约束

- **主对话零开销**：模式A的变更记录是附随动作，不打断主对话（与 eval-observer 同原则）
- **调研硬约束**：模式B 必须包含调研阶段；模式A 如无调研需标注风险
- **排除方向必填**：每次变更必须记录排除了什么方向（或显式写"无替代方案讨论"）
- **不自动修改 Rule/Skill**：本 Skill 只记录和追踪，不自动执行修改（模式B 的实施阶段由用户确认后执行）
- **禁止自循环**：本 Skill 自身的创建/修改不触发 workflow-change-tracker（首次创建由 skill-creator 管理）

## 🏗️ 架构版本追踪

> 架构版本是工作流系统的"发布版本号"，标记架构层面的重大状态变化。
> 与 OPT 记录关联，实现"每个版本对应哪些变更"的可追溯性。
> 与 `workflow-retrospective` 模式 D（架构快照）联动，实现"状态快照 ↔ 变更记录"双向关联。

### 版本号管理

| 文件 | 作用 | 位置 |
|------|------|------|
| `ARCHITECTURE_VERSION` | 当前架构版本号（一行文本，如 "V1.0"） | `ai-coding-workflow/ARCHITECTURE_VERSION` |
| 架构快照 | 每个版本的完整架构状态 | `.agent/eval/retrospective/YYYYMMDD_architecture-snapshot_{版本号}.md` |
| OPT 记录 | 每个版本包含的变更清单 | `.agent/eval/workflow-changes/` |

### 版本演进记录

每次重大架构版本变更后，在 `.agent/eval/workflow-changes/INDEX.md` 的版本演进记录表中追加一行。

### 与 retrospective 的联动

- **模式 B 优化立项时**：Step 1.5 读取当前架构版本 → 调 retrospective 模式 D 拍优化前快照
- **模式 D 优化回顾时**：读取优化前后快照 → 对比差异 → 评估架构演进
- **小版本变更**（V1.0→V1.1）：OPT 记录中标记版本，不强制拍新快照
- **中版本变更**（V1→V2）：必须拍优化前快照 + 优化后快照

## 质量自检

每次写入变更日志后，必须检查：
- 问题驱动是否明确？（不能只写"优化了 XX"，必须写"因为 XX 问题做了这次优化"）
- 排除方向是否记录？（即使写"无"，也必须有此字段）
- 索引是否同步更新？（INDEX.md 必须追加）
- 回滚路径是否可追溯？（变更日志中 files_changed 列表 + git history）
