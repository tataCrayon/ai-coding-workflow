# Audit & Slim（工作流审计瘦身）

> **核心定位**：把"工作流是否过重"从主观感受变成**有证据的审计**，每轮减重可量化、可回溯。
> **适用时机**：任何"工作流变重、任务变慢、token 变多"的信号出现时 → 跑一轮完整审计；无信号时按季度节奏例行跑。
> **来源**：从一次全局上下文降重实战（rules 分层 / skill 瘦身 / effort 降档，-60% 常驻注入）提炼固化而成，方法论见本文件与 [docs/EVOLUTION-V3.md](../../docs/EVOLUTION-V3.md)。

---

## 失败模式（为什么需要审计）

1. **常驻资产无触发证据**：rules/skills/hoooks/cron 配上就常驻，但从未在真实任务中命中，"显得有用"不等于"真被用过"
2. **为旧模型/旧环境写的补偿**：模型能力升级后（如上下文 200K→1M、工具按需加载），以前需要写的"防御性规则"已不需要
3. **被工具/测试覆盖**：确定性机制（hook/CI/测试）出现后，同职责的概率性话术（文字规则）应该退役
4. **新增无闸门**：每加一条规则都很合理，但加起来就是膨胀；缺"新增过滤器"

## Step 0（版本升级后必跑）：内容一致性巡检

> 触发时机：**版本升级 / 大规模迁移 / 规则重组落地之后**。此时最大风险不是膨胀，而是**新旧并存**——新文档上线了，旧规则还活着且与之矛盾。V3.0 梳理的复盘教训（见 Step 0.4 案例）证明：改完主体 ≠ 收敛完成。

四层检查，每层都有确定性工具或明确动作：

| 层 | 检查什么 | 怎么查 |
|----|----------|--------|
| L1 链接层 | symlink/junction 断链 | `scripts/check-links.py`（Windows 注意：`os.path.islink` 认不出 junction，用 `dir /a` 找 `<JUNCTION>`） |
| L2 引用层 | 文档/技能引用的文件是否存在（幽灵引用） | `check-links.py --dir <skills目录>`；零 issue 才算过 |
| L3 指挥层 | rules/入口文件是否还在指挥已退役的能力、与新流程**双头指挥** | 全文检索旧件名；每个命中判断：叙述性提及（保留）/ 指挥性引用（改写或加消歧注记） |
| L4 陈述层 | 数字/版本号/名称/路径是否与新现状一致 | 抽查门面文档（README/架构文档/版本文件）中的计数与标题；跑密钥与个人路径扫描 |

**判定动词**（防误删）：L3 命中分两类——「叙述性提及」（历史章节、演进记录、案例引用）**保留**；「指挥性引用」（当前仍会被当作执行指令加载的 rules/入口文件）**必须改写**。删文件前先查引用；删引用后再跑 L2 归零。

**案例存档**（2026-09-13，本仓 V3.0 落地复盘，完整经过见 [docs/EVOLUTION-V3.md](../../docs/EVOLUTION-V3.md)）：版本发布后复检仍发现 8 处冲突（铁律触发条件指向已退役编排器、验证规则与包内阶段双头指挥、登记表指向链接壳路径、部署推荐集未更新）+ 2 个该删文件（零引用通知脚本、"待填充"幽灵承诺 README）+ 旧仓库名/个人路径/业务名残留。结论：改完主体 ≠ 收敛完成，Step 0 必须作为发布 DoD。

### Step 0.4 根因备忘（为什么梳理后仍有残留）

1. **梳理的默认视角是"建立新"，不是"清旧"**——写新文档天然不会去检索旧文档里指向相反方向的指挥语句。改法：把"旧件全文检索"列为 Step 0 固定动作，不靠自觉。
2. **缺少机器可查的完成定义（DoD）**——"梳理完了"当时没有可验证标准；后来 check-links.py 归零才变成可判定。改法：任何工作流变更的 DoD 必须包含"巡检工具 exit 0"。
3. **一次性手工扫不全**——48 项引用失效是脚本抓出来的，人眼扫文档抓不到。改法：引用完整性永远交给工具，人只审工具的判定。

## 五步流程（一个工作日内可分次跑）

### Step 1 审计（10 分钟）：把工作流摊成一张表

列出所有**常驻资产**并标注触发证据：

| 资产类型 | 包含对象 |
|---------|---------|
| CLAUDE.md | 每个小节 |
| rules 文件 | 每个文件（focus: 是否被 active loading）|
| skills | 每个 description（focus: 触发词能否被句法命中）|
| hooks / cron | 每次运行/最近一次触发 |
| rules-dev/methodology | 每个方法论文件（看 eval-observer/session log）|

标注两列：**最近一次被触发的证据**、**本条在解决什么失败模式**。

- 触发证据来源：直接问模型"你有没有用到这些规则"、翻会话记录、看评估/hook 日志（部署了评估管线的项目见 `.agent/eval/`）、看 cron 运行记录；都没有 → 无证据
- **没有触发证据的条目直接进入删除候选**

### Step 2 分级（5 分钟）：Keep / Merge / Delete

| 分级 | 判定 | 动作 |
|------|------|------|
| **Keep** | 有触发证据 + 有明确失败模式 + 写入 ≤5 句 | 保留，编号进入"上限预算" |
| **Merge** | 与另一条职责重叠 | 合并成一条，删除被覆盖的 |
| **Delete** | 无触发证据 / 为旧模型写的补偿 / 已被工具或测试覆盖 | 移入 `archived/`（保留 git 历史，不用真删）|

> 分区原则：**设限**见 Step 4。分级时**只依据证据**，不因"这个规则有历史"而保留。

### Step 3 搬迁（10 分钟）：知识放回系统

- **领域知识** → 文档/代码/测试：能编译检查的进 CI，能检索的写进 docs
- **流程约束** → hook/脚本/CI 门禁：确定性的交给机制
- **能力** → Skill 懒加载：只用 description 常驻，正文下沉到 reference/
- **同步清单**：每删一条指令，检查它有没有被某条 hook 或测试"兜住"（防删了规则 → 行为失控）

### Step 4 设限（3 分钟）：给膨胀装三个闸门

- **CLAUDE.md 行数上限**（建议 ≤100 行）：超限就必须拆分到子文件或删除
- **Skill 数量上限**：新增一个 Skill，必须删/合并一个同域旧 Skill（否则总量只增不减）
- **description 字数上限**（建议 ≤120 字）：写不短，说明职责没想清楚

### Step 5 固化（2 分钟）：把审计变成节奏

- **季度"规则税审计"**：按 Step 1 表重跑一遍 sustain（不依赖"感觉胖了"才跑）
- **模型/Harness 升级时触发"重写仪式"**：从零重写 CLAUDE.md，而不是逐条打补丁（旧模型补偿直接退役）
- **联动 workflow-retrospective**：周报若显示摩擦点/token 上升 → 自动触发一轮完整审计

## 新增规则前的五个自问（防回潮过滤器）

无论平台多完善，规则仍会被继续需要。给"新增"装过滤器：

1. **这是知识还是指令？** 知识（事实、映射、算法）→ 放文档/代码；指令（何时、如何做）→ 才考虑写入。
2. **模型自己能不能想出来？** 能，就不写。写规则是在替模型省思考，而省掉的思考会变成模型的负担。
3. **能不能用工具/测试表达？** 能，就换。确定性机制优先于概率性话术。
4. **触发条件是什么？** 写不出明确触发条件的规则，一定会"乱触发"或"永不触发"。
5. **怎么评估它有效？** 没有评估口径的规则，无法判断保留还是删除。

## 输出

| 产出 | 内容 |
|------|------|
| 审计摊表 | 每轮审计的资产清单 + 触发证据 + 分级判定 |
| 分级结果 | Keep（编号进预算）/ Merge（合并项）/ Delete（归档项）|
| 搬迁清单 | 知识→文档、流程→hook、能力→skill 懒加载 |
| 设限值 | CLAUDE.md 行数 / skill 数 / description 字数 三个闸门 |
| 固化动作 | 季度审计 / 重写仪式 的触发条件 |

## 生态位（部署了完整体系时的挂接点；缺件不影响本 Skill 独立运行）

- **巡检工具**：`scripts/check-links.py` 随本 Skill 分发（`--dir <skills目录>` 支持任意部署形态）
- 有 `workflow-change-tracker` 类规则：把 Step 4"五自问"设为新增 Skill/Rule 的强制门槛
- 有 `workflow-retrospective` 类回顾：摩擦点/token 上升趋势 → 自动触发一轮完整审计
- 有优化留痕机制（OPT 式变更档案）：审计结果转立项，保留证据链
