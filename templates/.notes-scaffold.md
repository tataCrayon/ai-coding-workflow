# .notes 知识资产目录脚手架

> 按以下结构在项目根目录创建 `.notes/` 目录。
> 三层架构按变化频率组织知识，避免平铺。

## 目录结构

```
.notes/
├── README.md                    # 知识库使用说明
├── foundation/                  # 🏗️ 基座层 — 项目的"身份证"，极少变化
│   ├── project-brief.md             # 项目简报（必填）
│   ├── system-map.md                # 系统全景地图（必填）
│   ├── module-graph.md              # 🆕 模块活图谱（必填）— 模块间依赖、上下游、角色、契约
│   ├── tech-context.md              # 技术栈上下文（必填）
│   ├── glossary.md                  # 业务术语表（推荐）
│   ├── code-business-mapping.md     # 代码-业务映射表（推荐）
│   ├── external-systems.md          # 外部系统契约表（推荐）
│   └── decisions/                   # 架构决策记录 ADR（按需）
│       └── 001-{decision-name}.md
│
├── patterns/                    # 🔧 模式层 — 可复制的编码范本
│   ├── canonical/                   # 编码范本（新增某类代码时的范例）
│   ├── architecture/                # 架构模式（设计模式应用案例）
│   ├── playbooks/                   # SOP 操作手册（如何做某件事）
│   ├── troubleshooting/             # 排查手册（常见问题排查指南）
│   └── anti-patterns.md             # 反模式清单（禁止做法）
│
└── analysis/                    # 📊 分析层 — 业务链路深度分析
    ├── {domain-1}/                  # 按业务域组织（如：order/、payment/、user/）
    ├── {domain-2}/
    └── archive/                     # 归档参考
```

## 各层定位

| 层级 | 定位 | 更新频率 | 典型内容 |
|------|------|---------|----------|
| **Foundation** | 项目的"身份证" | 极少变化 | 项目简报、系统地图、术语表、ADR |
| **Patterns** | 高频编码动作的可复制范本 | 跟随技术栈演进 | 编码范本、SOP、排查手册 |
| **Analysis** | 特定业务链路的深度分析 | 跟随需求生命周期 | 链路分析报告、规则解读 |

### module-graph.md — 🆕 模块活图谱

```markdown
# 模块活图谱

> 本文件表达模块间的依赖关系、上下游关系、角色定位和对外契约。
> 改动任何模块时，先查此图谱了解影响面。代码变更后必须同步更新此文件。

## 模块角色定位

| 模块 | 角色 | 描述 | 核心入口 |
|------|------|------|---------|
| {gateway} | facade | 对外API门面,路由转发,鉴权拦截 | {GatewayApplication} |
| {auth-service} | core | 鉴权核心,Session管理,SM3签名 | {AuthService} |
| {user-service} | core | 用户管理,账户体系 | {UserService} |
| {product-service} | core | 产品管理,货架与详情 | {ProductService} |
| {order-service} | core | 订单生命周期,买入卖出 | {OrderService} |

<!-- 角色定义: facade=对外门面; core=核心业务; infrastructure=基础设施; external=外部对接 -->

## 模块依赖关系

| 模块 | 依赖谁(调用) | 被谁依赖(被调用) |
|------|-------------|----------------|
| {gateway} | auth-service, user-service, product-service, order-service | {外部客户端} |
| {auth-service} | {Redis, 用户DB} | gateway, order-service |
| {order-service} | auth-service, product-service, user-service, payment-service | gateway |

## 对外契约

| 模块 | 暴露的API/接口 | 消费的外部API |
|------|--------------|-------------|
| {gateway} | /api/v1/*, /admin/* | auth-service: /internal/auth/verify |
| {auth-service} | /internal/auth/verify, /internal/auth/session | Redis: get/set |

## 变更敏感度

| 模块 | 敏感度 | 改动影响说明 |
|------|--------|-------------|
| {gateway} | 🔴 high | 对外门面,改动影响所有外部调用方 |
| {auth-service} | 🔴 high | 鉴权核心,改动影响所有需鉴权的模块 |
| {product-service} | 🟡 medium | 产品管理,改动影响订单和货架 |
| {order-service} | 🔴 high | 订单核心,改动影响资金流和用户体验 |

<!-- 敏感度: high=改动影响3+模块; medium=改动影响1-2模块; low=改动仅影响本模块 -->

> **维护规则**: 任何模块的接口签名变更、新增/删除模块、依赖关系变化时，必须同步更新此文件。`knowledge-asset-manager` Workflow E 会自动验证此文件的时效性。
```

## Patterns 层使用说明

### canonical/ — 编码范本

存放"新增某类代码时应该参考的范例"。每个范本文件应包含：

1. **范本定位**：这个范本适用于什么场景
2. **完整代码示例**：一个可运行的、符合项目规范的完整实现
3. **关键要点**：实现时容易犯错的地方
4. **反模式**：不应该怎么做

命名建议：`{ClassName}-{中文描述}.md`，如 `OrderValidator-订单校验器.md`

### architecture/ — 架构模式

存放项目中使用的设计模式、架构模式的说明和应用案例。

### playbooks/ — SOP 操作手册

存放"如何做某件事"的标准操作流程，如：
- 部署与发布流程
- 本地开发环境搭建
- 消息队列接入指南
- 日志和监控配置规范

### troubleshooting/ — 排查手册

存放常见问题的排查指南，如：
- 单元测试运行问题排查
- 依赖冲突排查
- 性能问题排查

### anti-patterns.md — 反模式清单

集中记录"禁止做法"和常见错误模式。

## Analysis 层使用说明

按业务域创建子目录，每个分析文档应包含：

1. **分析对象**：分析的是什么业务流程/模块/接口
2. **完整链路**：从入口到出口的完整调用链
3. **关键逻辑**：核心业务规则和决策点
4. **数据流**：输入输出和中间状态
5. **扩展点**：可定制和可配置的位置

命名建议：`{ProcessName} {中文描述}.md`，如 `OrderCreateProcess 创建订单链路分析报告.md`

## 检索机制

知识资产通过两级索引进行检索：

1. **knowledge-router.md**（场景路由）：按"我要做什么"快速定位，常驻 AI 上下文，覆盖最高频场景
2. **knowledge-index.md**（关键词索引）：完整的关键词-路径映射表，场景路由未命中时按需加载兜底

随着 `.notes/` 中的资产不断积累，需要定期更新这两个索引文件。可以使用 `knowledge-asset-manager` Skill 进行盘点和校验。
